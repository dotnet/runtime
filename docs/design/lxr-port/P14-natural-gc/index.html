What the collectors do when nobody calls the GC

Our earlier tests called GC.Collect() eight times. Real programs do not do that. This page measures what happens when the collector runs by itself, because the program allocates memory. We wrote the same three programs in C# and in Java. We ran them on the Java LXR, on our .NET port and on the standard collectors of both runtimes.

Short answer

The gap is real, and it is not only about full collections

  • Our port is much slower in real use. In all 24 cases where it finished, it needed 7.5 to 28 times the wall time and 12 to 43 times the CPU time of the .NET Workstation GC.
  • The Java LXR is close to the standard Java collectors. At 4 times the minimum heap or more, it is 1.1 to 2.2 times slower than Java G1. So the Java LXR is a real, working target.
  • Our port stops the program for a long time. Its longest stall is 140 ms to 1.9 s. The Java LXR and the standard collectors stay below 50 ms.
  • Even the cheap collections are slow in our port. In the binary-trees program, neither LXR runs a full collection. The Java LXR pauses for 2 ms on average. Our port pauses for 109 ms.
  • Our port also chooses full collections too often. In the requests program at 4 times the minimum heap, 51 of its 57 collections are full collections. The Java LXR runs none in 113.
  • Our port stops with "Out of memory" in the tightest heap of the list-suffix program, where .NET Workstation and the Java LXR both finish.

This changes our earlier picture

We studied forced full collections first. That was too narrow. In real use, the cost comes from three places: slow normal collections, too many full collections, and slow full collections. All three need work.

01

What we ran

Three programs, written twice

Each program exists in C# and in Java. The two versions do the same steps, use the same random numbers and compute the same checksum. All 234 successful runs of a program gave the same checksum, so every collector did the same work. (36 runs failed: see the limits.) No program asks for a collection while it is measured.

Binary trees

A well-known GC test. It builds many short-lived trees of small objects and keeps one large tree alive. It makes many objects and many pointers. It does not change old objects.

Requests

Like a server with a cache. 32,768 cache entries stay alive (about 295,000 objects). Each of 600,000 requests builds 24 short-lived objects, reads 8 entries and, one time in 8, replaces an entry.

List suffix

4,096 lists of 64 nodes stay alive (262,144 objects). Each of 800,000 steps cuts a list at a random place and builds a new tail. It writes pointers into old objects and makes garbage.

Who competes

In Java

The Java LXR, and the standard collectors G1, Parallel, Serial and ZGC. All run on the same Java build that contains the Java LXR.

In .NET

Our accepted port in three modes (no moving of objects, moving young objects, moving all objects), the Workstation GC and the Server GC. They run on the same .NET build.

How big is the heap

Java objects and .NET objects have different sizes. So we do not use one heap size for both. For each runtime, we find the smallest heap in which its simple standard collector (Java Serial, .NET Workstation) finishes the work. Then every collector of that runtime gets 2, 4 and 8 times this size. A tight heap makes the collector work more.

What we measure

  • Wall time and CPU time of the measured part. An unmeasured warm-up of one eighth of the work comes first.
  • Collections and pause time. The runtime reports them. For the Java LXR, we read its own log, because the Java tools report nothing for it. For our port, we also read its own counters.
  • Longest stall. A helper thread sleeps for 1 ms in a loop and notes how long it really waited. A long wait means that the program stopped. It uses the same method in both runtimes.
  • Peak memory of the process (RSS).

We ran each case 3 times, with the order of the collectors changed in each round, and we use the median. The machine has 16 logical CPUs (Intel Xeon Platinum 8370C) and runs Linux under WSL2. Both runtimes use their default number of GC threads, except that the .NET Server GC uses 2 heaps, as in our earlier tests.

02

How much slower than the standard collector

We compare each collector with the standard collector of its own runtime: the Java LXR with Java G1, and our port with the .NET Workstation GC. We never compare a Java time with a .NET time. A bar of 1 means the same speed. A bar of 10 means ten times slower. The scale is logarithmic.

What the figure shows:

  • Every bar of our port is above 7. The best case for our port is the list-suffix program at the largest heap (7.5 times slower). The worst is the requests program with moving of young objects at the tightest heap (27.7 times).
  • The Java LXR stays between 1.1 and 2.2 at 4 times the heap or more. At the tightest heap it is 1.1 (binary trees), 1.5 (requests) and 6.9 (list suffix). So the Java LXR also needs some room. It is not perfect.
  • Moving objects makes our port slower in most cases.
  • The .NET Server GC is faster than the Workstation GC in the list-suffix program (0.4 to 0.7 times). The table at the end of this page has the numbers.

03

How long the program stops

Low latency is the purpose of LXR. So the stalls matter as much as the total time.

Over all 27 cases, the longest stall of the Java LXR is 7 to 43 ms. For .NET Workstation, it is 8 to 39 ms. For our port, it is 143 ms to 1.9 s.

  • Requests. Our port makes 51 full collections in 57 collections, at about 300 ms each. The Java LXR makes 113 cheap collections of 1.7 ms each. Our policy chooses full collections much more often, although the heap is 4 times the minimum.

05

What it means

  1. The comparison is now fair. The same programs run on the working Java LXR and on our port. The result of the earlier forced tests (a gap of 30 to 100 times) was too large for real use. The real gap is 7 to 28 times. It is still large.
  2. The Java LXR proves that the design can be fast. In the same conditions, it stays within about 2 times of G1.
  3. We must fix more than the full collection. Three problems show up: the cost of the cheap collections, the choice to run full collections, and the cost of a full collection. Our earlier page about the full collection explains the last one. The first two need their own source comparison.
  4. Our port is not robust at tight heaps. It stops with "Out of memory" at 2 times the minimum heap in the list-suffix program, in 9 of 9 runs. .NET Workstation finishes in the same heap size, and the Java LXR finishes in a smaller one.
  5. Memory. Peak RSS of our port is 147 to 658 MiB. The standard collectors use 46 to 146 MiB. The Java LXR uses 869 to 959 MiB in every case, even with a 14 MiB heap. We did not look for the reason. It may come from memory that the Java LXR reserves outside its heap.

Where to look next (a proposal)

  • Count the causes of our collections. Find why the policy chooses a full collection in the requests program.
  • Compare one cheap collection step by step with the Java LXR, as we did for the full collection.
  • Find why the tight heap ends with "Out of memory" in our port.
  • Then fix the full-collection path (the 16 differences in the earlier page).

06

Limits of this measurement

  • One machine, Linux under WSL2, 3 runs per case. The table shows the fastest and slowest run of each case. We did not measure on Windows in this test.
  • The programs are small and synthetic. The heaps are small (14 to 168 MiB).
  • A larger live set makes our port slower still. In one single probe with 1 million live objects (file results/probe-large-live-set.jsonl), our port needed 75 to 98 s. .NET Workstation needed 8 s, Java G1 needed 4 s and the Java LXR needed 7 s. Each collection of our port took about 3 s.
  • Java 11 and .NET 11 have different runtimes. The ratios to the standard collector of the same runtime reduce the problem. They do not remove it.
  • The Java LXR writes a log line for each collection. We did not measure the cost of this.
  • Java ZGC finished in none of the 27 runs. ZGC needs more room than the other collectors. We did not use it in the conclusions.
  • Our minimum-heap search used a shortened run (one twentieth of the steps). The real runs are longer, so a heap of 2 times the minimum can be tight.
  • The measured .NET code is the accepted port e8d2d23 (Release build). Nothing in the collector changed for this test.

Appendix B

Repeat it

The files are in the same folder as this page.

GcBench.cs and GcBench.java
The two versions of the programs. The run mode never calls the GC. An unused calibration mode does, and these results do not use it.
run-matrix.py
Finds the minimum heaps, selects each collector, runs the matrix and records one JSON line per run. It runs in WSL.
summarize.py and build-report.py
Make the medians and the checks of the checksums, and then this page.
results/
runs.jsonl has all 270 runs. summary.json has the 90 aggregated cases. sizes.json has the minimum heaps. probe-large-live-set.jsonl has the single probe with a larger live set.
