# P0.2 — Paper acceptance targets

The numbers the LXR paper actually states, extracted from the local PDF, with a citation for every
one. These become the P9 acceptance thresholds.

> **Read this before quoting any number below.** These are **OpenJDK** measurements against a **G1**
> baseline on a **Java** workload set (DaCapo Chopin), taken on one AMD Zen 3 machine in 2022. They
> are a *reference point for a different runtime*, not a .NET contract. A ratio derived from G1 on
> OpenJDK 11 does not transfer to CoreCLR, and P9 must not treat it as if it does. Section 11 says
> what this does and does not license.

> **Numbers previously circulated in this project are superseded.** Earlier figures came from a text
> proxy, not the PDF. Everything here was re-read from the local file; nothing was carried over.

---

## 1. Source identity — this is *not* the PLDI proceedings paper

The roadmap calls this "PLDI 2022". **The local PDF is the extended arXiv version**, and every
downstream citation has to say so, because table and figure numbering is version-specific.

| property | value |
|---|---|
| path | `C:\github\lxr-reference\paper\2210.17175.pdf` |
| size | 1 044 637 bytes |
| SHA-256 | `7240A23970550D3FE4551A5D987A11CBC32CB2EBD28CFA5C68C4A1A95BD270FE` |
| pages | 17 |
| encrypted | no |
| `/Title` | **`Low-Latency, High-Throughput Garbage Collection (Extended Version)`** |
| `/CreationDate`, `/ModDate` | `D:20221101010213Z` — **1 November 2022** |
| `/Creator` | `LaTeX with acmart 2021/09/24 v1.80 … hyperref` |
| `/Producer` | `pdfTeX 3.14159265-2.6-1.40.21 (TeX Live 2020)` |
| provenance | `paper/SOURCE.txt`: <https://arxiv.org/abs/2210.17175>, downloaded 2026-08-07 |

Four independent signals agree that this is the extended version, not the proceedings version:

1. The `/Title` metadata string ends in `(Extended Version)`.
2. The page-1 title block typesets `(Extended Version)` as a second title line.
3. **There is no venue line, DOI, ACM ISBN, or copyright block anywhere in the file.** The acmart
   template emits those in proceedings mode; this document has none of them. A search of the full
   text finds `PLDI` only inside the bibliography, never as this paper's own venue.
4. It is dated 1 November 2022, whereas PLDI 2022 took place in June 2022.

**Consequence.** Cite as *"LXR extended version, arXiv:2210.17175 (1 Nov 2022), Table N, PDF page M"*.
Never cite as *"PLDI 2022, Table N"*. **I have no copy of the PLDI proceedings version**, so I cannot
say whether its figure and table numbering matches; assume it may not until someone checks.

**Page numbers in this document are PDF page indices (1–17).** The paper carries no printed folios —
running heads contain only the title and the author list, and there is no page number anywhere on the
page. So "page 13" here means the 13th page of the file.

Library provenance: `pypdf` **6.15.0** and `pymupdf` **1.28.2**, both official wheels from the

### The four verification paths

A number is recorded here **only if all four agree**.

| path | what it is | why it is independent |
|---|---|---|
| **A — pypdf naive** | `page.extract_text()`, reading order | baseline; mangles columns, so disagreement is informative |

**No chart-reading was required.** All four targets come from numeric tables or from a caption on a

Scripts in the session workspace, not committed (machine-local paths): `extract.py` (paths A–C),

## 3. Measurement context — what all these numbers are conditioned on

Everything in §4–§7 shares this context, from §4 *Methodology* (PDF pages 9–10) and Table 2 (page 9).

| | |
|---|---|
| collector under test | LXR in **MMTk on OpenJDK**, fork `jdk-11.0.11+6`, commit `1007c9c1f46644d325bb4d4bd3a3d6dc718c713e` (2021-03-10) |
| baseline | **G1**, plus Shenandoah and ZGC, **on the same OpenJDK fork**. "C4 is not available in OpenJDK" |
| machine | **AMD Zen 3, Ryzen 5950X**, 16C/32T, 3.4 GHz, 64 MB LLC, 64 GB DDR4-3200, SSD. "Unless otherwise stated, we report AMD Zen 3 results" |
| OS | Ubuntu 18.04 |
| workload set | **17 benchmarks from the DaCapo Chopin development branch**, commit `b00bfa96b6db296bdc6f57a57e56a9a34b2d2d89` (2022-04-09). `tradebeans` and `tradesoap` omitted — they "frequently fail on this version of JDK 11 unless the C2 compiler is disabled" |
| throughput method | 20 invocations × 5 iterations, **report the fifth iteration**, machine otherwise idle; geomean and 95% CI over the 20; collectors interleaved to reduce systemic bias |
| latency method | 40 invocations, DaCapo *metered* latency (models request queuing) |
| heap sizing | a multiple of the **minimum G1 heap size** per benchmark (Table 3, page 10) |
| LXR configuration | 4 MB lock-free global block allocation buffer; **two-bit reference count**; 128 MB survival threshold; no increment threshold; 5% mature wastage threshold; single evacuation set |

**A caveat that matters for a .NET port.** §4 states the implementation is *"missing class unloading,
compressed pointers, and weak references … we disable them in all systems"* (page 9). Every number
below was measured with those three features switched off in **all four collectors**. A .NET port
cannot disable its equivalents, so these ratios are measured on a runtime configuration a shipping
CoreCLR will never be in.

**ZGC coverage is incomplete by the paper's own admission**: it "fails on many benchmarks at 2× their
nominal heap size because it requires a substantial minimum heap", so ZGC has no geomean in Table 6.

## 4. Target 1 — throughput versus G1 at a 2× heap

### The headline

> **geomean LXR / G1 = 0.958** — Table 6, `geomean` row, LXR column, **PDF page 12**

| | |
|---|---|
| **quoted value** | `0.958` (normalized to G1; **lower is better**, it is a time ratio) |
| **exact source** | **Table 6**, `geomean` row, `LXR` column |
| **page** | PDF page 12 |
| **workload set** | all 17 DaCapo Chopin benchmarks |
| **heap factor** | **2× the minimum G1 heap**, per benchmark (Table 6 caption: *"Benchmark throughput with a 2× heap"*) |
| **baseline** | **G1 on OpenJDK 11**, same fork, same machine |
| **agreement** | paths A, B, C identical; re-read from the rendered page (path D) |

### Corroboration inside the paper

Three statements agree, which is why this target is the most solid of the four:

| source | page | statement |
|---|---|---|
| Table 6 `geomean` | 12 | LXR `0.958`, Shenandoah `1.373`, ZGC — (no geomean) |
| §5.2 prose | 12 | *"LXR's average speedup is 4% over G1 and 43% over Shenandoah."* |
| §5 intro prose | 10 | *"On throughput, LXR improves over G1 by 4% and Shenandoah by 43% on our benchmarks."* |
| Table 5, `2×` row, `Time/G1` | 11 | LXR `0.96`, Shen `1.37`, ZGC — |

`0.958` and the "4%" prose are the same result; Table 5 is the same number rounded to two decimals.
**Use `0.958`** and treat "4%" as its prose rounding, not as an independent measurement.

### Heap-size sensitivity — 2× is not the best case

Table 5 (page 11) shows the same ratio at three heap sizes. Recording all three, because quoting only
2× would overstate how stable the result is:

| heap | Time/G1 — LXR | Time/G1 — Shen | Time/G1 — ZGC | 99.99% Latency/G1 — LXR |
|---|---|---|---|---|
| 1.3× | `0.97` | `1.77` | — | `0.72` |
| **2×** | **`0.96`** | `1.37` | — | **`0.92`** |
| 6× | `1.01` | `1.09` | `1.26` | `0.85` |

**The two halves of Table 5 cover different workload sets**, per its caption: the latency column is the
*"geometric mean of 99.99% latency for cassandra, h2, lusearch, and tomcat"* — the four
latency-sensitive workloads only — while `Time/G1` is throughput *"for all benchmarks"*. Do not read a
row as one experiment over one set. ZGC's `—` at 1.3× and 2× is the paper's own dash: it could not run
at those heap sizes.

**At a 6× heap LXR is *slower* than G1 (`1.01`).** The throughput win is a tight- and moderate-heap
result and it disappears in a generous heap. Any P9 threshold stated as "beats G1" must name its heap
factor or it is meaningless. Note the contrast: **the latency win holds at every heap size** (0.72 /
0.92 / 0.85) while the throughput win does not — further reason to prefer a latency-shaped target.

## 5. Target 2 — GC pause p50 / p95

### The headline

> **p50 = 5.0 ms, p95 = 7.5 ms**, arithmetic mean over 17 benchmarks — Table 7, **PDF page 13**

| | |
|---|---|
| **quoted values** | `50% ms` = **`5.0`**, `95% ms` = **`7.5`** (`mean` row) |
| **exact source** | **Table 7**, columns `50% ms` and `95% ms`, under the `GC Pauses` group |
| **page** | PDF page 13 |
| **workload set** | all 17 DaCapo Chopin benchmarks |
| **heap factor** | **2×** — §5.3, page 12: *"Table 7 presents results for LXR in a 2× heap"* |
| **baseline** | **none — Table 7 is LXR-only.** See the warning below |
| **agreement** | paths A, B, C identical; re-read from the rendered page (path D) |

Prose confirmation, §5.3 page 13: *"The median and 95th percentiles of pause durations are 5.0 and
7.5 ms respectively, on average."*

### The full summary row set, because "5.0 / 7.5" is not the whole picture

| statistic | p50 (ms) | p95 (ms) |
|---|---|---|
| **mean** | **5.0** | **7.5** |
| geomean | 3.0 | 4.7 |
| min | 1.0 | 1.4 |
| max | **20.7** | **24.5** |

The spread is a factor of ~20. `batik` is the worst at 20.7 / 24.5 ms and `h2o`, `pmd`, `h2` are also
well above the mean. A P9 threshold of "p95 ≤ 7.5 ms" would be a threshold on the *mean across a
benchmark set*, which no single workload has to meet — that is a materially different claim from
"p95 ≤ 7.5 ms on every benchmark", which the paper does **not** support.

### **There is no pause comparison against G1 anywhere at this heap size**

This is the most important qualification on this target, and it is easy to get wrong:

- **Table 7 reports LXR only.** It has no G1, Shenandoah or ZGC columns. So the paper provides **no
  p50/p95 pause ratio versus G1** at a 2× heap, or at any heap.
- The paper's only *comparative* GC-pause table is **Table 1** (page 2), and it is a different
  measurement in three ways: it is **lusearch only**, at a **1.3× heap**, and its percentiles are
  **50 / 99 / 99.9 / 99.99 — there is no p95 in it at all**.

For completeness, Table 1 in full (lusearch, 1.3× heap, page 2) — **both halves**, because the GC-pause
half alone inverts the paper's meaning:

| collector | **GC pause** p50 | p99 | p99.9 | p99.99 | **Query latency** p50 | p99 | p99.9 | p99.99 |
|---|---|---|---|---|---|---|---|---|
| G1 | 0.4 | 0.9 | 1.1 | 1.2 | 0.1 | 12.0 | 14.6 | 15.9 |
| Shenandoah | 0.1 | 0.3 | 2.2 | 3.0 | 0.3 | 78.0 | 116.1 | 127.8 |
| **LXR** | 0.9 | 1.4 | 1.8 | 2.9 | **0.1** | **3.0** | **8.0** | **13.1** |

**LXR's GC pauses are longer than G1's at every percentile shown, and its query latency is better at
every percentile** — 3.0 ms vs 12.0 ms at p99, a 4× improvement. That inversion *is* the paper's
thesis, stated in the caption: *"Short GC pauses **do not** assure low latency."*

**Consequence for P9, stated plainly:** an acceptance target of the form *"LXR must beat G1 on GC pause
time"* would **contradict the only comparative pause data the paper contains**. The paper does not
claim LXR wins on pause duration; it claims LXR wins on *application-visible latency* while keeping
pauses short enough not to matter. A pause-duration threshold is the wrong shape of target. If P9 wants
a latency target with a G1 baseline, the paper's supported one is Table 5's **99.99% latency ratio**
(0.72 / 0.92 / 0.85 at 1.3× / 2× / 6×), not a p50/p95 pause figure.

## 6. Target 3 — the Young / Old-RC / SATB reclamation split

### The headline

> **Young 94.3% · Old-RC 0.6% · SATB 5.1%**, arithmetic mean over 17 benchmarks — Table 7, page 13

| | |
|---|---|
| **quoted values** | `Young` = **`94.3`**, `Old` = **`0.6`**, `SATB` = **`5.1`** (`mean` row) |
| **exact source** | **Table 7**, `Reclamation (%)` group, columns `Young`, `Old`, `SATB` |
| **page** | PDF page 13 |
| **unit** | **percentage of objects reclaimed**, not bytes — Table 7 caption: *"percentage of reclamation due to young RC objects, old RC objects, SATB"*; §5.3: *"the percentage of objects reclaimed via the implicitly dead RC optimization (Young), mature RC (Old), and by the SATB trace"* |
| **workload set** | all 17 DaCapo Chopin benchmarks |
| **heap factor** | **2×** — §5.3, page 13: *"At this 2× heap size, the vast majority of objects are reclaimed via the implicitly dead optimization"* |
| **baseline** | none — this is an internal decomposition of LXR, not a comparison |
| **agreement** | paths A, B, C identical; re-read from the rendered page (path D) |

The `mean` row sums to exactly 100.0, as a split should.

### **Do not use the geomean row as a split**

| statistic | Young | Old | SATB | sums to |
|---|---|---|---|---|
| **mean** | **94.3** | **0.6** | **5.1** | **100.0** |
| geomean | 92.9 | 0.1 | 0.0 | 93.0 |
| min | 42.9 | 0.0 | 0.0 | — |
| max | 100.0 | 2.6 | 54.5 | — |

The geomean `SATB` is `0.0` because several benchmarks reclaim nothing via SATB and a geometric mean
over a set containing zero collapses. The geomean row **does not sum to 100 and is not a split** —
use the `mean` row.

### The distribution matters more than the mean here

The mean hides a bimodal population. Sixteen of seventeen benchmarks reclaim ≥93% via Young RC, but
**batik is a different regime entirely** — 42.9% Young / 2.6% Old / **54.5% SATB**, i.e. the SATB
trace does the majority of the work. Three benchmarks (`biojava`, `h2o`, `jython`) reclaim **100.0%**
via Young RC and never use the other two mechanisms at all.

So the paper supports "Young RC dominates on most workloads" but **not** "Young RC always dominates".
A port that only implements the Young path would reproduce 16 of 17 benchmarks and fail batik badly.
Full per-benchmark data is in §8.

### A second, differently-denominated split — do not conflate them

§5.1 (page 11) quotes a *different* set of percentages that look like they contradict the above:

> *"Mature object RC reclaims 60% of mature objects for cassandra, 48% for h2, 40% for lusearch, and
> 71% for tomcat. The SATB trace reclaims the other mature objects."*

These are percentages of **mature objects only**, whereas Table 7's `Old` column is a percentage of
**all** reclaimed objects. They are derived from the same Table 7 columns as `Old / (Old + SATB)` —
verified arithmetically:

| benchmark | Table 7 `Old` | Table 7 `SATB` | `Old/(Old+SATB)` | §5.1 states |
|---|---|---|---|---|
| cassandra | 0.9 | 0.6 | 60.0% | 60% |
| h2 | 1.9 | 2.1 | 47.5% | 48% |
| lusearch | 0.2 | 0.3 | 40.0% | 40% |
| tomcat | 0.5 | 0.2 | 71.4% | 71% |

All four reconcile. So §5.1 and Table 7 are consistent, they are the same 2× heap data, and the only
hazard is the denominator. **Quoting "60% of reclamation is mature RC" would be wrong by two orders
of magnitude** — the correct statement is "mature RC accounts for 0.9% of all reclaimed objects on
cassandra, which is 60% of the *mature* objects reclaimed".

## 7. Target 4 — write barrier overhead

### The headline

> **1.6% — and it is the *geometric* mean, not the arithmetic mean**

| | |
|---|---|
| **quoted value** | **`1.6%`** (Table 7 `o/h` geomean = **`1.016`**) |
| **exact source** | **Figure 3 caption** (page 8) and **Table 7** `o/h` column, `geomean` row (page 13) |
| **page** | 8 (caption), 9 (§3.4 prose), 13 (table + §5.3 prose) |
| **workload set** | all 17 DaCapo Chopin benchmarks |
| **heap factor** | 2× (Table 7) |
| **baseline** | **no write barrier at all, on full-heap Immix — *not* G1.** §5.3: *"measured relative to no write barrier using full heap Immix"* |
| **agreement** | paths A, B, C identical; re-read from the rendered page (path D) |

### Why the mean-versus-geomean distinction is not pedantry

| statistic | `o/h` | as a percentage |
|---|---|---|
| **geomean** | **1.016** | **+1.6%** ← the headline |
| mean | 1.017 | +1.7% |
| min | 0.968 | −3.2% |
| max | 1.046 | +4.6% |

§5.3 (page 13) says *"On average the field barrier adds 1.6% overhead"*, which reads as the arithmetic
mean but the arithmetic mean is 1.017 (1.7%). §3.4 (page 9) resolves it explicitly:

> *"The **geometric mean** overhead of this write barrier compared to no write barrier on Immix is
> 1.6%, with a worst case for h2o at 4.6% (Table 7)."*

So **1.6% is the geomean**; the arithmetic mean is 1.7%. Quote 1.6% with the word "geometric".

### Three qualifications P9 will need

1. **The baseline is a barrier-free Immix, not G1.** This number says what LXR's barrier costs against
   *no barrier*. It is not comparable to a .NET write-barrier cost measured against the existing
   CoreCLR barrier, which is not free.
2. **It is the *field* write barrier only.** Figure 3 is the `putfield` fast path; the caption and both
   prose statements scope the number to that barrier.
3. **The range crosses 1.0.** Four benchmarks measure *below* 1.0 (`zxing` 0.968, `graphchi` 0.977,
   `cassandra` 0.991, `avrora` 0.997) — i.e. faster with the barrier than without, which is
   measurement noise or layout effects rather than a real speedup. That sets the noise floor: **an
   effect smaller than about ±3% is not distinguishable in this data.**

Small wording note: §5.3 describes the range as *"from no measurable overhead for avrora … to 4.6%
for h2o"*, but avrora (0.997) is not the minimum — `zxing` at 0.968 is. Immaterial to the headline.

## 9. What the paper does **not** state

Listed explicitly, because the step asks for targets the paper may not contain. Nothing in this
section was inferred or interpolated — these are absences.

1. **No .NET, CoreCLR or C# data of any kind.** The paper is OpenJDK-only. There is no basis in it for
   any .NET-relative threshold.
2. **No p50/p95 pause comparison against G1 — at any heap size.** Table 7 is LXR-only. Table 1 is the
   only comparative pause data and it has no p95, covers one benchmark, and uses a 1.3× heap. So "LXR
   pauses are N% shorter than G1's at p95" **cannot be sourced from this paper**.
3. **No single headline reclamation split.** The split is reported per benchmark with `mean`/`geomean`
   summary rows; the mean is the only row that is a valid split (§6).
4. **No pause distribution for Shenandoah or ZGC at a 2× heap.** §5.2 notes Shenandoah's extra pauses

5. **No barrier overhead versus any production collector's barrier.** The only barrier baseline is

6. **No per-benchmark confidence intervals in Table 6 or Table 7.** §5.2 gives only the aggregate
   statement quoted above; Table 4 is the sole table carrying explicit CIs.
7. **No 90th-percentile latency data**, despite the prose claiming it — see §10.
8. **No allocation-rate or pause target expressed in absolute terms for a non-Java runtime.** Every
   absolute millisecond figure is conditioned on Zen 3 + OpenJDK 11 + DaCapo Chopin.

## 10. Errata found in the paper

Both reproduce identically in the LaTeX-derived ar5iv rendering **and in the rendered page image**,
which rules out PDF-extraction error. **These are errors in the paper.**

### 10.1 Table 7 `!Lazy%` — the summary rows are wrong: `min` exceeds `max`

Table 7 states **`min` = 22** and **`max` = 2** for the `!Lazy%` column. The 17 per-benchmark values
are `0` for fourteen benchmarks, `1` (avrora), `5` (lusearch) and `22` (xalan) — so the true minimum
is **0** and the true maximum is **22**.

Note the printed `max` of `2` is not the true minimum either — it equals the column's own `mean`. A
simple `min`/`max` swap is therefore **ruled out**: a swap would have printed `max` = `0`. Nor is the
block uniformly shifted by one row, because the `mean` cell is itself correct (see the third check
below). The cause is not determinable from the PDF, so only the observation is recorded: **the
printed `min` exceeds the printed `max`, which is impossible, and the true range is 0–22.**

Three independent checks confirm the table is wrong:

- The observed range over the 17 published values is 0–22.
- §5.3 (page 13) states: *"For most benchmarks, it never happens, but in the worst case, xalan, it
  reaches 22%"* — i.e. the prose says 22 is the **maximum**.
- The table's own `mean` of `2` matches the arithmetic mean of the 17 values (1.65 → 2), so the
  per-benchmark column and the `mean` row are mutually consistent; only `min`/`max` are not.

Does not affect any of the four targets — `!Lazy%` is not one of them — but it is recorded because it
calibrates how much trust the summary rows deserve. Every summary statistic quoted in §4–§7 was
checked against its per-benchmark column; **the `!Lazy%` row is the only one that failed.**

### 10.2 A 90th-percentile column is described but not present

§4 (page 10) says *"We present DaCapo's metered 50, 90, 99, 99.9 and 99.99 percentile tail latencies
in tabular form"*, and §5.1 (page 11) says *"Table 4 shows the median, 90, 99, 99.9 and 99.99
percentile request latencies"*. **Table 4's column headers are `50 · 99 · 99.9 · 99.99`** — there is
no 90th-percentile column, in the PDF text, the ar5iv rendering, or the rendered page image. The p90
data is simply not in the paper. Worth knowing before anyone goes looking for it.

## 11. How P9 should use these targets

1. **Treat them as a reference point, not a contract.** Per the roadmap, a mechanism whose parity
   oracle is `lxr-head` is being compared against an implementation that has moved on from this 2022
   artifact. These numbers describe the artifact, not the current reference.
2. **Never state a target without its heap factor.** LXR beats G1 at 1.3× and 2× and *loses* at 6×
   (§4). A bare "LXR is 4% faster than G1" is false at a generous heap.
3. **Do not convert an OpenJDK/G1 ratio into a .NET/CoreCLR threshold.** Different runtime, different
   baseline collector, different workload set, and — per §3 — a configuration with class unloading,
   compressed pointers and weak references disabled in all systems.
4. **Prefer distributions to means.** The mean p95 of 7.5 ms is not a per-benchmark bound (max 24.5
   ms), and the 94.3% Young-RC share is not universal (batik: 42.9%).
5. **Respect the noise floor.** Barrier `o/h` values below 1.0 put the resolution of these
   measurements at roughly ±3%; differences smaller than that are not meaningful.
6. **Do not write a "beat G1 on pause time" target.** It contradicts the paper's only comparative pause
   data, where LXR's pauses are *longer* than G1's at every percentile (§5). The paper's claim is about
   application-visible latency, not pause duration. The supported latency target with a G1 baseline is
   Table 5's 99.99% latency ratio — and unlike throughput, it holds at every heap size.
7. **If a .NET acceptance threshold is needed, it has to be derived from a .NET baseline measured in
   this project** — P0.1's reference numbers measured the *implementation*, and this document records
   the *paper*. Neither is a .NET measurement, and no number in either can become one by arithmetic.
