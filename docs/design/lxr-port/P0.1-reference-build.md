# P0.1 — Reference build record

How the two LXR parity oracles were pinned and built, exactly enough to reproduce. Anything that
could not be built or run is stated plainly in §7.

---

## 1. What was pinned

**An oracle is a *build pair* — a `(mmtk-openjdk, mmtk-core)` tuple that actually shipped — not a
tag or branch name.** A tag names one repository; LXR only exists as the two together. The two
oracles are therefore the pairs below, each being the configuration someone actually built,
ran and measured.

| | PLDI oracle | HEAD oracle |
|---|---|---|
| named by the roadmap as | tag `lxr-pldi-2022` | branch `lxr` |
| **mmtk-openjdk (binding)** | **`abbdd1d`** (tag `lxr-pldi-2022`), 2022-04-12 | **`0682434`**, 2026-04-22 |
| **mmtk-core (as the binding pins it)** | **`df8d30a3`** — *rc_bits* | **`304ce69d`** |
| mmtk-core revision the roadmap names | `4d4e516c` — *class pointer validity checks* | `9625c174` — *Add an option to disable RC decs* |
| OpenJDK | `f817e9d0`, branch `jdk-11.0.11+6-mmtk` of `mmtk/openjdk.git` | `7caf8f7d`, same repo |
| rust toolchain | `nightly-2021-10-29` (from `mmtk/rust-toolchain`) | `1.92.0` (from `mmtk/rust-toolchain`) |
| LXR selection | **compile-time**, `--features lxr,immix` | **runtime**, `MMTK_PLAN=LXR` |
| build levels | release, fastdebug | release, fastdebug |

The pin is read from the binding's own `mmtk/Cargo.toml` and confirmed in its `Cargo.lock`:

```toml
# mmtk-openjdk abbdd1d
mmtk = { git = "https://github.com/wenyuzhao/mmtk-core.git", rev = "df8d30a39237a5bf5a8e27ca5a6f46acc6080c94" }
# mmtk-openjdk 0682434
mmtk = { git = "https://github.com/wenyuzhao/mmtk-core.git", rev = "304ce69d43aae87de501111fceb8cbd33173a03a" }
```

`lxr-x/simplified` is excluded by the parity contract and was never checked out.

## 2. Revision skew: neither named revision is what its binding builds

| | binding | mmtk-core the binding pins (**the oracle**) | mmtk-core the roadmap names | relationship |
|---|---|---|---|---|
| PLDI | `abbdd1d` | **`df8d30a3`** | `4d4e516c` | the named revision is 9 commits **behind** the oracle |
| HEAD | `0682434` | **`304ce69d`** | `9625c174` | the named revision is 9 commits **ahead** of the oracle |

The situation is symmetric, and in both directions the gap is exactly nine commits. Every one of
those eighteen commits is classified individually in `P0.1-mechanism-diff.md` §18.

> **Correction — and a trap worth naming.** Two earlier drafts of this record got the PLDI direction
> wrong, because both reasoned from the commit *date*. `df8d30a3` carries author date **2022-03-14**,
> which is *earlier* than `4d4e516c`'s 2022-04-08, so it looks like the older commit. It is not:
> the commits between them are dated 2022-04-09/10, i.e. `df8d30a3` was **rebased or amended** and
> its author date is stale. The topology is unambiguous and is what counts:
>
> ```console
> $ git merge-base --is-ancestor 4d4e516c df8d30a3 && echo "4d4e516c is the ancestor"
> 4d4e516c is the ancestor
> $ git rev-list --count 4d4e516c..df8d30a3   # 9
> $ git rev-list --count df8d30a3..4d4e516c   # 0
> ```
>
> **Never order MMTk revisions by date; ask `git merge-base`.**

### 2.1 Both configurations were built — but only one is an oracle

Two configurations exist per revision, and they are not interchangeable:

| configuration | how built | status |
|---|---|---|
| **shipped pair** — binding + its own pinned `rev` | pristine `Cargo.toml` + `Cargo.lock`, cargo fetches the pinned git rev | **the oracle.** All parity claims and all benchmark rows attribute here. |
| **path-override** — binding + the roadmap-named revision | `mmtk = { path = ... }`, the override the manifest itself documents | **evidence about buildability only.** A configuration that never shipped; never a parity baseline. |

The override experiment was run deliberately, for both revisions, because "does this binding compile
against that revision?" is a real question worth a recorded answer. The answer, for both:

**Yes — both bindings build *and run* cleanly against their roadmap-named revision.** Not merely
`cargo check`; full `make` plus DaCapo execution. That is a positive, citable buildability result,
and it is reported separately from the oracle numbers in `P0.1-benchmarks.md` §9 — never in the same
table, always labelled as a configuration that never shipped.

**Do not delete `Cargo.lock` for the PLDI build.** Re-resolution pulls `log v0.4.28`, which requires
rustc ≥ 1.61; the required toolchain is 1.58.0-nightly. Restore with `git checkout -- mmtk/Cargo.lock`.

## 3. Host environment

Decided up front (see the P0.1 plan): **build on WSL2/Ubuntu, not on Windows.** Both revisions'
only build path is `CONF=linux-x86_64-normal-server-*`; `CompileThirdPartyHeap.gmk` hardcodes
`libmmtk_openjdk.so`, `-Wl,-rpath,$$ORIGIN` and GCC-style flags. There is no Windows
third-party-heap integration to fall back on, and the head CI runs `ubuntu-22.04`.

| | |
|---|---|
| host | Windows 11 build 26200, 16 logical CPUs, 64 GB RAM |
| guest | WSL2, Ubuntu 22.04 (installed for this step — the machine had **no** WSL distribution) |
| gcc | 11.x (Ubuntu 22.04 default) |
| boot JDK | OpenJDK 11 from the distro |
| rust | rustup, toolchains `nightly-2021-10-29` and `1.92.0` |
| libclang | `/usr/lib/llvm-14/lib` — **required**, `bindgen` via `pfm-sys` |

apt prerequisites: `build-essential libx11-dev libxext-dev libxrender-dev libxtst-dev libxt-dev
libcups2-dev libasound2-dev libxrandr-dev zip unzip python3-pip autoconf`.

GCC 11 against 2021-era JDK 11 source was **not** a problem; `--disable-warnings-as-errors` sufficed.
The planned Ubuntu 20.04 fallback was not needed.

### Reference checkout integrity

The shared reference checkout at `C:\github\lxr-reference` was **never modified**. All four repos
were obtained by `git clone` *from* it into the WSL ext4 filesystem at `/root/lxr/`, which is both
faster than building over the `/mnt/c` 9p bridge and a stronger guarantee than worktrees. Verified
before and after: `git status --porcelain` empty, `mmtk-core` and `mmtk-openjdk` both on branch
`lxr` at their original HEADs.

> Note: running `git status` on the Windows checkout **from inside WSL** reports spurious
> modifications, because `core.autocrlf` is interpreted differently across the boundary. The Windows
> view is authoritative. Verify from PowerShell, not from WSL.

## 5. Build recipe

### 5.1 The `--features` doubling bug — read this before building PLDI

PLDI's `mmtk-openjdk/openjdk/CompileThirdPartyHeap.gmk`:

```make
ifdef MMTK_PLAN
  GC_FEATURES=--features $(MMTK_PLAN)     # line 6  -- already includes the flag
endif
...
CARGO_BUILD_FEATURES = --features $(GC_FEATURES)   # line 46 -- adds it AGAIN
```

Setting `MMTK_PLAN=lxr` therefore emits

```
cargo build --release --features --features lxr
```

Cargo consumes `--features` as the value of the first `--features` and **silently ignores `lxr`**.
The build succeeds, links, and runs — as **NoGC**. It then panics with *"GC triggered in nogc"* the
moment the heap fills.

**The correct knob at the PLDI revision is `GC_FEATURES`, given a bare feature list**, with
`MMTK_PLAN` unset.

This bug is present verbatim at HEAD too (same two lines), but is harmless there because HEAD selects
the plan at runtime and does not need `MMTK_PLAN` as a cargo feature.

### 5.2 `immix` is required alongside `lxr`

The binding's `mmtk/src/lib.rs` (lines 137–149) forces the `MMTK_PLAN` builder option from its **own**
cargo features — it has cases for `nogc`, `semispace`, `gencopy`, `marksweep`, `markcompact`,
`pageprotect`, `immix`, `genimmix` — and **no case for `lxr`**. The binding's `lxr` feature only
forwards to `mmtk/lxr`, which reconfigures the *Immix* plan. With no binding feature selecting a
plan, the default `PlanSelector` is `NoGC` (`mmtk-core/src/util/options.rs:169`).

So `lxr` alone builds LXR's *code* but never selects it. The correct invocation is:

```
GC_FEATURES=lxr,immix
```

`lxr` turns on the LXR mechanisms inside Immix; `immix` makes the binding ask for the Immix plan.

### 5.3 PLDI

```bash
export PATH=/root/.cargo/bin:$PATH
export LIBCLANG_PATH=/usr/lib/llvm-14/lib
unset MMTK_PLAN                                   # critical, see 5.1
cd /root/lxr/pldi/mmtk-openjdk/repos/openjdk
rustup override set nightly-2021-10-29

sh configure --disable-warnings-as-errors --with-debug-level=release
make CONF=linux-x86_64-normal-server-release \
     THIRD_PARTY_HEAP=/root/lxr/pldi/mmtk-openjdk/openjdk \
     GC_FEATURES=lxr,immix

sh configure --disable-warnings-as-errors --with-debug-level=fastdebug
make CONF=linux-x86_64-normal-server-fastdebug \
     THIRD_PARTY_HEAP=/root/lxr/pldi/mmtk-openjdk/openjdk \
     GC_FEATURES=lxr,immix
```

**Verify the cargo line**, do not trust the exit code. The make output must contain exactly:

```
cargo build --release --features lxr,immix
```

If it says `--features --features lxr`, §5.1 applies and you have built NoGC.

## 6. Runtime verification — what was actually checked

> **Correction.** An earlier draft of this record claimed the PLDI release build was
> "runtime-verified" by a HelloWorld run reporting `live=1801`. **That claim was invalid** and has
> been removed: the build under test at that point was the accidental NoGC build of §5.1, and a
> trivial HelloWorld in a 128 MB heap passes perfectly well under NoGC. It proved nothing about LXR.
> This section now records only checks that discriminate.

### 6.1 HEAD — plan selection is real

- `MMTK_PLAN=LXR` + an allocation loop that allocates **far more than the heap size** completes
  successfully, so the collector genuinely collects rather than merely bump-allocating.
- **Negative control:** `MMTK_PLAN=NoSuchPlan` aborts the JVM (exit 134). The environment variable is
  therefore genuinely consumed and validated, so a passing `MMTK_PLAN=LXR` run is meaningful.

### 6.2 PLDI — LXR configuration confirmed from the collector's own banner

Running with `RUST_LOG=info` makes the PLDI build print an *"Immix Args"* banner at startup. The
build under test reports:

```
 * barrier: "FieldLoggingBarrier"
 * ix_ref_count: true
 * ix_concurrent_marking: true
 * ix_lock_free_block_allocation: true
 * lxr_lazy_decrements: true
 * lxr_nursery_evacuation: true
 * lxr_mature_evacuation: true
 * ix_block_only: false
 * ix_defrag: false
 * log_block_size: 15      (32 KB blocks)
 * log_line_size: 8        (256 B lines)
 * log_bytes_per_rc_lock_bit: 9
 * concurrent_marking_threshold: 90
 * max_mature_defrag_percent: 15
```

This is **full LXR** — coalescing RC, concurrent marking, lazy decrements, and both nursery and
mature evacuation, driven by the field-logging barrier. It is the strongest available evidence that
the PLDI build is correctly configured, and it is a runtime observation rather than an inference from
the build command.

### 6.3 Both — the shipped pairs are what was measured

Every build links `libmmtk_openjdk.so` into `build/linux-x86_64-normal-server-*/jdk/lib/server/`
and runs `java -XX:+UseThirdPartyHeap -version` successfully.

All four **shipped-pair** configurations were rebuilt from pristine `Cargo.toml` + `Cargo.lock`
(§2.1) and `Cargo.lock` re-read afterwards to confirm the resolved revision:

| configuration | `Cargo.lock` says | expected |
|---|---|---|
| PLDI release / fastdebug | `mmtk … #df8d30a3…` | `df8d30a3` ✓ |
| HEAD release / fastdebug | `mmtk … #304ce69d…` | `304ce69d` ✓ |

`[verified]` The four path-override `.so` files were preserved at `/root/lxr/so-backup/` rather than
overwritten, so either variant can be swapped back in for comparison.

## 7. Deviations, failures and things that cost time

### 7.1 The PLDI oracle fails the step's correctness criterion

All four configurations of both shipped pairs were produced successfully, and all four **run**. But
the PLDI oracle is not reliable, and that is the single most consequential outcome of this step.

P0.1's correctness criterion is *"both builds run the reference benchmark set without assertion
failures."* **HEAD meets it. PLDI does not.** Stated plainly rather than softened:

| | benchmark set | assertion failures |
|---|---|---|
| HEAD `(0682434, 304ce69d)` | **8/8** at `-n 1` and `-n 5`, both heaps, 3 invocations each | **none**, in any of seven log directories |
| PLDI `(abbdd1d, df8d30a3)` | **5/8** at `-n 1` @2000 MB; 2/8 at `-n 5` | **yes** — `zero rc count` in the write barrier |

**The assertion.** In a fastdebug build PLDI trips, in `FieldLoggingBarrier::slow()`:

```rust
// src/plan/barriers.rs:315 — byte-identical at 4d4e516c and df8d30a3
#[cfg(any(feature = "sanity", debug_assertions))]
assert!(old.is_null() || rc::count(old) != 0, "zero rc count {:?}", old);
```

```text
thread '<unnamed>' panicked at 'zero rc count 0x2001ef08000', .../df8d30a/src/plan/barriers.rs:315:9
```

A field being overwritten still refers to an object whose reference count has already reached zero.

**Signature.** In release builds the `cfg` compiles that check out and the same corrupt state instead
faults with `SIGSEGV`, alternating between `FieldLoggingBarrier::write_barrier` and
`ImmixConcurrentTraceObjects::do_work` — the two ends of the SATB handshake. Non-deterministic for a
fixed configuration; several worker threads trip the assertion simultaneously on different objects.
**One defect, two faces:** fastdebug catches the RC-invariant violation, release lets it run on.

> **Correction.** Earlier drafts of this record and of `P0.1-benchmarks.md` stated that *"no assertion
> fired on either revision"* and that the failures were "hard SIGSEGVs below the level the assertions
> check". **That was wrong.** It came from scanning one of seven log directories. The full scan found
> the panic above. The corrected statement is the opposite of the original: the assertion is exactly
> what fires, and it names the defect.

**Two things that cost the most time, recorded so they are not repeated:**

1. **Heap size.** The first runs used a multiple of the MarkCompact minheaps from the binding's own
   `common.sh` (antlr 5 MB, fop 13, …). *Everything* crashed, which nearly produced the wrong
   conclusion that the build was broken. The reference's own `ci-test-normal.sh` uses
   `-Xms500M -Xmx500M` for every benchmark and notes those options *"are necessary for now to ensure
   the benchmarks work"*. At 500 MB+, PLDI passes. The minheap table describes MarkCompact's needs,
   not LXR's.
2. **Iteration count.** At `-n 5` PLDI crashes on 6 of 8, including antlr, which passes at `-n 1`.
   Controlled experiment: PLDI antlr at a fixed 2000 MB survives `-n 1,2,3,4` and crashes at `-n 5`
   after completing four warm-up iterations. HEAD is unaffected throughout.

**Ruled out, each by experiment rather than by reasoning:**

| hypothesis | test | result |
|---|---|---|
| wrong plan (the NoGC build of §5.1) | `RUST_LOG=info` banner | ruled out — full LXR active (§6.2) |
| revision skew | built the **shipped pair** against the binding's own pin `df8d30a3` | ruled out — identical failure set, benchmark for benchmark |
| the skew range contains the fix | classified all 9 commits; `014368ef Fix stw LXR` targets the *stop-the-world* variants and is inert under `--features lxr` | ruled out — and confirmed empirically by the row above |
| compressed oops | read the binding | ruled out — it forces `UseCompressedOops=false` itself and asserts on it |
| a hang | `RUST_LOG=info` + timing | ruled out — a crash; the ~155 s wall time was WSL core-dump capture, eliminated by `echo core > /proc/sys/kernel/core_pattern` |
| below the level assertions check | scanned **all seven** log directories | **refuted** — an assertion does fire; see above |

**Not all three failures are LXR's fault.** PLDI's own `ci-test-normal.sh` comments out `lusearch`
(*"validation failed"*) and `xalan` (*"mmtk-core gets stuck in slowdebug build"*) for **stock** plans.
`eclipse` is in the actively-tested list, so its failure under LXR is a genuine LXR-specific defect.
Reduced to LXR-specific single-iteration failures, the count is **one benchmark: eclipse**. That
caveat applies to the *pass count*; it does not apply to the assertion, which is an invariant
violation in LXR's own barrier regardless of which benchmark provokes it.

**What this means for P0.3.** PLDI remains the clearest *statement* of the algorithm and is still the
recommended oracle for several mechanisms. It is not a runnable specification: a .NET port cannot be
differentially tested against it on any sustained workload. See `P0.1-mechanism-diff.md` §3.4 and §15.

### 7.2 The reference's own CI never tests LXR

- PLDI `ci-test-normal.sh` exercises SemiSpace, Immix and GenImmix — **not LXR**.
- HEAD `.github/configs/normal-heap.yml` lists nine plans — **none of them LXR**.

Neither revision's LXR path is protected by the reference's own CI. This calibrates how much the
reference can be trusted as an oracle and is carried into the mechanism diff.

### 7.3 Operational notes worth keeping

- **`ulimit -c 0` is not enough.** Under WSL the kernel `core_pattern` is a capture pipe
  (`/wsl-capture-crash`), which runs regardless and turns every SIGSEGV into a ~150 s stall — long
  enough to look like a hang. Set `echo core > /proc/sys/kernel/core_pattern` as well; crash
  turnaround drops from ~155 s to 2–6 s.
- **`timeout -k <n>`.** Plain `timeout` only sends SIGTERM, which this JVM ignores.
- PowerShell → `wsl.exe`: write scripts to files and run `bash <path>`, after
  `sed -i 's/\r$//'`. Inline `bash -c` mangles `$1`, `$f` and quoting. Use `--cd /root` or the
  Windows cwd leaks in and breaks git.
- Do **not** `pkill -f 'Bench -n'` from a `bash -c` whose own command line contains that string — it
  matches, and kills its own parent shell.

## 8. Scripts

`scripts/` in this directory holds the scripts actually used:

| script | purpose |
|---|---|
| `clone.sh` | clone all four repos from the Windows reference checkout at the pinned commits |
| `oracle-check.sh` | `cargo check` each binding against its roadmap-named revision via path override (§2.1) |
| `fetch-openjdk.sh` | fetch the two OpenJDK trees at `f817e9d0` / `7caf8f7d` |
| `build-jdk.sh` | configure + build one (revision, debug-level) pair |
| `build-rest.sh` | build the remaining three configurations |
| `build-shipped.sh` | restore pristine `Cargo.toml`/`Cargo.lock` and rebuild all four **shipped-pair** `.so`s, backing up the override ones |
| `sanity.sh` | plan-selection checks including the `MMTK_PLAN=NoSuchPlan` negative control |
| `mk-harness.sh` | build the mutator-observed pause meter (`Hiccup.java`, `Bench.java`) |
| `bench-final.sh` | DaCapo 2006 driver, emits TSV with throughput and pause percentiles |
| `assert-scan.sh` | scan **all** log directories for Rust panics and JVM assertion failures |

Bulk build state (clones, OpenJDK trees, JDK images, DaCapo jars — tens of GB) lives **only** in WSL
at `/root/lxr/` and is deliberately not in version control.
