# P0.1 — Reference benchmark results

Pause and throughput behaviour of the **reference** LXR implementation on both parity oracles, as a
sanity anchor for later .NET comparisons. **No .NET numbers appear in this step.**

> **What is an oracle number.** An oracle is a **shipped build pair** — a binding together with the
> `mmtk-core` revision that binding actually pins (`P0.1-reference-build.md` §1). Every table in
> §4–§8 is a shipped-pair measurement. Numbers from the **path-override** configuration, where a
> binding is repointed at the revision the roadmap names, are quarantined in **§9** and are never
> mixed into an oracle table. An override build is evidence about buildability, not a parity
> baseline.

| | binding | mmtk-core (the oracle) |
|---|---|---|
| **PLDI** | `abbdd1d` | `df8d30a3` |
| **HEAD** | `0682434` | `304ce69d` |

The headline result is stated up front because it constrains everything downstream:

> **HEAD runs the full DaCapo 2006 set cleanly. PLDI does not.**
> PLDI completes single-iteration runs of 5 of 8 benchmarks but crashes with SIGSEGV under sustained
> execution. It is usable as a *short-observation* oracle only.
>
> This holds on the **shipped** PLDI pair, not merely on the roadmap-named revision — so it is not an
> artefact of revision skew. See §9.2.

### Caveats on the numbers

- The host is a WSL2 VM on a desktop, not a quiesced benchmarking machine. Treat these as **order of
  magnitude and shape**, not as publishable measurements. They exist to anchor "is a later .NET
  number in the right ballpark", not to reproduce the paper.
- DaCapo 2006 `msec` is one iteration's wall time, not a steady-state average.
- The two revisions run on **different OpenJDK builds** (`f817e9d0` vs `7caf8f7d`, four years apart)
  and different rustc. A PLDI-vs-HEAD throughput difference is therefore *not* attributable to the
  collector alone. This is unavoidable — neither binding builds against the other's JDK.

## 2. Why the heap is 500 MB and not a multiple of the minheap

Initially the heaps were derived as a multiple of the MarkCompact minheaps recorded in the PLDI
binding's own `common.sh` (antlr 5 MB, fop 13, luindex 6, lusearch 8, pmd 24, hsqldb 117, eclipse 23,
xalan 21). **At those sizes PLDI crashed on every benchmark**, which nearly produced the wrong
conclusion that the PLDI build was unusable.

The reference's own `ci-test-normal.sh` runs *every* DaCapo 2006 benchmark at
`-XX:MetaspaceSize=100M -Xms500M -Xmx500M`, with the comment:

> *"the command line options are necessary for now to ensure the benchmarks work"*

At 500 MB, PLDI passes. The minheap table describes what **MarkCompact** needs, not what LXR needs;
LXR at this revision requires far more headroom. That is itself a finding — recorded in §6.

## 3. How pauses were measured

There is **no symmetric GC log** across the two revisions. PLDI has `HARNESS_PRETTY_PRINT`,
`LOG_PER_GC_STATE` and `LOG_STAGES` behind a `log_gc` feature; HEAD has none of them. Neither
OpenJDK fork exposes a Java-visible `harness_begin`/`harness_end` entry point. Parsing GC logs would
therefore have compared two different things.

Instead pauses are measured **from the mutator's point of view**, jHiccup-style: a daemon thread
sleeps on a 1 ms cadence and records how far each wake-up overshoots its intended time. Any excess is
time the mutator was not permitted to run. For a collector with stop-the-world phases the tail of
that distribution is dominated by GC pauses.

This is deliberately the *pessimistic* and *portable* measure: it captures everything the application
actually feels — STW pauses, safepoint bias, and scheduler noise — and it will work identically
against a future .NET port, which is the point. It **over**-reports at the median (~0.12 ms of pure
timer jitter on this host, visible as the p50 floor in every row below), so **read the tail, not the
median**.

Sources: `scripts/mk-harness.sh` (`Hiccup.java`, `Bench.java`).

> ### Correction — an assertion *does* fire, and it names the defect
>
> Earlier drafts of this record stated that "no assertion failed in any run, on either revision."
> **That was wrong.** It was produced by scanning only one of the seven log directories. A
> comprehensive scan of every log directory, both revisions, every pass, gives:
>
> | | logs containing a Rust panic |
> |---|---|
> | HEAD | **0** |
> | PLDI | **2** (shipped fastdebug `xalan`; override fastdebug `eclipse`) |
>
> The assertion is worth far more than the crash it replaces, because it names the broken invariant:
>
> ```text
> thread '<unnamed>' panicked at 'zero rc count 0x2001ef08000',
>     .../mmtk-core-.../df8d30a/src/plan/barriers.rs:315:9
> ```
>
> Site — `FieldLoggingBarrier::slow()`, i.e. the **write barrier's slow path**: `[verified]`
>
> ```rust
> #[cfg(any(feature = "sanity", debug_assertions))]
> assert!(old.is_null() || rc::count(old) != 0, "zero rc count {:?}", old);
> ```
>
> The barrier, overwriting a field, finds that the **old referent already has reference count zero** —
> an object that should have been unreachable is still installed in a live field.
>
> This also explains the release-build crashes. The assertion is `#[cfg(debug_assertions)]`, so it is
> compiled **only** into fastdebug. In release the same corrupt state is never checked and simply
> proceeds, surfacing later as `SIGSEGV` — in the barrier itself or in
> `ImmixConcurrentTraceObjects::do_work`. **One defect, two faces**: the fastdebug assertion and the
> release segfault are the same RC-invariant violation, caught at different distances from its origin.
>
> Re-running the three failing benchmarks with `RUST_BACKTRACE=1` shows **several worker threads
> panicking simultaneously** on the same assertion with different object addresses — the violation is
> widespread within a run, not a single unlucky object. All three abort with exit 134.
>
> The assertion site is **byte-identical** at `4d4e516c` and `df8d30a3` (`git diff` over
> `src/plan/barriers.rs` across the skew range is empty), so this is not a revision-skew artefact.

So, against the P0.1 correctness criterion *"both builds run the reference benchmark set without
assertion failures"*:

- **HEAD: met in full.** 8/8 benchmarks, zero assertions, zero crashes, across every pass.
- **PLDI: not met.** It fails 3 of 8 benchmarks, and at least one of those failures is a genuine
  **assertion failure on an RC invariant**, not merely an opaque memory fault.

> **Do not read this as "PLDI has better pauses."** PLDI's worst observed max is 5.5 ms and HEAD's is

### 6.3 Reading

1. **The common case is genuinely low-latency.** On six of eight benchmarks HEAD's p99 mutator stall
   is **well under 1 ms**, and on eclipse — the longest-running benchmark, 55 000+ samples per
   invocation — p99.9 at 2000 MB is **0.90–1.18 ms**. That is the LXR result the paper claims, and it
   reproduces here.
2. **hsqldb is the outlier on HEAD**, p99 ≈ 54–56 ms at both heaps, and PLDI is two orders of
   magnitude better on the same workload. See §8.
3. **lusearch and xalan have a mid-tail** on HEAD, p99 of 3.7–7.4 ms. Both are heavily multi-threaded
   allocation-intensive benchmarks.
4. **luindex@2000M shows a 232–315 ms max** against a p99.9 of ~1 ms — a single very long outlier per
   run, most likely heap growth or a full defrag, not a recurring pause.
4. **Larger heaps flatten the tail** as expected: eclipse p99.9 drops from ~5.5 ms at 500 MB to
   ~0.5 ms at 2000 MB.
5. **PLDI's tails are tighter than HEAD's on every benchmark it completes** — but only over `-n 1`
   runs, which is a fraction of the GC activity. Do not read this as PLDI having better pause
   behaviour.

## 7. The PLDI failure, characterised

### 7.1 Signature

The failure has **two faces, one cause**:

**Fastdebug — a named invariant violation.** `[verified]`

```text
thread '<unnamed>' panicked at 'zero rc count 0x2001ef08000',
    .../df8d30a/src/plan/barriers.rs:315:9
```

```rust
// FieldLoggingBarrier::slow(), the write barrier's slow path
#[cfg(any(feature = "sanity", debug_assertions))]
assert!(old.is_null() || rc::count(old) != 0, "zero rc count {:?}", old);
```

The barrier overwrites a field and finds the **old referent's reference count is already zero**.
Under `RUST_BACKTRACE=1`, several worker threads trip this simultaneously with different addresses,
so the violation is widespread within a run.

**Release — an unchecked segfault.** Two faulting sites, alternating between runs of the *same*
configuration:

```text
C  [libmmtk_openjdk.so+0x139c20]
   <mmtk::plan::barriers::FieldLoggingBarrier<E> as ...::Barrier>::write_barrier

C  [libmmtk_openjdk.so+0x189434]
   <mmtk::util::cm::ImmixConcurrentTraceObjects<VM> as ...::GCWork<VM>>::do_work
```

The assertion is `#[cfg(any(feature = "sanity", debug_assertions))]`, so it exists **only** in
fastdebug. In release the identical corrupt state is never checked and proceeds until it faults —
in the barrier itself, or in the concurrent trace consuming the object. The two faulting sites are
**the two ends of the SATB handshake**, and the non-determinism for a fixed configuration is itself
evidence of a race.

### 7.2 Iteration scaling

Same benchmark, same heap (2000 MB), only `-n` varies:

| `-n` | PLDI antlr | HEAD antlr |
|---|---|---|
| 1 | OK | OK |
| 2 | OK (1 warm-up completed) | — |
| 3 | OK (2 warm-ups completed) | OK |
| 4 | OK (3 warm-ups completed) | — |
| 5 | **CRASH** — after completing 4 warm-ups | OK |

PLDI survives four full iterations of antlr and dies in the fifth. HEAD is unaffected at every point.

**This is a survival-time signature, not a workload signature**, consistent with slowly accumulating
RC-table corruption: the longer the collector runs, the more likely some object's count reaches zero
while a live field still points at it. It is inconsistent with "antlr does something LXR cannot
handle", since antlr does the same thing five times.

The heap-size axis points the same way: at one iteration PLDI passes 5/8 at 2000 MB but only 3/8 at
500 MB. More collection work per unit of application progress ⇒ earlier failure.

### 7.3 What was ruled out, by experiment not by reasoning

| hypothesis | test | outcome |
|---|---|---|
| Not actually running LXR | `RUST_LOG=info` startup banner | **ruled out.** `ix_ref_count`, `ix_concurrent_marking`, `lxr_lazy_decrements`, `lxr_nursery_evacuation`, `lxr_mature_evacuation` all `true`; `barrier: "FieldLoggingBarrier"` |
| **Revision skew** — wrong mmtk-core | **built the shipped pair** (`abbdd1d` + `df8d30a3`) and re-ran the whole matrix | **ruled out.** The shipped pair reproduces the identical pass/fail pattern, benchmark for benchmark. See §9.2. |
| Compressed oops | read the binding | **ruled out** — it sets `UseCompressedOops=false` itself and asserts on it |
| Heap too small | 15 / 50 / 100 / 200 / 500 / 1000 / 2000 MB | **a contributing factor** — 500 MB+ is necessary but not sufficient |
| A hang | `RUST_LOG=info` + timing | **ruled out** — a crash; the 155 s wall time was WSL core-dump capture, removed by resetting `core_pattern` |
| ~~Assertion / invariant violation~~ | fastdebug builds | **confirmed, not ruled out** — see the correction in §4.1 |

> The last row was previously recorded as "ruled out — no assertion fired". That was an artefact of
> scanning one log directory instead of all seven. The assertion **does** fire, and it is the single
> most informative piece of evidence in this document.

### 7.4 Two of the three failures are already known-broken in the reference

PLDI's own `ci-test-normal.sh` **comments out** several benchmarks with reasons:

```text
#... lusearch - validation failed
#... xalan    - mmtk-core gets stuck in slowdebug build
#... bloat    - does not work for stock build
#... jython   - does not work for stock build
```

So **lusearch and xalan are on the reference's own broken list at this revision, for stock plans**
— they are not LXR regressions. **eclipse is not**: it is in the actively-tested CI list for
SemiSpace, Immix and GenImmix, so its failure under LXR is a genuine LXR-specific defect.

Reduced honestly, the LXR-specific single-iteration failure at PLDI is **one benchmark: eclipse**.
The multi-iteration instability, however, affects nearly everything — and the `zero rc count`
assertion is not excused by any known-broken list.

### 7.5 Neither revision's LXR path is covered by the reference's own CI

- PLDI `ci-test-normal.sh` tests SemiSpace, Immix, GenImmix. Not LXR.
- HEAD `.github/configs/normal-heap.yml` lists nine plans. None is LXR.

Nobody upstream is running these tests. The instability found here was never going to be caught by
the reference's CI, and "the reference works" is not something CI attests to for LXR on either
revision.

## 8. Consequences for P0.3

1. **HEAD is the only oracle that can be *observed* across the full benchmark set.** PLDI can be
   observed for short runs of 5 benchmarks and read for everything else.
2. **The `zero rc count` assertion is a mechanism-level finding, not just a bug report.** It says the
   PLDI *implementation* violates the coalescing-RC invariant that the barrier itself asserts:
   a field's old referent has RC 0. This directly weakens any recommendation to follow PLDI for **RC
   semantics** or for the **RC/barrier coupled set**, because the reference implementation of exactly
   that mechanism is demonstrably not self-consistent under load. It does **not** invalidate the
   paper's *design*; it does mean PLDI's code cannot be treated as an executable specification of it.
   Carried into `P0.1-mechanism-diff.md` §3 and §4.
3. **Do not treat PLDI's numbers as the paper's numbers.** The paper's evaluation used a quiesced
   machine, `running-ng`, many invocations, and heap sizes expressed as multiples of a measured
   minheap. This step reproduces the *shape* — sub-millisecond p99 on most benchmarks — not the
   magnitudes.
4. **A .NET port should target HEAD's behaviour as the pass/fail bar** and use PLDI only where a
   mechanism's *definition* is clearer there.
5. **hsqldb tail latency is the single most interesting number here.** On the one non-trivial
   benchmark both revisions complete at `-n 5` @2000 MB, PLDI shows p99 of **0.34–0.40 ms** and HEAD
   shows **54–56 ms** — two orders of magnitude apart, like for like. That is a candidate latency
   regression between the paper-contemporaneous revision and head, and P0.3 should treat it as an
   open question rather than a settled result, since a single benchmark on a noisy host is thin
   evidence. If it is real, it matters: pause tail is LXR's entire value proposition.

## 9. The path-override configuration — quarantined

**Nothing in this section is an oracle number.** These are builds where a binding was repointed, via
the `path` override its own manifest documents, at the `mmtk-core` revision the roadmap *names*
rather than the one the binding *pins*:

| | binding | mmtk-core | shipped? |
|---|---|---|---|
| PLDI override | `abbdd1d` | `4d4e516c` | **no — this pair never existed** |
| HEAD override | `0682434` | `9625c174` | **no — this pair never existed** |

They are recorded because "does this binding build against that revision?" is a real question that
deserves a recorded answer, and because the answer turned out to matter.

### 9.1 Buildability result — positive for both

**Both bindings build, link and run against their roadmap-named revision.** Not merely `cargo check`:
a full `make` of release *and* fastdebug, followed by DaCapo execution.

| override configuration | builds | runs DaCapo |
|---|---|---|
| PLDI `abbdd1d` + `4d4e516c` | yes, release + fastdebug | 5/8 at `-n 1` @2000 MB |
| HEAD `0682434` + `9625c174` | yes, release + fastdebug | **8/8**, release + fastdebug |

This is the load-bearing consequence: the mechanisms introduced in the HEAD skew range — the
concurrent plan (`0a11e2c0`), the upstream concurrent-marking interface (`50cc7ff8`), and the
`plan/lxr` relocation (`e6e7d2eb`, `3c634449`, `dbf1ebbf`) — have been **observed executing**, not
merely read. `P0.1-mechanism-diff.md` §18.3 records them as `[obs-override]`.

### 9.2 Agreement with the shipped pairs — the useful part

The override and shipped configurations produce the **same pass/fail pattern**:

| configuration | `-n 1` @2000 MB | fastdebug `-n 1` @2000 MB |
|---|---|---|
| PLDI shipped (`df8d30a3`) | 5/8 — fails lusearch, eclipse, xalan | 5/8 — same three |
| PLDI override (`4d4e516c`) | 5/8 — fails lusearch, eclipse, xalan | 5/8 — same three |
| HEAD shipped (`304ce69d`) | 8/8 | 8/8 |
| HEAD override (`9625c174`) | 8/8 | 8/8 |

Identical benchmark for benchmark. This is what rules out revision skew as the cause of PLDI's
instability (§7.3): the defect is present in the configuration that actually shipped, and the nine
commits between the two PLDI revisions do not touch it — consistent with the source-level
classification in `P0.1-mechanism-diff.md` §18.1, which finds that range inert in the LXR feature
configuration. Two independent lines of evidence agreeing.

The `zero rc count` assertion was observed in **both** configurations (shipped `xalan`, override
`eclipse`), which further confirms it is not skew-related — as expected, since `src/plan/barriers.rs`
is byte-identical across the range.

### 9.3 The sustained test, tag versus pin — the decisive comparison

The `-n 1` agreement above could in principle mask a difference that only appears under load, since
PLDI's instability is load-dependent (§7.2). It does not. At **`-n 5` @2000 MB, 3 invocations**, the
two PLDI configurations agree on every single cell:

| benchmark | PLDI pin `df8d30a3` (shipped) | PLDI tag `4d4e516c` (override) |
|---|---|---|
| antlr | **CRASH ×3** | **CRASH ×3** |
| fop | PASSED ×3 | PASSED ×3 |
| luindex | CRASH ×3 | CRASH ×3 |
| lusearch | CRASH ×3 | CRASH ×3 |
| pmd | CRASH ×3 | CRASH ×3 |
| eclipse | CRASH ×3 | CRASH ×3 |
| hsqldb | PASSED ×3 | PASSED ×3 |
| xalan | CRASH ×3 | CRASH ×3 |
| **total** | **2/8** | **2/8** |

`[verified]` 48 runs, no disagreement in any cell. `antlr` is the sharpest case: it passes at `-n 1`
and fails at `-n 5` on **both** revisions, so the load-dependent failure that defines PLDI's
instability is reproduced identically by the pinned revision.

**This answers the tag-versus-pin question empirically.** A plausible reading of the nine-commit skew
range was that the tag is unstable and the reference fixed it in the commits the binding pins past
it — two of them are named *"Fix stw LXR"* and *"fix stw lxr again..."*, and PLDI's crash sites are
the barrier and the concurrent trace, exactly what such fixes would touch. **That hypothesis is
disproven.** The pin is neither more nor less stable than the tag; they are behaviourally
indistinguishable across 96 release runs and two fastdebug passes.

The mechanical reason is in `P0.1-mechanism-diff.md` §18.1: `014368ef Fix stw LXR` changes a constant
from `true` to `cfg!(feature = "lxr_lazy")`, and the `lxr` feature *implies* `lxr_lazy`, so under
`--features lxr` it still evaluates `true`. Those fixes target the **stop-the-world** LXR variants,
which is what "stw LXR" names. They are inert in the configuration under test — confirmed at runtime
by the collector's own banner reporting `lazy_mu_reuse_block_sweeping: true`.

**Consequence for the oracle choice:** stability cannot decide between tag and pin, because there is
no stability difference to decide on. The choice is therefore a provenance choice, not an empirical
one, and either selection is defensible on the evidence — the numbers in this document are valid for
both. What is *not* defensible is the inference the hypothesis rested on: that a fix-shaped commit
message implies the fix applies to your configuration.
