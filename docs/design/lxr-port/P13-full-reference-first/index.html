Full collection / how it works / where we differ

How a full collection works in the Java LXR and in our .NET port

We have a garbage collector named LXR. In Java, it works well and it is fast. We copied its ideas into .NET. Our copy is much slower in one test. This page explains, from the basics, how each one works. It shows where our copy does extra work.

Short answer

Are we reinventing the wheel?

Partly, yes. We copied the main ideas of LXR. We did not copy the way the Java LXR organizes the work. In several places, we built our own method. Our methods do more steps than the Java LXR does.

Two examples:

  • The Java LXR shares the main marking work between many threads. Our port uses one thread for it.
  • The Java LXR reads a field of an object with a normal memory read. Our port reads it with a locked CPU instruction, and then adds one to a shared counter with a second locked instruction.

What we found

We found 16 places where our port does different or extra work in a full collection. The last part of this page lists all 16.

What we do not know

We do not know how much time each difference costs. We did not measure them one by one. So this page does not say that these 16 differences explain the whole slowdown.

01

What we compare

The Java LXR

LXR comes from a 2022 research paper by Zhao, Blackburn and McKinley. The authors wrote the code in the Rust language. It is part of MMTk, a toolkit for building collectors. It works inside the Java runtime (OpenJDK).

We use the exact version that the authors keep today. We built it and ran it ourselves. It works.

Our port

We wrote LXR again for .NET. It is C++ code inside the .NET runtime (CoreCLR). A setting selects it in place of the standard .NET GC.

This is the version we accepted earlier. It is not the two later experiments that we rejected.

What we study

This page explains one kind of collection: the full collection. A full collection stops the program and looks at the whole heap. You start one when you call GC.Collect() in .NET or System.gc() in Java. LXR also starts one by itself, for example when the heap is nearly full.

Why we study it

Our first test called GC.Collect() eight times. Our port needed roughly 30 to 100 times longer than the standard .NET Workstation GC for this test. We wanted to know why, and if we built what the Java LXR builds.

Real programs do not call GC.Collect(). So we also measured the collectors when they run by themselves, with the same programs written in C# and in Java. That second page has the results. Our port is 7 to 28 times slower there, and it makes many full collections by itself. So the full collection matters in real use too, but it is not the only problem.

How we studied it

We read the source code of both collectors, from the start of a full collection to its end. We used exact versions. We also looked at the machine code of one hot place in our port. We did not run a new test.

Two limits to keep in mind

  • A full collection is the rare path in LXR when the heap is large enough. LXR does most of its work in short, cheap collections. This page explains the full collection, because it is easy to read in the source code. The cheap collections need their own comparison.
  • The exact test of eight forced collections was not run on the Java LXR. The natural-collection page runs three matched programs on the Java LXR instead, without forced collections.

02 / basics

What a garbage collector does

A program makes objects. Objects live in a large area of memory named the heap. An object has fields. A field can hold a pointer: the address of another object.

When the program stops using an object, its memory must become free again. The GC finds these objects and frees them.

How does the GC know that an object is not in use? It starts from the roots. Roots are the places where the program holds pointers: local variables on thread stacks, static variables and handles. An object is live if you can reach it from a root when you follow pointers. All other objects are garbage.

The GC does two jobs:

  1. Find the live objects. The GC follows pointers from the roots and puts a mark on each object that it reaches. We call this a trace.
  2. Free the memory of the objects without a mark.

Some collectors also move live objects together, to close the gaps between them. When an object moves, every pointer to it must change to the new address.

While the GC changes pointers, the program must not run. So the GC stops all program threads. The time the program waits is a pause.

03 / the LXR idea

How LXR works

LXR uses two methods together.

Method 1: counting

Each object keeps a number: how many pointers point to it. When the program changes a pointer, it writes a short note in a log. During a pause, LXR reads the log and changes the counts. When a count falls to zero, nothing points to the object. Its memory is free.

Counting is fast. It looks only at what changed. It does not look at the whole heap.

Counting has one problem: cycles.

Method 2: tracing

A trace finds garbage that counting cannot find. LXR follows pointers from the roots and marks every live object. An object without a mark is garbage, also when it is part of a cycle. Tracing costs more, because it reads every live object.

Full collection

LXR does most of its work in short pauses that only use counting. It runs a trace in the background when it can. A full collection is different. It is one pause that does the counting work and a complete trace while the program is stopped. LXR uses it when the program asks for it, or when memory is nearly full.

A full collection has these stages. We use these numbers on the rest of this page.

04 / the walk-through

The full collection, stage by stage

Both collectors use worker threads. A worker thread is an extra thread that takes small jobs from queues. If many workers do jobs at the same time, the work is parallel.

The time of a full collection depends on three things. First, how many steps the collector does for each object and each pointer. Second, how it shares the work between threads. Third, how many times it visits all objects. We look at all three.

In this text, the Java LXR is the version that works in Java. Our port is the version in .NET.

Stages 1 and 2: decide and stop

Both collectors treat GC.Collect() or System.gc() as a request for a full collection. If no background trace is active, both choose a full collection. Both stop the program threads before they start. We found no important difference here.

One note. The older Java LXR, from the paper, ignores System.gc(). The newer one that we use does not ignore it.

Stage 3: find the roots and prepare

The Java LXR

Worker threads scan the thread stacks. Each worker takes some of the stacks. Many small jobs clear the old marks, one job for each chunk of the heap.

Our port

One thread scans the roots. It is a thread that the .NET runtime knows. Before the scan, our port prepares two large helper tables. The same thread also visits every object in the heap to reset flags for pinning and finalizers.

The helper tables. Our trace uses two tables: one lock byte and one pointer for each 8 bytes of the heap. In our test, the normal-object area is 64 MiB. The tables for it are 72 MiB, larger than the area itself, because they use 9 bytes for each 8 bytes of heap. At the start of every full collection, our port asks the operating system for this memory and writes a starting value into every cell. At the end, it gives the memory back.

Visiting every object. Most objects in a heap are plain data. They have no finalizer and no pin. Our port still visits all of them, one by one, to reset the flags. The time of this visit grows with the number of objects.

Stage 4: the counting work

Both collectors share this work between worker threads. Our port does this part in parallel too. Not all work in our port is single-threaded.

The difference is in how the trace starts. In the Java LXR, the root pointers become the starting points of the trace. In our port, the counting work for each root also adds that root to the list of objects to trace. Later, the trace-preparation step adds the same roots again. Our port also adds the objects that logged pointer changes point to. The Java LXR does not add these.

These extra starting points take time. They do not find more live objects if the roots already lead to them. We do not know yet which of them our port needs.

Java LXR: src/plan/lxr/rc.rs:527-661. Our port: src/coreclr/gc/lxr_reference_counting.cpp:1711-1822,2911-3040,3744-3807,5309-5337.

Stage 5: the trace

This is the largest stage. The next part of this page explains it in detail. Here is the main difference in one sentence: the Java LXR shares the trace between many worker threads, and our port runs the whole trace on one thread.

Stage 6: weak pointers and finalizers

Some objects need special care. A weak pointer does not keep its object alive. A finalizer is code that must run after its object dies. A dependent handle keeps object B alive only if object A is alive. The GC must handle all of these after the trace.

The Java LXR

During the trace, the Java runtime finds weak and finalizable objects and puts them in lists. In this stage, the collector reads only these lists. It does not search the heap.

Our port

Our port searches the heap. It visits every object again to find the ones that have finalizers. Sometimes it visits them a third time. It also repeats the loop for dependent handles until nothing changes.

.NET needs finalizers, so the work itself is required. The standard .NET GC keeps a list of the objects that have finalizers. It does not visit every object. We have not yet checked if our port can use the same list.

Java LXR: src/scheduler/scheduler.rs:311-350, mmtk/src/reference_glue.rs:181-287. Our port: src/coreclr/gc/lxr_gc.cpp:1194-1223, src/coreclr/gc/lxr_reference_counting.cpp:3685-3707.

Fixing pointers to moved objects

When a collector moves an object, it must change all pointers to that object. Our port has three modes: no moving, move young objects, and move young and old objects. In a mode that moves objects, our port repairs several lists in several passes. The lists are the roots, the logs and the lists of trace work. It makes these passes also when the collection moved nothing. In the no-moving mode, it skips these passes.

Our port: src/coreclr/gc/lxr_reference_counting.cpp:3362-3435,3628-3707, src/coreclr/gc/lxr_gc.cpp:1224-1240.

Stage 7: free the memory

Both collectors finish the counting work and sweep memory for objects without a mark. The Java LXR cuts the heap into chunks and gives each chunk to a worker thread. Each worker reads the tables directly. Our port does similar work, but it uses general functions that check each address.

In one place our port does less work than the Java LXR. It keeps a list of where objects start. The Java LXR checks every possible start position. So we cannot say that every difference in this stage costs us time.

Java LXR: src/plan/lxr/global.rs:272-297, src/policy/immix/immixspace.rs:602-638, src/plan/lxr/rc.rs:692-913, src/policy/immix/rc_work.rs:181-292. Our port: src/coreclr/gc/lxr_reference_counting.cpp:3122-3359,3434-3595,5369-5454.

Stage 8: finish

The Java LXR

A worker deletes each job when it ends it. The last worker closes the queues, updates the page counts and lets the program run again.

Our port

Our port visits every object once more, to compute statistics for GC.GetGCMemoryInfo(). Then the program runs again. After that, but before GC.Collect() returns, our port deletes its job records and frees the helper tables.

.NET needs these statistics. A separate visit of all objects is our own choice. The Java LXR uses page counts.

The Java LXR drops each finished job at once. Our port keeps the finished jobs on a list until the end of the collection. This keeps the old jobs available for safety checks. We do not know yet if it can free them earlier.

05 / stage 5 in detail

The trace: how each collector marks live objects

A trace is simple in principle. Start at a root. Mark the object that it points to. Look at each field of that object. For each field that holds a pointer, do the same for the object it points to. Continue until nothing new is left.

The collector keeps a queue of work that it still has to do. The two collectors differ in what is in the queue, who takes work from it and how many steps each item needs.

What is in the queue, and who works on it

The Java LXR puts fields in the queue. It groups them in packets: small jobs of up to 8,192 fields. Packets go to queues that all workers can use. A worker takes a packet, processes it, and puts new packets back. A worker with no work takes packets from a busy worker. A very large array is cut into slices of 8,192 fields.

Our port puts objects in the queue. Our trace list is one list. One thread takes objects from it, one after another. The other worker threads do counting work. They do not help with the trace. A large array is cut into slices of 1,024 fields. For an array of 262,144 fields, this is at least 256 slices. The Java LXR needs 32 slices for the same array. Each slice is a job that must save where it stopped.

The steps for one field

Now look at what each collector does for one field, and for the object that the field points to. We call that object the child.

A locked CPU instruction is a special instruction. It makes sure that no other CPU core changes the same memory at the same moment. The CPU must wait for earlier memory work to finish. So a locked instruction is slower than a normal read. We have not measured by how much in this program.

Why our port does more

  • Reading a field. Our port reads each field with Interlocked.CompareExchange(field, null, null). This asks the CPU: "if the field holds null, store null, and tell me what was in it." It is a trick for an ordered read. We checked the machine code of our Linux build. It uses a locked instruction. The Java LXR reads the field with a normal read on x64.
    The same code also runs during a background trace, while the program runs. There, ordered reads may be needed. In a full collection, the program is stopped. A locked read may not be needed. We must check this case by case.
  • Counting every field. Our port adds one to a shared counter for every field it visits, also for empty fields. This is a second locked instruction. The Java LXR has detailed counters too, but they are off unless a special option is on.
  • Queuing every child. Our port puts every non-empty child in the list, also children that are already marked. It finds out later, when it takes the object from the list, that the object is marked. By then, it has already used the lock and the table reads. The Java LXR checks the mark before it queues. This early check is used for ordinary objects. It is not used for the slices of a large array.
  • Marking an object. Our port reads the count and the mark with general functions that first check the address and the table layout. For a new object, it makes the CPU wait six times, and then does one more atomic update. The Java LXR does one atomic update with no extra waits.
  • Extra writes. In the modes that move old objects, our port writes the field back after the scan, also when the child did not move.

The two experiments we rejected

Earlier, we spent two experiments on how our port reads two small tables: the count and the mark. The second experiment removed two of the CPU waits. In some tests, the full collection became 4 to 10 percent faster. In one Linux test, it became 31 percent slower. We rejected it.

This page shows why a gain of this size was expected: those two reads are one small part of the whole picture.

06

What .NET needs that Java does not

We cannot copy the Java LXR without change. .NET asks for things that the Java LXR does not do. Our port must keep all of them:

  • Pinned objects. A program can fix the address of an object, for example when it passes it to native code. The Java LXR does not support this at all. Its code says pinning is unsupported.
  • Finalizers, weak pointers and dependent handles, with their exact rules.
  • Pointers into the middle of an object (interior pointers), frozen objects and the pinned object heap.
  • Collectible code: assemblies that .NET can unload.
  • The rules of the .NET runtime for suspending threads and scanning roots.

A requirement does not tell us how much the implementation must cost. For example, .NET needs finalizers. It does not need us to visit every object to find them. Each extra step in our port needs its own reason.

07

What we do not know

  • The cost of each difference. We did not measure them one by one. They overlap. You cannot add them as percentages.
  • The time of the Java LXR on the forced test. We did not run it. On matched programs without forced collections, the Java LXR is close to the standard Java collectors (natural-collection page). There, the Java LXR also makes full collections, but they are short.
  • How much the single trace thread costs. One thread alone cannot explain a slowdown of 30 to 100 times compared with the standard .NET Workstation GC. That GC also marks with one thread. The cost of each step matters too.
  • Which extra steps in our port are really needed. Some protect against stale pointers or old readers. We must prove what is safe to remove.
  • Where our port does less. The list of object starts in the sweep is one example.

We found these facts by reading code. We did not profile the Java LXR.

08

What we should do next

The lesson: do not tune one helper function. Rebuild the full collection so that it has the same shape as the Java LXR. Keep every .NET rule. Do it in these steps:

  1. Use the matched programs as the target. The natural-collection benchmark already runs the Java LXR on the same work. A change is good only if it moves our port toward the Java LXR there.
  2. Change the trace to the Java LXR shape. Use fields as work items. Skip marked children before you queue them. Use slices of 8,192 fields. Give the work to all worker threads.
  3. Remove setup and extra visits. Do not create and free the 72 MiB tables in every collection. Find a list or a counter to replace the visits of every object.
  4. Make the hot loop small. Use a short, fixed way to read the count and mark. Do it only after we prove that it is safe.
  5. Keep the .NET rules. Test pins, finalizers, weak pointers and moved objects after each change.

For each change, count the steps before and after. Then measure the time, and compare with both the Workstation GC and the Server GC.

The large area of memory where a program's objects live.
Pointer
The address of an object. A field can hold a pointer.
Root
A place where the program holds a pointer: a stack variable, a static field or a handle.
Live object / garbage
A live object has a path from a root. Garbage has no such path.

A trace follows pointers from the roots. It puts a mark on each object that it reaches.
Counting
The method that keeps a number for each object: how many pointers point to it. The research papers call it reference counting.
Cycle
Objects that point to each other. Their counts never fall to zero.
Full collection
One pause with the counting work and a complete trace.
Pause
The time that the program waits for the GC.
Worker thread
An extra thread that takes small jobs from queues.
Packet
A small job in the Java LXR. It holds up to 8,192 fields.
Child
The object that a field points to.

A CPU instruction that makes sure that no other core changes the same memory at the same time. It is slower than a normal read.
