# P0.1 — Mechanism-level diff: `lxr-pldi-2022` vs `lxr` branch head

**Purpose.** This is the direct input to **P0.3** (the mechanism parity ledger). For each LXR
mechanism it records where the mechanism lives on each of the two parity oracles, what changed
between them, whether the change is **semantic** or **cosmetic**, and which revision a .NET/CoreCLR
port should follow — with a reason.

**Revisions under comparison**

An oracle is a **build pair**, not a tag: LXR only exists as binding + core together.

| | mmtk-openjdk (binding) | mmtk-core **as the binding pins it** — *the oracle* | mmtk-core the roadmap names |
|---|---|---|---|
| **PLDI** (`lxr-pldi-2022`) | `abbdd1d` | **`df8d30a3`** *rc_bits* | `4d4e516c` *class pointer validity checks* |
| **HEAD** (`lxr` branch) | `0682434` | **`304ce69d`** | `9625c174` *Add an option to disable RC decs* |

Neither roadmap-named revision is what its binding builds, and the skew is symmetric: PLDI's named
revision is **9 commits behind** its oracle, HEAD's is **9 commits ahead** of its oracle. All
eighteen commits are classified in **§18** — none is waved through.

`lxr-x/simplified` is out of scope by the parity contract and is not considered anywhere below.

**Evidence convention.** Every claim is tagged:

- `[verified]` — read directly out of both checked-out revisions (file listing, line count, or
  quoted source), or observed at runtime.
- `[inferred]` — a reasonable reading of the code that was *not* separately confirmed by running it.

**Observability convention.** Reading code and watching it run are different kinds of evidence, and
P0.3 must not mistake one for the other. Every mechanism carries one of three levels:

| level | meaning |
|---|---|
| **`[obs-oracle]`** | observed executing in a **shipped-pair** build. The strongest evidence available here. |
| **`[obs-override]`** | observed executing, but only in a **path-override** build that never shipped. Real execution evidence; *not* a parity baseline. |
| **`[read-only]`** | never observed executing. Established by reading source alone, however carefully. |

A mechanism that exists only inside one of the two nine-commit skew ranges cannot be `[obs-oracle]`
on both revisions by construction — see §18.3.

> **`mmtk-core/src/plan/lxr/` does not exist at the PLDI revision.** `[verified]`

plan**. `src/plan/` at PLDI contains `barriers.rs`, `generational/`, `global.rs`, `immix/`,

organised **by mechanism**, and each section states the *location on each revision* before it states
the delta. This is not a stylistic preference; it is the only form the comparison can take.

## 2. Plan identity and configuration

### Location

| | PLDI | HEAD |
|---|---|---|
| plan | `src/plan/immix/{global,mod,mutator,gc_work}.rs` (1025/154/90/297 lines) | `src/plan/lxr/{global,mod,mutator}.rs` + `gc_work/` (1100/124/75 lines + 8 files) |
| selection | `Cargo.toml` feature `lxr` | `PlanSelector::LXR` in `src/util/options.rs:54` |

`[verified]`

### What changed

**PLDI.** LXR is a stack of cargo features. `Cargo.toml` defines **41 `lxr*` features**. `[verified]`
The composite is:

```toml
lxr_basic = ["ix_ref_count"]
lxr_cm    = ["lxr_basic", "lxr_concurrent_marking"]
lxr_lazy  = ["lxr_basic", "lxr_lazy_decrements"]
lxr_evac  = ["lxr_basic", "lxr_nursery_evacuation",
             "lxr_mature_evacuation", "lxr_count_bytes_for_mature_evac"]
lxr       = ["lxr_basic", "lxr_cm", "lxr_lazy", "lxr_evac"]
```

`src/args.rs` then turns each feature into a `const bool` — `REF_COUNT`, `CONCURRENT_MARKING`,
`LAZY_DECREMENTS`, `RC_NURSERY_EVACUATION`, `RC_MATURE_EVACUATION`, `BLOCK_ONLY`, `DEFRAG` — so the
whole plan is monomorphised at compile time. `[verified]`

**HEAD.** `PlanSelector::LXR` is a runtime enum variant; `src/plan/global.rs:63` and `:103`
dispatch to `create_lxr_mutator` and `LXR::new`. `[verified]` The head `Cargo.toml` says outright:
*"We can select plan at runtime. So no need to use any of these features"*. `[verified]`

### Semantic or cosmetic

**Semantic**, and it is the single most consequential difference for a port. It changes what a
"plan" *is*: at PLDI, choosing LXR is a build; at HEAD it is a startup option.

### Which revision should a .NET port follow, and why

**HEAD.** A CoreCLR standalone GC is a DLL loaded at process start and selected by configuration
(`GCName`); it cannot be a compile-time monomorphisation of a different collector. HEAD's shape is
already the shape the port must have. The PLDI feature list remains useful as an *ablation
catalogue* — it enumerates precisely which mechanisms can be independently disabled, which is
valuable for staged bring-up — but it should not drive the architecture.

## 3. Coalescing reference counting

### Location

`src/util/rc.rs` on both revisions — but **PLDI 1057 lines vs HEAD 245 lines**. `[verified]`

### What changed

This 4× shrink is *not* a loss of function. At HEAD the RC work packets moved out of `util/rc.rs`
into `src/plan/lxr/gc_work/rc.rs` (956 lines). `[verified]` What remains in `util/rc.rs` is the bit
manipulation layer.

The core operations are the same set on both: `inc`, `dec`, `set`, `count`, `is_dead`, `rc_stick`,
`promote`, `mark_straddle_object` / `unmark_straddle_object`, `is_straddle_line`,
`address_is_in_straddle_line`, `rc_table_range`, `assert_zero_ref_count`. `[verified]`

Both use the same side-metadata specs: `RC_TABLE`, `RC_STRADDLE_LINES`, and (PLDI) `RC_LOCK_BITS`.
`[verified]`

**Stuck counts.** Both implement the paper's saturating count: `rc_stick(o)` is
`count(o) == MAX_REF_COUNT`, and `inc` refuses to increment past it. `[verified]`

**The one real difference is the count *type*, not the width.**

| | PLDI oracle `df8d30a3` | HEAD oracle `304ce69d` |
|---|---|---|
| `LOG_REF_COUNT_BITS` | a `const` block selecting 1/2/3 from features `lxr_rc_bits_{2,4,8}`, **defaulting to 1** | **identical `const` block, character for character** |
| `REF_COUNT_BITS` | `usize` | `u8` |
| `MAX_REF_COUNT` | `(1 << REF_COUNT_BITS) - 1` | `REF_COUNT_MASK`, `u8` |

`[verified]` **The tunable-width construct is not a HEAD innovation** — it is introduced *within the
PLDI skew range*, by the very commit the PLDI oracle is named after (`df8d30a3` "rc_bits", §18.1),
and then survives four years to HEAD unchanged. Only the integer type narrows, `usize` → `u8`.

At the roadmap-*named* PLDI revision `4d4e516c` the constant is instead a plain `pub const
LOG_REF_COUNT_BITS: usize = 1;`. `[verified]` All three spellings evaluate to the same thing in a
`--features lxr` build: **2 bits per object, counts 0–3, 3 = stuck** — what the paper describes.

**Porting consequence.** RC field width is a *designed* tunable in the reference, offering 2, 4 or 8
counts. A .NET port should parameterize it rather than hardcode 2 bits, and must reproduce the
saturating "stuck at `MAX_REF_COUNT`" semantics that a 2-bit field forces.

**`LOG_MIN_OBJECT_SIZE`**: PLDI hard-codes `4`; HEAD takes it from
`crate::util::constants::LOG_MIN_OBJECT_SIZE`. `[verified]` Same value on 64-bit OpenJDK; a port must
re-derive it from CoreCLR's own minimum object size, which is **not** 16 bytes.

### Semantic or cosmetic

**Cosmetic, plus parameterisation.** No change to the RC algorithm at the default configuration.

### 3.4 The PLDI implementation violates its own RC invariant `[verified]`

This is the most consequential runtime observation in P0.1 and it lands squarely on this mechanism.

Running PLDI's **fastdebug** build on DaCapo `xalan` (and `eclipse`) trips an assertion in the write
barrier's slow path:

```rust
// src/plan/barriers.rs:315 — identical at 4d4e516c and df8d30a3
#[cfg(any(feature = "sanity", debug_assertions))]
assert!(old.is_null() || rc::count(old) != 0, "zero rc count {:?}", old);
```

```text
thread '<unnamed>' panicked at 'zero rc count 0x2001ef08000', .../df8d30a/src/plan/barriers.rs:315:9
```

A field being overwritten still points at an object whose reference count has **already reached
zero**. Several worker threads trip it simultaneously on different objects. In release builds the
assertion is compiled out and the same corrupt state surfaces as a `SIGSEGV`, either in the barrier
or in `ImmixConcurrentTraceObjects::do_work`. HEAD never trips it, in any configuration.

Full characterisation, including what was ruled out, is in `P0.1-benchmarks.md` §7.

**What this does and does not mean.**

- It does **not** invalidate the paper's design, and it does not make PLDI's source a bad statement
  of the algorithm. The RC code reads cleanly and matches the paper.
- It **does** mean PLDI's RC implementation cannot serve as an *executable specification*. A .NET
  port cannot differentially test its RC behaviour against PLDI on any sustained workload, because
  the reference itself violates the invariant under exactly those conditions.
- It **does** mean the RC/barrier coupled set (§15) should be validated against **HEAD**, even where
  the algorithm is taken from PLDI.

`[inferred]` The most likely reading — decrement applied while a live field still holds the
reference, i.e. a coalescing/lazy-decrement race — is *not* confirmed. Diagnosing it was out of scope
for P0.1, which asked for observation rather than repair. P0.3 should decide whether root-causing it
is worth the effort before any RC work begins; if PLDI is chosen as the RC oracle, it probably is.

### Which revision should a .NET port follow, and why

**PLDI for the *specification*, HEAD as the *executable reference*.** At PLDI the whole mechanism —
bit layout, straddle-line handling, and the inc/dec processing packets — is in one 1057-line file
that can be read end to end against the paper, and that remains the clearest statement of the
algorithm. But per §3.4 it cannot be run as an oracle, so implementation behaviour must be checked
against HEAD. Port HEAD's *split* (metadata layer vs work packets) once the semantics are
established, because that split is better engineering.

**Porting note.** `LOG_MIN_OBJECT_SIZE` and the RC-table granularity are the first two constants that
must be re-derived for CoreCLR. Every straddle-line computation depends on them.

## 4. The field barrier (coalescing RC + SATB, fused)

> This section corrects an error I made and caught. The initial reading was that HEAD splits LXR's
> barrier into an RC barrier and an SATB barrier. **It does not.** LXR's barrier is fused on *both*
> revisions. What HEAD adds is a *separate* SATB-only barrier belonging to a *different* plan.

### Location

| | PLDI | HEAD |
|---|---|---|
| Rust | `src/plan/barriers.rs` → `FieldLoggingBarrier` (655 lines total) | `src/plan/lxr/barrier.rs` → `LXRFieldBarrierSemantics` (249 lines) |
| C++ | `openjdk/barriers/mmtkFieldLoggingBarrier.{cpp,hpp}` (12.7 KB + 13.6 KB) | `openjdk/barriers/mmtkFieldBarrier.{cpp,hpp}` (20.9 KB + 3.5 KB) |
| selector | `BarrierSelector::FieldLoggingBarrier` | `BarrierSelector::FieldBarrier` |

`[verified]`

### The fusion evidence

**PLDI `FieldLoggingBarrier`** carries both buffers and imports the SATB packet type:

```rust
use crate::util::cm::ProcessModBufSATB;   // barriers.rs:10
...
incs: Vec<Address>,                       // :197
decs: Vec<ObjectReference>,               // :198
```

and in `slow()` (`:313`) pushes `old` onto `decs` and `edge` onto `incs` in the same call. `[verified]`

**HEAD `LXRFieldBarrierSemantics`** is structurally the same:

```rust
use super::gc_work::tracing::ProcessModBufSATB;  // barrier.rs:10
...
incs: VectorQueue<VM::VMSlot>,                   // :35
decs: VectorQueue<ObjectReference>,              // :36
```

with `flush_incs()` (`:145`) and `flush_decs_and_satb()` (`:159`) — the latter feeding the *same*
`decs` buffer to both `ProcessModBufSATB` and `ProcessDecs`. `[verified]`

**That last point is the mechanism.** LXR's decrement buffer *is* its SATB buffer. The old target
overwritten by a field write is simultaneously (a) an object that lost a reference, so it needs a
decrement, and (b) an object that was reachable at the snapshot, so the concurrent trace must see it.
One barrier, one buffer, two consumers. This is the core insight the port must preserve, and it is
identical on both revisions.

### What HEAD's `SATBBarrierSemantics` actually is

`src/plan/concurrent/barrier.rs:18` defines `SATBBarrierSemantics` with a **single** field
`satb: VectorQueue<ObjectReference>` (`:25`) and no `incs`/`decs`. `[verified]` It belongs to HEAD's
new **ConcurrentImmix** plan (`src/plan/concurrent/immix/`), not to LXR. `[verified]`
Similarly `mmtkSATBBarrier.cpp` and `mmtkUnlogBitBarrier.cpp` are new **additional** barrier
implementations, not a decomposition of the field barrier. `[verified]`

So: HEAD split the barrier **family**; it did not split **LXR's** barrier.

### The genuine LXR-visible delta

1. **Rename** `FieldLoggingBarrier` → `FieldBarrier` (and the C++ file with it).
2. **`Address` → `VM::VMSlot`.** PLDI's `incs` buffer holds raw `Address`; HEAD's holds an
   abstract slot type. Every barrier entry point changes accordingly
   (`get_edge_logging_state(edge: Address)` → `get_slot_logging_state(slot: VM::VMSlot)`,
   `log_edge_and_get_old_target` → `log_slot_and_get_old_target`). `[verified]`
3. **`Vec` → `VectorQueue`.** A capacity-aware buffer replacing manual `len() >= CAPACITY` checks.
   `[verified]`
4. **PLDI has explicit per-edge locking** — `attempt_to_lock_edge_bailout_if_logged`, `unlock_edge`,
   `log_and_unlock_edge`, backed by the `RC_LOCK_BITS` side-metadata spec and
   `LOG_BYTES_PER_RC_LOCK_BIT`. HEAD has `attempt_to_log_field` and **no** `RC_LOCK_BITS`.
   `[verified]` HEAD appears to have replaced the lock-bit protocol with a CAS on the log bit itself.
   `[inferred]` — I did not confirm this by execution.
5. **PLDI's `slow()` returns `Result<ObjectReference, ()>` from the log helpers; HEAD returns
   `Result<Option<ObjectReference>, ()>`** — an explicit null-target case rather than a sentinel.
   `[verified]`

### Semantic or cosmetic

**Cosmetic for the algorithm; semantic for the interface.** Item 4 is the one item that could be
semantic, and it is flagged `[inferred]`: P0.3 should resolve whether HEAD dropped a lock protocol
that PLDI needed, or whether PLDI's lock was superseded by a correct single-CAS.

### Observed behaviour — the PLDI barrier fails its own assertion `[verified]`

The PLDI build does not merely crash near this mechanism; in a fastdebug build it **states what is
wrong**, on line 315 of the very file this section describes:

```rust
// src/plan/barriers.rs:315, in FieldLoggingBarrier::slow() — byte-identical at 4d4e516c and df8d30a3
#[cfg(any(feature = "sanity", debug_assertions))]
assert!(old.is_null() || rc::count(old) != 0, "zero rc count {:?}", old);
```

```text
thread '<unnamed>' panicked at 'zero rc count 0x2001ef08000', .../df8d30a/src/plan/barriers.rs:315:9
```

The barrier is logging a slot whose **old referent already has reference count zero** — a live field
pointing at an object RC has already declared dead. In release builds the `cfg` compiles the check
out, and the same state instead faults in `FieldLoggingBarrier::write_barrier`, alternating with
`ImmixConcurrentTraceObjects::do_work` (§5) — the producer and consumer of the shared decs/SATB
buffer described above. **One defect, two faces.** HEAD never trips it. Full evidence in
`P0.1-benchmarks.md` §7.

Two things follow, and they should be kept apart:

- This is **not** evidence that the barrier *algorithm* is wrong. PLDI is a research snapshot whose
  own CI never exercised LXR (§16.5), and the assertion site is identical across the whole PLDI skew
  range, so it is not a revision-skew artefact either.
- It **is** conclusive that the PLDI barrier implementation cannot be treated as a known-good
  executable reference. Implement the algorithm as described here, and validate against **HEAD**,
  which runs the full benchmark set cleanly at every heap size and iteration count tried.

It also raises the priority of resolving item 4 above: a dropped lock protocol is exactly the kind of
change that would produce a race between these two sites, and the failing assertion is precisely an
RC-count race. `[inferred]` — a hypothesis, not a diagnosis.

### Which revision should a .NET port follow, and why

**HEAD**, for the interface. `VM::VMSlot` is exactly the abstraction a CoreCLR port requires: CoreCLR
slots are not uniformly "an address holding a full pointer" (there are interior pointers, byrefs, and
— if the port ever wants them — compressed forms). Porting PLDI's raw-`Address` barrier would bake in
an assumption that has to be undone later.

But **read PLDI's `mmtkFieldLoggingBarrier.hpp` for the fast path.** It is 13.6 KB of header versus
HEAD's 3.5 KB, because at PLDI the C1/C2/interpreter fast-path emission lives in the header.
`[verified]` That fast path — the inline unlogged-bit test that runs on every reference store — is
the single most performance-critical piece of the entire port and the part that must be re-expressed
as JIT-emitted code in RyuJIT rather than as a runtime call.

## 5. SATB concurrent marking

### Location

| | PLDI | HEAD |
|---|---|---|
| implementation | `src/util/cm.rs` (`ProcessModBufSATB`) | `src/plan/lxr/gc_work/tracing.rs` (815 lines) for LXR; `src/plan/concurrent/concurrent_marking_work.rs` (309 lines) for the generic plan |
| enable flag | `args.rs: CONCURRENT_MARKING = cfg!(feature = "ix_concurrent_marking")` | runtime |
| interface | none — inline in the Immix plan | `src/plan/concurrent/mod.rs` (35 lines) + `src/plan/concurrent/global.rs` (10 lines) |

`[verified]`

Files mentioning concurrent marking:

- PLDI: `policy/largeobjectspace.rs`, `args.rs`, `util/rc.rs`, `lib.rs`, `plan/immix/global.rs`,
  `plan/barriers.rs` `[verified]`
- HEAD: `lib.rs`, `plan/concurrent/{immix/mutator,immix/global,barrier,mod}.rs`,
  `plan/lxr/global.rs`, `vm/collection.rs` `[verified]`

### What changed

HEAD **extracted a reusable concurrent-marking framework** and made a second plan (ConcurrentImmix)
use it. LXR at HEAD keeps its own `ProcessModBufSATB` in `plan/lxr/gc_work/tracing.rs`, *distinct
from* the one in `plan/concurrent/concurrent_marking_work.rs`. `[verified]` — the two barrier files
import different `ProcessModBufSATB` types (`super::gc_work::tracing::ProcessModBufSATB` vs
`super::concurrent_marking_work::ProcessModBufSATB`).

The scheduler side did change materially — see §12.

`vm/collection.rs` appearing in HEAD's list is the VM-facing hook for concurrent work, which PLDI
does not have. `[verified]`

### Semantic or cosmetic

**Semantic at the framework level, largely unchanged at the LXR level.** LXR still owns its own SATB
tracing; what is new is that the *scheduler* now has first-class concurrent buckets to run it in.

### Which revision should a .NET port follow, and why

**Split, deliberately, and this is the one place I recommend a split within a broadly HEAD-leaning
port:**

- **LXR's SATB semantics: PLDI.** It is the paper's, it is unchanged at HEAD, and it is readable in
  one place.
- **The scheduler contract that runs it: HEAD** (§12). PLDI has no concurrent bucket; it cannot
  express "run this work while mutators are running" without the `Concurrent` /
  `ConcurrentResumable` / `FinishConcurrentWork` triple.

These are **not** the same mechanism, so this is not a coupled-set violation. §15 records the
coupling explicitly.

**Porting note.** CoreCLR already has a suspend-EE / restart-EE protocol and a GC-safe-point
mechanism; the `vm/collection.rs` hook is where that maps. This is the largest single piece of
generic runtime capability the project will need.

## 7. Mature sweeping / cycle collection

### Location

| | PLDI | HEAD |
|---|---|---|
| | inline in `plan/immix/global.rs` + `util/cm.rs` | `src/plan/lxr/gc_work/mature_sweeping.rs` (155 lines) |

`[verified]`

### What changed

Same story as §6: extraction. This is the mechanism that reclaims cycles — the part RC alone cannot
do, and the reason LXR needs the SATB trace at all.

Relevant PLDI knobs: `LAZY_MU_REUSE_BLOCK_SWEEPING = true`,

## 12. Work bucket / scheduler

### Location

`src/scheduler/work_bucket.rs`: **PLDI 308 lines, HEAD 458 lines**. `[verified]`

### What changed — this is the clearest semantic delta in the whole comparison

**Strongly semantic.**

**HEAD, without qualification.** Points 1 and 2 are not optional for CoreCLR. A port built on PLDI's

## 15. Coupled mechanism sets

Per the parity contract, mechanisms inside one set must share an oracle.

| Set | Members | Shared oracle | Why coupled |
|---|---|---|---|
| **A. RC core** | §3 RC, §9 block/line metadata, the RC-table and straddle-line specs in §11 | **PLDI** (algorithm) — but see the caution below | The RC bit layout, the block's RC-table range accessors, and straddle-line marking are one data structure viewed three ways. Mixing widths or table granularities across revisions is silently corrupting. |
| **B. Barrier + SATB buffer** | §4 field barrier, §5 LXR SATB semantics | **PLDI semantics, HEAD interface** | The decs buffer *is* the SATB buffer. The buffer's producer and both consumers must agree. The `Address`→`VMSlot` change is interface-only and does not cross the semantic boundary. |
| **C. Concurrency substrate** | §5 scheduler contract, §12 work buckets, §6 nursery sweeping, §7 mature sweeping | **HEAD** | The sweeps are scheduled *into* the buckets; `STWRCDecsAndSweep` exists only at HEAD and is where mature sweeping runs. |
| **D. Evacuation** | §8 mature evac + defrag, §10 block allocation | **HEAD** | Defrag selects blocks that the allocator must then honour; the `ImmixHooks` split changed both sides together. |
| **E. Configuration** | §2 plan identity, §14 args | **HEAD** | Runtime plan selection and runtime args are the same change. |

**Sets A and B are the ones that need care, and for the same reason.** Both take semantics from PLDI,
and PLDI's implementation of exactly those semantics is the one that fails `assert!(old.is_null() ||
rc::count(old) != 0)` under load (§3.4, §4). The failing assertion sits at the *seam between the two
sets* — the barrier (B) checking an invariant owned by RC (A) — which is itself weak evidence that
A and B may need to be treated as a single coupled set rather than two.

The practical rule for P0.3:

- **Specify** sets A and B from PLDI. Its source is the clearest statement of the paper's algorithm
  and remains the right thing to read.
- **Validate** them against HEAD. PLDI cannot be differentially tested against, because it does not
  hold its own invariant.
- Set B additionally takes its *interface* from HEAD. That is defensible only because §4 established
  the algorithm is unchanged — if P0.3 finds the `RC_LOCK_BITS` removal was semantic, set B must
  collapse to a single oracle, and sets A and B should then be merged.

## 16. Honest limits of this document

These are the things a reader must not assume I verified.

1. **The PLDI revision could only be partially benchmarked.** It runs 5 of 8 DaCapo 2006 benchmarks
   at one iteration and crashes under sustained execution; see `P0.1-benchmarks.md` §7.
   Recommendations in §5 (PLDI SATB semantics) and §8 (evacuation policy) therefore rest
   substantially on **code reading**, not on observed behaviour. HEAD runs 8 of 8 cleanly, so it is
   the only oracle that can be *observed* across the whole set.

2. **No line-by-line diff was taken of the extracted files** (§6, §7, §10). There is no PLDI file to
   diff against; the claim "same mechanism, relocated" is `[inferred]` from names, sizes and call
   sites. P0.3 should confirm each by reading PLDI's `immixspace.rs`/`global.rs` against HEAD's
   extracted files.

3. **The `RC_LOCK_BITS` removal (§4 item 4) is not explained.** I verified the spec exists at PLDI
   and not at HEAD; I did not establish what replaced it.

4. **`CM_LARGE_ARRAY_OPTIMIZATION` flipping `true`→`false` is unexplained** (§14).

5. **Neither revision's LXR path is covered by the reference's own CI.** PLDI's
   `ci-test-normal.sh` tests SemiSpace, Immix and GenImmix only; HEAD's `normal-heap.yml` lists nine
   plans, none of them LXR. `[verified]` So "the reference works" is not something CI attests to for
   LXR on either revision — a materially important fact for calibrating how much the reference can be
   trusted as an oracle.

6. **Version skew.** Neither roadmap-named mmtk-core revision is the one its binding pins:

   | | binding | mmtk-core the binding pins (**the oracle**) | mmtk-core the roadmap names | relationship |
   |---|---|---|---|---|
   | PLDI | `abbdd1d` | **`df8d30a3`** | `4d4e516c` | the named revision is 9 commits **behind** the oracle |
   | HEAD | `0682434` | **`304ce69d`** | `9625c174` | the named revision is 9 commits **ahead** of the oracle |

   `[verified]` All eighteen commits are classified in §18. Both bindings additionally build *and
   run* against their roadmap-named revision, but such a build never shipped and is treated as
   buildability evidence only (`P0.1-benchmarks.md` §9).

   > **Correction.** Earlier drafts recorded PLDI's direction as "the oracle is newer than the pin",
   > reasoning from author dates. `df8d30a3` carries a **stale author date** (2022-03-14) because it
   > was rebased; topologically it is the *tip*, nine commits after `4d4e516c`. Order MMTk revisions
   > with `git merge-base`, never by date.

7. **PLDI's implementation is not a runnable oracle.** It trips `assert!(old.is_null() ||
   rc::count(old) != 0)` in the write barrier under sustained load and segfaults in release builds
   (§3.4, `P0.1-benchmarks.md` §7). `[verified]` Every PLDI-selecting recommendation in §1 therefore
   selects PLDI as a *statement of the algorithm*, never as something a port can be differentially
   tested against.

## 18. The two nine-commit skew ranges, classified

Neither roadmap-named revision is what its binding builds (§0, and `P0.1-reference-build.md` §2).
This section classifies all eighteen commits, because "the delta is small" is not a finding — the

### 18.1 PLDI: `4d4e516c` (named) → `df8d30a3` (oracle), 9 commits

Aggregate: 6 files, +65/−78. `[verified]` by `git show` on each commit.

| # | commit | subject | files | class | effect in a `--features lxr` build |
|---|---|---|---|---|---|
| 1 | `9c7a2b78` | copy counter | `lib.rs`, `util/rc.rs` | instrumentation | counters only |
| 2 | `7a3e0b72` | reclaim blocks counters | `lib.rs`, `immixspace.rs` | instrumentation | counters only |
| 3 | `c1e0172d` | mature copy counter | `lib.rs`, `immixspace.rs` | instrumentation | counters only |
| 4 | `0bfba649` | log_pause_time | `lib.rs` (−74), `memory_manager.rs` | **observability removed** | deletes a pause-time logging path |
| 5 | `014368ef` | **Fix stw LXR** | `args.rs`, `util/rc.rs` | **semantic, non-LXR paths** | none — see below |
| 6 | `38d2b7c9` | fix | `util/rc.rs` | typo fix for #5 | none |
| 7 | `518e9bc2` | **fix stw lxr again…** | `util/rc.rs` | **semantic, non-LXR paths** | none — see below |

| 9 | `df8d30a3` | **rc_bits** | `Cargo.toml`, `util/rc.rs` | **parameterization, default preserved** | none — see below |

**Why the three semantic commits are inert in the LXR configuration.** `[verified]` — three
independent ways: source expansion, the runtime banner, and identical benchmark outcomes.

*`014368ef` "Fix stw LXR"* changes a hardcoded constant into a feature test:

```rust
-pub const LAZY_MU_REUSE_BLOCK_SWEEPING: bool = true;                        // 4d4e516c
+pub const LAZY_MU_REUSE_BLOCK_SWEEPING: bool = cfg!(feature = "lxr_lazy");  // df8d30a3
```

This looks like a `true → false` flip, and would be one — except that `lxr` *implies* `lxr_lazy`:

```toml
lxr_lazy = ["lxr_basic", "lxr_lazy_decrements"]
lxr      = ["lxr_basic", "lxr_cm", "lxr_lazy", "lxr_evac"]
```

So in a `--features lxr` build the constant is `true` on **both** revisions. The runtime banner
confirms it independently: `* lazy_mu_reuse_block_sweeping: true` in the shipped-pair build. The
commit's real target is the **stop-the-world LXR variants** (`lxr_basic` and friends *without*
`lxr_lazy`) — which is exactly what "stw LXR" names, and which the .NET port does not use.

*`518e9bc2`/`c2657a63`* likewise gate `max_copy` on `!cfg!(feature = "lxr")`; with `lxr` on, the
`else` branch yields `*crate::args::MAX_COPY_SIZE` — byte-identical to `4d4e516c`'s unconditional
value.

*`df8d30a3` "rc_bits"* makes the RC field width selectable while **preserving the default**:

```rust
pub const LOG_REF_COUNT_BITS: usize = {
    if cfg!(feature = "lxr_rc_bits_2") { 1 }
    else if cfg!(feature = "lxr_rc_bits_4") { 2 }
    else if cfg!(feature = "lxr_rc_bits_8") { 3 }
    else { 1 }                       // <- default, == 4d4e516c's hardcoded 1
};
```

No `lxr_rc_bits_*` feature is set by `lxr`, so `LOG_REF_COUNT_BITS == 1` on both revisions:
`REF_COUNT_BITS == 2`, `MAX_REF_COUNT == 3`.

**Conclusion for PLDI.** In the `--features lxr,immix` configuration this step builds, `4d4e516c`
and `df8d30a3` are **behaviourally equivalent**; the only user-visible difference is that the oracle
has *less* pause-time logging (#4). This is corroborated empirically, not just by reading: the two
configurations produce an **identical DaCapo pass/fail pattern**, including identical failures
(`P0.1-benchmarks.md` §9).

> This supersedes an earlier claim in this project that "the PLDI delta is benign." That claim was
> right by accident and unsupported at the time. The supported statement is narrower and more
> useful: *the delta is inert **in the LXR feature configuration**, having been classified commit by
> commit; three commits are genuinely semantic but act only on non-LXR paths.*

**But `rc_bits` still matters to the port, as a design fact rather than a delta.** `[verified]`
It establishes that the reference treats **RC field width as a designed tunable** (2, 4 or 8 counts
= 1, 2 or 3 log-bits), with **2 bits the default**. A .NET port must therefore parameterize RC width
rather than hardcode it, and must reproduce the stuck-at-`MAX_REF_COUNT` semantics that a 2-bit
field forces. P0.3 should carry this as an RC-table ledger row.

transitions. Any §5, §10 or §12 claim in this document that rests on `src/plan/lxr/` file structure
or on the upstream concurrent-marking interface is describing the **named** revision, not the
oracle.

### 18.3 Consequences for observability

| mechanism area | on the PLDI side | on the HEAD side |
|---|---|---|
| RC semantics (§3), barrier (§4), block/line (§9), args (§14) | `[obs-oracle]` — the range is inert, so oracle and named revision behave alike | `[obs-oracle]` |
| Concurrent marking substrate (§5), work buckets (§12) | `[obs-oracle]` | **`[obs-override]`** — the upstream-interface switch (`50cc7ff8`) and concurrent plan (`0a11e2c0`) exist only in the skew range |
| `plan/lxr` structure, block allocation via `ImmixHooks` (§10) | n/a — no `plan/lxr` at PLDI | **`[obs-override]`** — relocation commits 1–3 |

**Correction to a stricter reading.** These HEAD-side mechanisms were initially expected to be
`[read-only]`. They are not: the path-override build of `9625c174` compiled, linked and **ran the
full DaCapo suite 8/8** (`P0.1-benchmarks.md` §9). So they have been *observed executing* — just
never in a configuration that shipped. `[obs-override]` is the honest middle category, and it is
stronger than reading source while remaining unusable as a parity baseline.

Nothing in this document is `[read-only]` by virtue of being unbuildable. The genuinely
never-executed claims are the `[inferred]` items in §16.
