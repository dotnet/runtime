# P3.4 - Lazy sweeping completion counters

P3.4 adds generation-scoped RAII completion ownership to the P3.1/P3.3 work-packet scheduler. An
overall counter owns every lazy packet and its mature-sweep continuation. A decrement sub-counter
owns only decrement-class work. Decrement zero schedules mature sweeping exactly once; overall zero
publishes the next-GC decision result exactly once.

This remains opt-in collector substrate. It does not implement an LXR collector, reference-count
updates, object scanning, mature sweeping policy, finalization policy, trigger prediction, or an
EE/JIT/public contract.

## Paper requirement

The paper is Zhao, Blackburn, and McKinley, *Low-Latency, High-Throughput Garbage Collection
(Extended Version)*, arXiv:2210.17175, 1 Nov 2022.

- Section 3.2.1, PDF pp.5-6 requires all increments before decrements, recursive child decrements,
  and unfinished lazy decrements to finish before a later epoch proceeds.
- "Optimization: Lazy Reclamation", PDF p.7 schedules mature sweeping only after all decrements.
- Section 3.5, PDF p.9 requires parallel decrement work and work stealing.
- Table 7, PDF p.13 reports unfinished lazy work for xalan (22%), lusearch (5%), and avrora (1%).
  These characterize the paper implementation; they are not thresholds for this scheduler substrate.

Table 1, PDF p.2 shows LXR pauses longer than G1 while application query latency is better. The
benchmark below therefore characterizes completion/backlog cost and makes no collector pause-win
claim.

## Embedded generation lifetime

Each of P3.3's two physical deferred queue sets embeds one
`LxrLazyCompletionGenerationState`. There is no `shared_ptr`, independently allocated control
block, or completion-state allocation. A move-only registration stores a non-owning state pointer,
the captured generation tag, work kind, and active bit.

The scheduler is the lifetime owner:

1. submissions can attach registrations only to scheduler-owned packets;
2. queued packets are returned and completed during shutdown;
3. executing callbacks finish before worker join;
4. the scheduler implementation, which contains both states, is deleted only after all workers join;
5. a state may be reset only with zero overall/decrement counts and a terminal callback result.

Every operation compares the captured generation with the embedded state's tag. Stale explicit use
returns `StaleGeneration`; an impossible stale destructor records an ownership violation without
mutating the retagged counters.

P3.3's direction reversal supplies the reuse proof. Before a formerly active side becomes the next
producer, its queue and worker ownership are drained, its overall callback is terminal, and its
cycle has reset. Only then is the old tag cleared and the new seed installed.

## Registration and zero ordering

All counter, generation, lifecycle, callback-result, cancellation, and snapshot operations are
sequentially consistent, matching the oracle.

- A decrement registration increments decrement first and overall second.
- Overflow is rejected before wrap. If overall registration fails, the decrement increment rolls
  back while the active parent prevents a zero transition.
- Completion decrements the decrement counter first.
- The unique `previous == 1` decrement transition creates an overall-counted
  `LxrMatureSweepContinuation` and invokes the sweep callback.
- Sweep registrations cannot register decrement children and are the only registrations that can
  create an `LxrBlockReleaseGuard`.
- The completing decrement releases its own overall count only after sweep scheduling returns.
- The unique `previous == 1` overall transition invokes the next-GC result callback.

The prior-value transitions, not ad hoc callback booleans, establish exactly-once execution.
Lifecycle and callback-result enums record recovery and state reuse eligibility.

## Scheduler integration

Tracked deferred roots bind to P3.3's producer side and generation. Final-stage sealing closes that
root capability and prepares the old drained active side as the next producer. Resume remains an
explicit operation. Publication installs the sealed side and transfers its queue cardinality into
P3.1 accounting under the scheduler lock, then releases the generation seed outside the lock.

Packet callbacks execute outside the scheduler lock. Their RAII registration completes before the
worker reacquires the lock for packet state and bucket accounting. A decrement packet can register
recursive child work while its own registration is still active. Zero callbacks may synchronously
query or submit to the scheduler, proving they do not run under an internal lock.

`ResetCompletedCycle` additionally requires a drained completion state and successful overall
callback. It returns `Busy` while lazy/sweep work remains and fails explicitly on callback failure.

## Finalizable promotion and block release

P7 owns finalization semantics and has no runnable paper oracle. P3.4 supplies ordering only:
future promotion work that can protect or create referents registers as decrement-class work. The
decrement-zero transition cannot occur until promotion and its children complete.

The validation uses synthetic promotion and release. Release is denied before decrement zero and
allowed only inside a mature-sweep packet with a generation-bound release guard. The later real
mature sweeper must require this same capability when it calls P2.2 block release; P3.4 does not
pretend to implement mature sweeping.

## Next-GC seam

The overall-zero callback records only success/failure and generation. It does not name a pause
kind or predict a trigger. A later P3.2 coordinator may provide a callback whose context owns its
pause-kind result, while P8 owns the prediction. A stale, failed, or incomplete generation never
returns a default decision.

## Shutdown and failure

Shutdown marks completion states cancelling and the scheduler shutting down under the lock. It
returns queued producer, sealed, active, global, and local packets exactly once, releases detached
registrations after unlocking, lets executing callbacks finish, joins every worker, verifies zero
counts and no running callback, and only then destroys the embedded states.

Cancellation suppresses unclaimed zero callbacks and never authorizes release or reports a
successful next decision. An already claimed callback may finish; follow-up submissions observe
shutdown. A decrement callback failure suppresses release and overall decision. An overall callback
failure prevents reset.

## Integration boundary

The implementation is compiled only with
`CLR_CMAKE_ENABLE_LXR_LAZY_COMPLETION_COUNTER_TEST=1`. This defines
`LXR_ENABLE_LAZY_COMPLETION_COUNTER` for the internal packet/scheduler extension and exposes only
`GC_LxrCompletionCounterTest_Run`.

Normal Workstation/Server builds contain no completion state, packet field, source object, branch,
callback, export, or configuration read. No dependency or runtime contract changes are made.

## Validation

The direct Windows and Linux validators cover:

- overall/decrement registration and completion balance;
- move-only RAII, double completion, overflow, and rollback;
- one-shot decrement-zero and overall-zero callbacks;
- sweep-before-decision ordering when both counters would otherwise reach zero together;
- release denial before decrement zero and typed release eligibility afterward;
- recursive child registration before parent completion;
- synthetic finalizable promotion before release;
- callbacks re-entering scheduler queries outside locks;
- stale generation and alternating embedded-state reuse;
- tracked P3.3 sealing/resume/publication/drain;
- callback failure propagation;
- disabled mode and producer-side shutdown ownership.

The clean-archive gate demonstrates a failing perturbation for each invariant, source/evidence
identity, and benchmark sensitivity.

## Benchmark

The native benchmark uses persistent workers, 32 preallocated 1024-reference packets, worker counts
1/2/4/8/16, and controlled decrement backlog depths 0/1/4/16/32. An arrival counter allows exactly
`32 - depth` callbacks to complete; the remaining work is released at the synthetic next-pause
request.

It publishes:

- concurrent backlog-drain/decision-wait cost;
- the next empty synthetic STW interval;
- their combined subsequent-pause-request cost;
- exact observed backlog and callback/ownership totals.

Policies are tracked base, untracked same-code, tracked null, tracked injected-cost, and adjacent
alternating tracked A/A. Launch, depth, and policy orders are interleaved. All failed/excluded rows
are retained. These are scheduler/substrate measurements, not LXR-versus-Workstation/Server or
paper-parity results.

were timer dominated; the frozen control uses depth 32 and eight measured cycles. A combined
Windows build initially accepted all four CMake definitions as the value of the first definition;
the final build uses four separate `-cmakeargs` values and verifies all six linked/standalone P3.1,
