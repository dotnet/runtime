# P1.5 - GC-side object reference enumeration

P1.5 adds a generic CoreCLR GC contract for enumerating object reference slots
without a per-object EE layout callback. The implementation is collector-neutral:
it exposes addresses and ranges, not tracing, reference counting, marking, or LXR
policy.

The implementation was developed from `kkokosa/runtime:lxr` commit
`74552e7de38ff2047f3d1b8a62ff03bb6f7c8067`. That commit contains the final P1.1
dependency and the P1.2-P1.4 contracts through GC interface 5.13.

## 1. The gap

CoreCLR already has the information required to scan ordinary object fields:

- the GC-visible MethodTable prefix exposes base size, component size, the
  `ContainsGCPointers` flag, and collectibility;
- `CGCDesc`, `CGCDescSeries`, and `val_serie_item` describe the field layout;
- `go_through_object` decodes those descriptors in the built-in and standalone
  CoreCLR GC.

The pre-P1.5 gap was therefore narrower than "the current GC calls the EE for
every ordinary object." It did not. The gap was that the decoder existed only as
a control-flow macro tied to the current GC implementation. A different
standalone collector had no resumable range API and either duplicated that macro
or introduced a callback boundary.

There was one real per-object EE call in the existing scanner:
`go_through_object_cl` calls
`IGCToCLR::GetLoaderAllocatorObjectForGC(Object*)` for every collectible object.
That MethodTable-to-LoaderAllocator keep-alive edge is not an in-object field.
The existing scanner reports it through a temporary local, and the handle table
owns relocation of the real handle slot.

P1.5 addresses both facts without conflating them:

1. `gcref.h` supplies inlinable range iteration over real in-object fields.
2. Interface 5.14 negotiates a resolver for the stable LoaderAllocator handle
   slot, allowing a collector to resolve it once per distinct collectible
   MethodTable and cache it for the collection.

The handle slot never enters the writable in-object range stream. Tracing and RC
consumers load its value; relocation remains solely owned by the handle table.

HEAD is chosen because the typed slot interface is the portable boundary used by

for the RC/SATB algorithm. The PLDI zero-RC assertion at
`df8d30a3:src/plan/barriers.rs:315-319` is compiled only for sanity/debug builds

`304ce69d:src/util/sanity/sanity_checker.rs:311-316` is behind non-default sanity
and was absent from the clean measured binary. Neither assertion is used as slot
enumeration evidence.

CoreCLR deliberately differs from the OpenJDK binding:

- heap object fields are aligned full pointers in this contract;
- byrefs and interior pointers are root-scanning concerns, not CGCDesc fields;
- collectible liveness is a MethodTable metadata edge, not an object slot;
- CGCDesc positive/repeating series replace OpenJDK oop maps.

Compressed or tagged object references require a future negotiated slot encoding.
They must not be interpreted as 5.14 `Object**`.

## 3. Interface 5.14

The GC interface remains major 5 and advances from minor 13 to 14. The EE
interface remains major 4. Existing 5.9-5.13 constants, vtable slots, and data
tails retain their exact meaning and layout.

The 5.14 descriptor is:

```cpp
enum class ObjectReferenceEnumerationRequestStatus : uint32_t
{
    NotProcessed = 0,
    Accepted = 1,
    Unsupported = 2,
};

enum class ObjectReferenceEnumerationRequest : uint32_t
{
    Disabled = 0,
    Enabled = 1,
};

typedef Object** (LOCALGC_CALLCONV *GetLoaderAllocatorObjectSlot)(
    MethodTable* method_table);

struct ObjectReferenceEnumerationParameters
{
    ObjectReferenceEnumerationRequestStatus request_status;
    ObjectReferenceEnumerationRequest request;
    alignas(void*) GetLoaderAllocatorObjectSlot
        get_loader_allocator_object_slot;
};
```

The structure is 16 bytes on x64 and 12 bytes on x86. Zero initialization means
disabled, `NotProcessed`, and no resolver.

P1.5 appends one final IGCHeap method with a disabled implementation:

```cpp
virtual ObjectReferenceEnumerationParameters*
    GetObjectReferenceEnumerationParameters()
{
    static ObjectReferenceEnumerationParameters parameters = {};
    return &parameters;
}
```

An unchanged 5.13 collector source rebuilt with the 5.14 header therefore remains
concrete. The runtime calls the slot only for exact major 5, minor 14 or later.
It validates `NotProcessed`, a known request, and a null output resolver before
writing `Accepted` or `Unsupported`.

For an enabled request, CoreCLR supplies a `LOCALGC_CALLCONV` resolver that:

- returns null for a non-collectible MethodTable;
- returns the stable handle-table slot for a collectible MethodTable;
- does not allocate, throw, trigger GC, block, switch mode, or enter managed code.

The returned slot is read-only to this service. The collector may cache its
address while the MethodTable is valid and load the current value. It must never
relocate or store through that slot.

NativeAOT accepts the same descriptor and supplies a resolver that returns null:
its MethodTable contract has no collectible types.

No IGCToCLR slot, MethodTable field, CGCDesc encoding, JIT-EE API, helper ID,
WriteBarrierParameters field, or DAC descriptor is added.

## 5. In-object range API

`src/coreclr/gc/gcref.h` exposes two forms over the same semantics:

```cpp
struct GCReferenceRange
{
    Object** start;
    size_t count;
};

class GCReferenceRanges
{
public:
    template <typename TVisitor>
    static bool Enumerate(Object* object, TVisitor&& visitor);
};

class GCReferenceRangeIterator
{
public:
    explicit GCReferenceRangeIterator(Object* object);
    bool Next(GCReferenceRange* range);
};
```

The visitor form is the hot full-object path. It inlines the descriptor walk and
calls the consumer once per contiguous range. The cursor form preserves state for
streaming consumers that must resume between ranges.

Both forms:

- return real in-object `Object**` ranges in ascending slot-address order;
- include fields whose current value is null;
- do not load values;
- allocate nothing and call no EE service;
- return no collectible handle slot;
- are excluded from `DACCESS_COMPILE`.

Both enumeration forms use one shared helper that receives the already masked
MethodTable, returns immediately for pointer-free types, and computes:

```text
base size + (component count * component size)
```

The helper uses the GC representation cast to read array length and asserts that
the multiplication fits in `size_t`. It does not call either runtime flavor's
`Object::GetSize()`, so a GC mark bit in the raw MethodTable slot cannot reach
NativeAOT's unmasked out-of-line implementation.

## 6. Layout algorithm

### 6.1 Positive series

A positive series count describes ordinary and inherited objects, boxes,
explicit/sequential layouts, flattened embedded value types, all-reference
objects, and reference arrays.

MethodTable construction sorts descriptor storage by descending offset. Walking
from `GetHighestSeries()` toward `GetLowestSeries()` therefore emits ascending
object addresses, matching `go_through_object`.

For each series:

```text
start = object + series.startoffset
bytes = series.seriessize + objectSize
count = bytes / sizeof(Object*)
```

The addition uses intentional unsigned modular arithmetic. Builders store
`actualSeriesBytes - baseSize`; reference arrays store a negative bias. Adding
the current object size reconstructs the actual run length.

An empty reference array produces no range. An all-reference array produces one
range over its elements.

Inheritance, generics, canonical sharing, nested value types, and explicit or
sequential layout need no branch in P1.5: MethodTable construction has already
flattened and adjusted the descriptor. Runtime parity tests exercise the actual
MethodTables.

### 6.2 Negative/repeating series

A negative count has one current meaning: an array of value types containing
references.

The absolute count is the number of pointer runs per element. The descriptor
provides:

- the first pointer-run offset;
- `nptrs` for each contiguous run;
- `skip` from the end of that run to the next run.

P1.5 iterates the immutable component count. Each item emits `nptrs` slots and
advances by `nptrs * sizeof(Object*) + skip`. The final skip advances to the first
run in the next element. A zero-length array reads no element data.

No new negative-series encoding is introduced.

### 6.3 Bounds and object kinds

Checked builds assert pointer alignment, nonzero descriptor series, monotonic
positive ranges, and that every emitted range ends within:

```text
object + objectSize - sizeof(ObjHeader)
```

Array allocation already checks length multiplication. Value-type array
`nptrs`/`skip` values are bounded by the existing half-word limits.

Strings, primitive arrays, and no-reference objects produce no ranges. Boxes use
their boxed MethodTable descriptor. A missing nullable box has no object.
SZ/MD/jagged reference arrays use the same positive data series; MD bounds and
lower bounds are outside it. LOH, POH, and frozen placement do not change the
descriptor. Free objects, fillers, gaps, and unpublished allocation memory are
invalid inputs.

## 7. Concurrency and lifecycle

The API describes layout, not a value snapshot.

- The object and MethodTable must be valid and fully initialized.
- A cursor or range cannot survive object relocation or MethodTable unload.
- Concurrent consumers must use their write-barrier/SATB protocol when values can
  mutate.
- In-object slots may be updated only by the relocation phase that owns them.
- The collectible handle slot is value-only for this service and remains under
  handle-table relocation.
- A per-type collectible cache must be preallocated or otherwise avoid allocation
  during scanning, and must be cleared at collection/unload boundaries.
- P1.4 payloads marked `PayloadMayBeUninitialized` are not safe value inputs until
  their reference contents are initialized.

## 9. Performance evidence

### 9.1 Native layout microbenchmark

The BenchmarkDotNet test scans 2,048 persistent objects per operation and returns
a checksum after loading the referenced MethodTable to prevent dead-code removal.
It is a layout-decoding microbenchmark, not execution of the harness's named
`pointer-chasing` scenario. It compares:

- a noinline callback per slot;
- the resumable range cursor;
- the fully inlined range visitor.

Each cell has 24 raw workload samples (three launches, eight iterations). The
benchmark allocates no managed memory in the measured operation.

| shape | callback | cursor | visitor | visitor/callback |
|---|---:|---:|---:|---:|
| sparse object, three singleton runs | 11.75 us | 15.22 us | 10.55 us | 0.90x |
| dense 256-reference array | 765.17 us | 476.27 us | 400.70 us | 0.52x |
| 32-element repeated mixed layout | 258.08 us | 243.25 us | 195.76 us | 0.76x |

The cursor's 1.30x sparse result is retained rather than hidden: resumable state
costs more than a callback when every range is one slot. The visitor is the hot
path and removes that regression while preserving the cursor for consumers that
need resumability.

`P1.5/raw/benchmark-invocations.csv` contains 216 raw samples.
`benchmark-summary.csv` and `benchmark-identities.csv` are derived from the same
run.

This is a native layout microbenchmark on a Hyper-V Windows host. It is not an
application-latency claim. The paper remains context only: the cited source is the
arXiv Extended Version, arXiv:2210.17175, dated 1 Nov 2022. Its 1.6% barrier
geomean is against no-barrier Immix, not a P1.5 threshold. Its G1 throughput and
LXR-only pause tables do not define a CoreCLR comparative p95 target.

### 9.2 Integrated scenario scan consumer

A separate validation-only consumer executes inside the real
`go_through_object_cl` path. For each pointer-bearing object the collector is
about to scan, the hook performs one shadow scan and then leaves the existing GC
scan authoritative for liveness and relocation. The hook is available in both
the linked and standalone CoreCLR GC builds only when
`CLR_CMAKE_ENABLE_OBJECT_REFERENCE_ENUMERATION_TEST` is enabled. The normal build
does not compile the source or the branch.

The three paired arms differ only in enumeration:

- `callback` independently walks the positive or repeating `CGCDesc` layout and
  invokes a noinline callback for every slot;
- `visitor` calls `GCReferenceRanges::Enumerate` and consumes every returned
  slot;
- `cursor` advances `GCReferenceRangeIterator` and consumes every returned slot.

All arms load the same slots, count null and non-null values, and update the same
checksum. Per-thread, cache-line-sized counters avoid a process-wide atomic
increment for every scanned object. Reset first latches the requested native
mode. Stop disables new observations and drains active scan threads before the
managed probe snapshots the counters. A deliberate requested/observed mode
mismatch exits 1 and is the executable negative control.

Scenario setup and two forced full collections complete before telemetry and
counter reset. Counters remain active from that reset until immediately after
telemetry ends, covering the 0.5-second warmup, the 3-second steady state, and
only the small harness boundary around them. Setup promotion is excluded.
Therefore, the reported object/range/slot counts are actual GC scan events during
the scenario window, not unique objects. Every measured invocation had at least
one natural Gen0 collection. `long-lived-cache` has exactly zero induced
collections. `pointer-chasing` has exactly two blocking, noncompacting full
collections, scheduled at evenly spaced steady-state targets. This is necessary
because its setup graph is promoted before reset: allocation-only Gen0
collections do not scan that graph. The runner rejects any induced count other
than two, requires at least two observed Gen2 collections, and still applies a
fixed 1,024 bytes of natural allocation pressure per operation.
For every pointer-chasing invocation, the verifier also requires at least 131,072
object scans and 262,144 non-null slots: two scans of the 65,536-node graph and
its two non-null reference fields per node.

## 11. Unused-path cost

P1.5 does not rewrite `go_through_object` or any built-in mark, background-mark,
or relocation loop. `gcref.h` is header-only and emits code only for a consumer.
The real-layout parity call is Debug-only and reached only from the profiler
diagnostic walk. The scenario observer is separately compile-time gated; in a
normal runtime its scanner macro expands to nothing.

The normal configuration adds no object-scan branch, callback, MethodTable field,
cache, allocation, JIT helper, or write-barrier change. A test-enabled build has
one inline disabled-mode check before entering the scenario observer. Interface
5.14 adds one cold startup negotiation and one vtable tail, as required for
source/binary-safe capability discovery; no byte-identical whole-runtime claim is
made for that cold contract code.
