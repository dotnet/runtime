# P2.5 - Large object space

P2.5 adds a default-off CoreCLR GC substrate for complete object sizes at or above 32 KiB. It owns
its address space, physical commitment, metadata, and release independently from Immix blocks. It
does not select an LXR collector, route normal CoreCLR allocations, or change CoreCLR's built-in
large object heap.

## Dependency and oracle

The dependency is merged P2.2 commit
`17ac93d30d5ebc08aeda0ddf24e562d506d72230`. P2.3 and P2.4 are not imported.

The coupled LOS mechanics oracle is binding
`0682434ae725787e38defbc17bd66dc918e4bdb7` with core
`304ce69d43aae87de501111fceb8cbd33173a03a`. HEAD supplies the live
`LargeObjectSpace`, `FreeListPageResource`, combined mark/nursery metadata, page-reuse count, and
independent release. PLDI defaults its Immix maximum to half a block and is not the threshold
oracle.

The roadmap's initial `304ce69d:src/plan/lxr/mod.rs:11-19` span exists and is live, but contains
plan exports and the cycle trigger, not LOS behavior. The operative policy is
`304ce69d:src/policy/largeobjectspace.rs`.

## Inclusive threshold correction

`304ce69d:src/policy/immix/mod.rs:12-20` defines `MAX_IMMIX_OBJECT_SIZE` as one 32 KiB block, and
`src/plan/lxr/global.rs:96-104` publishes it as the maximum non-LOS default allocation size.

The binding is inconsistent at equality. Runtime/slow and variable-size JIT paths use `>=` at
`0682434:openjdk/mmtkMutator.cpp:25-30`, `openjdk/mmtkHeap.cpp:587-592`,
`openjdk/mmtkBarrierSetAssembler_x86.cpp:68-71`, and
`openjdk/mmtkBarrierSetC2.cpp:100-110`. Constant-folded paths use `>` at
`openjdk/mmtkBarrierSetAssembler_x86.cpp:62-65` and
`openjdk/mmtkBarrierSetC2.cpp:91-98`.

P2.5 records a coordinator-approved correction: every complete object size greater than or equal to
32,768 bytes belongs to LOS. Placement must not depend on constant folding. The size includes the VM
object header and object padding; alignment and page padding do not alter classification.

## Geometry, ownership, and zeroing

The represented address range is `[0, 2^47)`. Pages are 4 KiB, matching
`LargeObjectPageReuse`. Initialization fails explicitly on 32-bit targets or a different host page
size.

One `LxrLargeObjectSpace` reserves one inaccessible contiguous arena. An address-ordered first-fit
free list splits spans and coalesces adjacent releases. A space-wide atomic gate serializes page
resource and lifecycle mutation. Each allocation has a nonzero opaque owner.

Allocation validates arithmetic before mutation, commits exact pages, zeroes the complete span,
resets stale metadata, updates page reuse during concurrent marking, and publishes valid-object
state last. Release is collector-only, decommits the exact span, and returns it without consulting
Immix state. Decommit failure leaves the allocation active; a later metadata failure quarantines the
already decommitted span until shutdown.

Promotion rounds only the `FieldUnlogged` metadata reset coverage to its eight-byte granularity.
Checked arithmetic requires that rounded metadata end to stay inside the object's committed page
span. The logical object size and release span remain unchanged.

## Metadata and phases

`LargeObjectMarkNursery` is a two-bit local value per eight represented bytes: bit 0 is current mark
state and bit 1 is nursery/young. Fresh allocation publishes current mark plus nursery.
Mark-and-promote initializes field-unlogged metadata and clears nursery atomically. Allocation and
release reset the existing parameterized RC plane without choosing its width.

`LargeObjectPageReuse` remains eight bits per 4 KiB page. Allocation during concurrent marking
increments every page sequentially consistently and wraps `255 -> 0`. Release preserves reuse
history while clearing all other object and slot metadata.

The local states are ownership restrictions, not the P3 scheduler: `Mutator` allows allocation,
`ConcurrentMark` allows allocation/mark/reuse recording, `Release` allows promotion/release, and
`Shutdown` allows no operations. P2.5 does not decide liveness, process RC work, enqueue SATB work,
sweep generations, or evacuate.

## Default-off and platform boundary

`CLR_CMAKE_ENABLE_LARGE_OBJECT_SPACE_TEST` defaults off. Only validation builds compile the product
source and smoke export. Normal Workstation/Server allocation has no P2.5 branch, call, object, or
export.

Direct validation executes on Windows/Linux x64 and fails closed on Windows x86 before reservation.
Windows ARM64 is build-only unless execution is recorded. Mono, NativeAOT, and WASM are not reached.
The existing harness `large-object-pressure` scenario characterizes built-in Workstation/Server GC
only; it is not LXR integration evidence.

## Evidence topology

All non-raw inputs freeze in one source commit. Exactly one direct child adds only `P2.5/raw/`.
The final gate checks identities against a committed archive, requires direct ancestry, runs clean
and perturbed copies, and removes its exact scratch mapping. Any later non-raw edit invalidates the
pair.
