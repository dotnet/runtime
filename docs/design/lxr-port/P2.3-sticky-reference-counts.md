# P2.3 - Sticky reference counts and straddle metadata

P2.3 adds the collector-internal sticky reference-count plane and the line
straddle sentinel that a later RC collector needs. It adds no collector, no
allocator, no sweep, and no public or runtime contract.

## Dependency and source identity

P2.3 depends on two merged squashes, not on the pre-merge branches:

| dependency | commit |
|---|---|
| P2.1 side-metadata framework | `8866eee4907667c93752cc4411bcdd838b98fec5` |
| P2.2 Immix block and line state | `17ac93d30d5ebc08aeda0ddf24e562d506d72230` |

P2.3 reuses P2.1's fixed-address layout, ownership checks, demand commitment,
and masked atomic word operations, and P2.2's block/line geometry and
lifecycle. It adds no third metadata table and no shadow copy of either.

The binding-pinned reference pairs are:

|---|---|---|---|

## Paper context

The local paper is Zhao, Blackburn, and McKinley, *Low-Latency,
High-Throughput Garbage Collection (Extended Version)*, arXiv:2210.17175,
dated 1 November 2022. It is the extended arXiv version, not the conference
version, and every reference below is to that PDF.

Qualifications that must travel with any P2.3 performance statement:

- Table 7 reports p50 and p95 pause percentiles for LXR only. It contains no
  comparison collector, so it cannot be used as a relative pause claim.
- Table 1 shows LXR taking *longer* GC pauses than G1 while delivering better
  application query latency. The pause number alone is not the result.
- Table 5 reports LXR/G1 throughput ratios of 0.97, 0.96, and 1.01 at 1.3x,
  2x, and 6x minimum heap. LXR is not uniformly faster.
- The paper's barrier cost is a 1.6% geometric mean against a *no-barrier*
  full-heap Immix baseline, which is within roughly +/-3% run-to-run noise on
  that platform. It is a small-cost claim, not a free-barrier claim.
- The paper's configuration disabled class unloading, compressed pointers, and
  weak references. CoreCLR supports all three, so no paper number is a CoreCLR
  acceptance threshold and none is used as one here.

None of these values is a P2.3 microbenchmark bound. The P2.3 bounds are the
injected-cost controls described under "Validation and performance evidence".

## Widths and sticky arithmetic

`ReferenceCountTable` derives a log-width selector of 1, 2, or 3 from the
validated P2.1 layout, so all three active widths are implemented now:

| log selector | active bits | maximum count |
|---:|---:|---:|
| 1 | 2 | 3 |
| 2 | 4 | 15 |
| 3 | 8 | 255 |

The default is the 2-bit width. The maximum for a width is `(1 << bits) - 1`
and is the sticky value. The rules are:

- an object at the sticky maximum cannot be incremented and cannot be
  decremented;
- an object at zero cannot be decremented;
- every operation returns the previous count, and reports `Updated`,
  `Saturated`, or `Zero` so a caller can distinguish a real update from a
  refused one;
- updates use a relaxed masked compare-exchange on the enclosing native word,
  so neighbouring counts packed in the same word are preserved.

Relaxed ordering is sufficient because P2.3 publishes no data through the
count. Registration writes retain P2.1's sequentially consistent contract;
hot-path validity checks are relaxed because the caller's object-lifetime and
quiescence protocol, not the marker read, provides publication.

Increment and decrement apply the saturating transitions. `Load` reads any
in-width value, while `CompareExchange` can seed or transfer any in-width
value except that a sticky-maximum comparand cannot be replaced by a lower
value.

## Object starts and the exact address lattice

An address accepted by P2.3 must be all of:

- 8-byte aligned (`sizeof(uintptr_t)` on the 64-bit-only layout);
- owned by a committed P2.1 data range;
- registered in the P2.1 `ValidObject` plane as an exact object start.

An interior pointer or a byref is *rejected*, not normalized. There is no
"find the containing object" step in P2.3: a request that does not name an
exact registered start returns `AddressNotOwned` (unregistered or interior)
or `InvalidArgument` (misaligned). Interior normalization belongs to a later
phase together with allocator metadata; introducing it here would make the
lattice ambiguous.

Registration is explicit. `InitializeObjectQuiescent` records an RC-zero
nursery object but deliberately does not mark straddles: the reference creates
those sentinels on the first zero-to-one promotion, which P4.2 will own. The
P2.3 test consumer synthetically registers
object starts through `InitializeObjectQuiescent` because P2.4 has not yet
supplied real allocation. When P2.4 lands, the allocator becomes the
registering owner and the synthetic path disappears from the product.

P2.3 cannot prove that two registrations do not overlap because it has no
object-extent map before P2.4. Non-overlap is therefore an explicit allocator
precondition; the synthetic consumer uses disjoint extents.

CoreCLR's 24-byte minimum object size is enforced for range operations. That
minimum changes the achievable *density* of live starts and therefore which
counts can alias inside one native word; it does not change the 8-byte
lattice, the sticky semantics, or the metadata reserved per represented heap
byte, all of which are derived from the 8-byte granularity alone.

## Straddle marking

Straddle metadata answers one question: "is this line the continuation of an
object that started in an earlier line?" For an object with start `S`, size
`N`, and end `E = S + N`, P2.3 marks continuation lines only when
`N > 256`, and then marks exactly the half-open range

```text
[align_down(S, 256) + 256, align_down(E, 256))
```

Consequences that the implementation and the validator both pin:

- the object's own first line is never marked, because the object starts in
  it;
- a partial tail line is never marked, because `align_down(E, 256)` truncates
  it;
- an exact line boundary end includes that final full line, because the range
  is half-open;
- an object of exactly 257 bytes starting at a line boundary has *no*
  continuation line;
- an object may straddle lines but may never cross a 32 KiB block, and a
  range that would cross a block is rejected outright.

Partial-tail safety depends on a rule that P2.3 does not implement: the
deferred P2.4 oracle "skip the first dead line" behaviour, which prevents a
later allocator from handing out the unmarked partial tail of a dead object.
P2.3 implements no allocator, no hole discovery, and no sweep, so it records
that dependency rather than claiming to satisfy it.

## The sentinel pair

A continuation line is identified by a *pair* of metadata values, not by an
object header bit and not by line state alone:

| plane | address | value |
|---|---|---:|
| `ReferenceCount` | line start | 1 |
| `ReferenceCountStraddle` | line | 1 |

Both halves are required. A line with the straddle bit but no count of 1, or
with a count of 1 but no straddle bit, is reported as `InconsistentState`
rather than silently treated as a continuation or as a free line. The
`ValidObject` bit of a continuation line start must be zero: a continuation
line start is by construction not an object start.

Clearing is ordered: the reference count is cleared first, then the straddle
bit. That order means a concurrent reader can observe "straddle set, count
zero" - an explicitly inconsistent state that fails closed - but can never
observe the reverse, where a stale count of 1 with no straddle bit would be
indistinguishable from a real single-reference object.

Marking establishes the pair under quiescence or under the owner of the
object, after validating that the target lines are empty.

## Lifecycle

**Copy.** `CopyObjectQuiescent` transfers only the source object's own count
to the destination and then re-derives the destination's sentinels from the
destination address and size. It does not copy the source's continuation-line
sentinels, because those encode source addresses. The source and destination
ranges must not overlap.

**Release, reuse, and epoch wrap.** Returning a P2.2 block, reusing it, and
wrapping the P2.2 phase epoch all *retain* the reference counts and straddle
sentinels of the represented range. P2.3 deliberately does not clear metadata
on those transitions: death and reclamation are owned by later phases, and
clearing early would destroy the counts that a later decrement phase needs.

**Explicit quiescent reset.** `ResetObjectQuiescent` accepts an exact,
registered, 8-byte-aligned start, a size of at least 24 bytes, and a
single-block extent. The start need not be line-aligned. It clears the
object's own count, derives and clears its continuation sentinels, and revokes
its `ValidObject` registration. `ResetRangeQuiescent` and its block-aligned
wrapper clear all three planes - `ValidObject`, `ReferenceCount`, and
`ReferenceCountStraddle` - for a line-aligned range. All three operations are
explicitly quiescent.

P2.2 block return or owner reacquisition does not reclaim objects and never
licenses overlapping allocation. Before P2.4 may reuse an overlapping extent,
death/reclamation must dismantle the prior object's registration, own count,
and derived continuation sentinels. P2.3 models that operation with
`ResetObjectQuiescent`; later death logic owns the production call. New-object
initialization and copy fail closed when the proposed start lies in a marked
full continuation line, preventing either path from overwriting its RC
sentinel while leaving the straddle byte behind. Without a P2.4 extent map,
other forms of overlap remain an explicit allocator precondition.

## The mandatory invariant consumer

From the first commit, P2.3 carries the zero-count invariant consumer: a
reference that is being overwritten must not already have a zero count.

- At PLDI, `df8d30a3:src/plan/barriers.rs:315-319` performs this check, with
  the condition at line 316, inside `FieldLoggingBarrier::slow`, guarded by
  the crate's `sanity`/debug configuration.
- At HEAD there is no equivalent check in the barrier. The only surviving
  consumer is `304ce69d:src/util/sanity/sanity_checker.rs:311-316`, with the
  condition at line 312, and it runs only under the non-default sanity
  configuration.

P2.3 therefore does *not* claim that the HEAD default configuration validates
this invariant. The CoreCLR side keeps the consumer as a debug-only assertion
plus an explicit validator case, so that the invariant has a live executable
consumer even though the upstream default no longer does.

## Default runtime path and platform matrix

Product and smoke sources compile only when
`CLR_CMAKE_ENABLE_REFERENCE_COUNT_TEST=1`. The option is AMD64-gated and
defaults off; another target architecture fails configuration explicitly. The
test-enabled linked CoreCLR and the standalone GC export only
`GC_ReferenceCountTest_Run`. No normal Workstation or Server allocation or
collection path calls it. The default-path evidence checks the option default,
normal GC source call sites, dynamic exports, and demangled product symbols in
the required `.dbg` sidecars for both `libcoreclr` and `libclrgc`, proving that
a default build contains no P2.3 object, branch, call, or export. A stripped
binary without its symbol sidecar is rejected rather than treated as proof of
absence. Each sidecar's ELF build ID must match the binary it describes and is
recorded in the default-path summary. Failure to read either dynamic or full
symbols is an evidence failure, never proof of absence.

On Unix the P2.3 export is appended to the export set selected by the other
validation features, so a combined-feature build carries the P2.2, P1.3, and
P1.4 exports alongside it. Every symbol scan drains `nm` instead of stopping
at the first match: a scan that exits early makes `nm` die of `SIGPIPE`, and
under `pipefail` that reports a non-zero pipeline for a symbol that is
present - which would fail a real combined export and, worse, silently pass an
absence control against a default build that does export the symbol.

| platform | scope |
|---|---|
| windows-x64 | full build, 37/37 validation, 4/4 runtime smoke, benchmark |
| linux-x64 | full build, 37/37 validation, 4/4 runtime smoke, combined exports |
| windows-x86 | exact P2.3 translation units plus 1/1 explicit fail-closed check; the full runtime build is a separately recorded pre-existing `ResolveCacheElem` failure |
| windows-arm64 | exact-source product translation units, build only |

Windows x86 fails closed: the fixed 47-bit metadata reservation cannot exist
in a 32-bit address space, so the validator's single x86 case asserts the
explicit `UnsupportedAddressSpace` rejection instead of exercising counts.
ARM64 is build-only; no ARM64 execution result is claimed. Linux results come
from real WSL Unix execution of the product path, not from a Windows shim.

## Validation and performance evidence

`P2.3/reference-count-validation.cpp` compiles the product sources directly
against the P2.1 OS shim and enumerates 37 x64 cases covering: all three
widths and their layout mapping, every representable value at every width,
previous-count returns, sticky and zero refusal, sticky transition against a
late decrement, same-word neighbours at every width, separate cache lines,
synthetic registration, interior and byref rejection, the 24-byte minimum, the
47-bit upper boundary, endian location formulas, the full straddle range
table, block-end and cross-block behaviour, sentinel-pair corruption, straddle
clear and reset, mature copy, a disabled plane, block lifecycle retention
across 127 epoch cycles, the zero-count invariant consumer, and a deterministic
stale-word control that demonstrates the failure a masked CAS prevents.

`P2.3/run-reference-count-runtime-smoke.ps1` and its `.sh` peer execute the
exported smoke in linked and standalone Workstation/Server modes on both
platforms.

The native and BenchmarkDotNet harness characterizes 13 width-parameterized
methods across the three widths (39 rows) and 6 contention methods across 1,
4, and 16 workers (18 rows), for 57 rows total. The declared evidence run is
three launches, eight warmups, and twenty measured iterations. Each iteration
has exactly one invocation and one unrolled operation so an iteration setup
preseeds exactly one measured native batch; the native batch rejects a status
that does not match the benchmark label. Its three
controls, one per worker count, must satisfy:

| control | bound |
|---|---|
| A/A (`SameSlotContentionControl` / `SameSlotContention`) | within `[0.90, 1.10]` |
| extra CAS (`ExtraCasContention` / `SameSlotContention`) | at least 1.5x |
| injected delay (`DelayContention` / `SameSlotContention`) | at least 1.25x |

Absolute rates are characterization, not acceptance thresholds. No benchmark
number here is compared with a paper number.

`P2.3/run-reference-count-evidence.ps1` drives the whole set from explicit
paths, records the SHA-256 identity of all thirteen Windows and Linux runtime
binaries the evidence executed against, and copies the caller-supplied build,
platform, and attempt summaries in unchanged, because that matrix spans
machines, drives, and architectures the wrapper does not itself run. Its
required parameters are validated in the body rather than declared mandatory,
so an incomplete invocation fails with one explicit message instead of
prompting. Two negative controls travel with it:
`verify-reference-count-cross-cwd.ps1` re-runs the benchmark harness from a
working directory outside the repository, and
`run-incomplete-coreroot-control.ps1` points the first runtime harness at a
Core_Root missing a required file and passes only when that harness rejects it
before producing any output. The control deliberately invokes the runtime
smoke rather than the wrapper, because the wrapper invokes the control.

## Evidence topology and a recorded dependency limitation

P2.3 uses a single immutable source commit and then a direct evidence-only
child commit. If any file in `P2.3/source-manifest.txt` changes, the evidence
run restarts against a new source commit; the archive gate refuses a source
commit that is not the direct parent of the evidence commit, and refuses a
dirty worktree, index, or untracked file.

P2.1 and P2.2 recorded their evidence source commits as pre-squash branch
tips - `f8e7811546a37e0687d26755b709ab01bab213cf` and
`4c99e4d89e4d3d2b9783b997d4f1c1fce37970c5`. Those commits still exist and are
content-equal outside their `raw/` trees, but after the integration squashes
they are no longer ancestors of the integration branch. That is a historical
limitation of the P2.1 and P2.2 evidence, recorded here rather than repaired:
rewriting their recorded identities would invalidate the hashes they publish.
P2.3 avoids the same outcome by pinning its source commit only after the
source content is final.

P2.3 also necessarily changes seven paths that P2.2 recorded in its own source
identity set: the LXR README, four shared CMake files, `side_metadata.h`, and
the VM CMake list. Consequently P2.2's verifier no longer passes against the
P2.3 working tree even though its recorded source archive remains valid. P2.3
does not re-stamp P2.2's published identities; it records the cross-phase
effect here and verifies P2.3 from its own immutable source commit.

Raw evidence, exact source/runtime/machine identities, archive-gate results,
and the remaining limitations are recorded under `P2.3/raw/` only after the
immutable source commit exists. The standalone verifier audits its own
committed tree: it re-hashes every manifest path, requires the complete
manifest, requires every declared raw file and every column its declared
schema names, checks the recorded topology, and requires every expected
platform, build, runtime, export, benchmark, control, runtime-binary identity,
and invocation row. Every build row must name the same source commit, the
thirteen runtime-identity roles must all be present with a well-formed hash,
and the executed check count must equal the manifest's
`verifierExpectedChecks`, so a silently skipped section fails the run.

Git ancestry is checked directly when a `.git` directory is present and
through the recorded topology summary otherwise, because an extracted archive
intentionally has no `.git`. With `.git` present the verifier additionally
requires the source commit to exist, to be HEAD's distinct direct parent and
ancestor, and every source-manifest path to be byte-identical between the two
commits, so a source change smuggled into the evidence commit is refused even
when `raw/source-identities.csv` is restamped to match it.

One consequence is recorded rather than repaired: `raw/topology-summary.csv`
is itself part of the evidence commit, so it can never carry that commit's own
hash - stamping the hash rewrites the commit it names. HEAD identity is
therefore pinned by the four ancestry checks above, and the recorded
`evidence_commit` is refused whenever it names a *different* commit that
exists in the repository, which is the substitution the field exists to catch.

## Non-goals

P2.3 adds no public API, no normal WKS/SVR path, no runtime/EE/JIT contract,
and no collector selection. It touches neither Mono nor NativeAOT execution
nor WebAssembly. It does not implement P2.4 allocation, the P3 scheduler, P4
packets or sweep, P5 SATB, or P6 evacuation. A later phase may consume the
count plane and the straddle sentinels, but must not add a second reference
count or straddle representation.
