# P0.4 — Benchmark harness and scenario matrix

This document is the P0.4 deliverable. It specifies the ten scenarios and why each exists, the
measurement methodology and why it is what it is, every pinned knob and how it is verified, the seven
controls and the evidence each was shown to fire, how to run the harness, and how the LXR arm will be
added.

The harness itself lives in [`harness/`](harness/). It has zero package references, builds offline,
and runs on three hosts including a locally built runtime.

**Scope.** P0.4 builds and proves the harness. P0.5 collects baselines. Every number in this document
is smoke evidence — proof that the machinery works — and none of it is a baseline. §11 states exactly
what was deliberately not done.

---

## 1. The decision that shapes everything

P0.2 established that **application-observed latency is the acceptance signal, and pause distribution
is a characterization rather than a win condition.**

The paper's only comparative pause table is Table 1 (arXiv:2210.17175, extended version dated
1 Nov 2022, PDF page 2). In it, **LXR's GC pauses are longer than G1's at every percentile** while its
query latency is far better, under the caption *"Short GC pauses do not assure low latency."*
Table 7's p50/p95 figures are LXR-only; there is no p95-versus-G1 pause comparison anywhere in the
paper.

A harness organised around pause times would therefore measure the wrong thing. This one is organised
around an **open-loop, coordinated-omission-free application latency pipeline**, with pause data
collected as clearly labelled secondary characterization. The existing benchmark-result schema is
organised the other way — it is pause-centric and has no field for application latency at all — which
is why §10 proposes an extension.

Two further facts from P0.2 shape the design directly:

- **Throughput versus G1 is heap-dependent and inverts**: 0.97 at 1.3×, 0.96 at 2×, **1.01 at 6×**.
  LXR is *slower* at generous heaps. Heap size is therefore a first-class axis of the matrix, not a
  constant.
- **Barrier overhead is 1.6% geomean against a noise floor of about ±3%.** That is a requirement on
  the harness's own resolution, and control 7 (§8) measures whether this host can meet it rather than
  assuming it.

## 2. The scenario matrix

Every scenario exposes one operation and can be driven in either mode: closed-loop maximum-rate for
throughput, or open-loop fixed-arrival for latency. "Primary" is what the matrix reports as the
headline for that scenario; both are always recorded.

| # | scenario | mechanism rationale | primary | timeout |
|---|---|---|---|---|
| 1 | `low-allocation-compute` | **Barrier cost in the limit.** LXR's field write barrier is paid on every reference store whether or not there is garbage to pay for it. This is the scenario where a barrier regression is the only thing visible, and where the harness's own resolution is validated (control 7). | throughput | 300 |
| 2 | `allocation-churn` | **Young-object throughput and RC decrement volume.** The paper's Table 7 mean has Young RC reclaiming 94.3% of objects. It is the dominant reclamation path, so a regression here is a regression everywhere. | throughput | 300 |
| 3 | `long-lived-cache` | **Mature space, high survival, defragmentation pressure.** Exercises Immix mature evacuation, the 5% mature-wastage threshold and the single evacuation set, and the `Stuck` RC population of Table 7. | throughput | 420 |
| 4 | `cyclic-garbage` | **The sharpest RC-versus-tracing discriminator.** Pure reference counting cannot reclaim cycles; this is what forces LXR's SATB backup trace. `batik` is the one paper benchmark where SATB does the *majority* of reclamation (54.5% against a 5.1% mean), so a port implementing only the Young path would reproduce 16 of 17 benchmarks and fail this one badly. | throughput | 420 |
| 5 | `pointer-chasing` | **Write-barrier cost under mutation-heavy pointer updates, plus post-evacuation locality.** Complements #1: that one measures the barrier with few stores, this one with many, so the pair separates per-store cost from per-object cost. | throughput | 300 |
| 6 | `multi-thread-throughput` | **Scalability and contention on RC updates.** LXR uses a lock-free global block allocation buffer, and coalescing RC logs are per-mutator with a contended drain. | throughput | 300 |
| 7 | `aspnet-request-load` | **The flagship. Application-observed latency is the acceptance signal** (§1). Real Kestrel over the loopback, driven open-loop. | latency | 420 |
| 8 | `pinning-heavy-io` | **Ledger row R05.** LXR declares pinning unsupported, so there is no reference mechanism to port and this scenario is the port-side evidence base. See §2.2. | throughput | 420 |
| 9 | `lifecycle-semantics` | **The paper has no evidence here at all.** Its §4 (PDF page 9) states class unloading, compressed pointers and weak references were disabled in all four collectors — a configuration a shipping CoreCLR can never be in. The harness must generate this evidence. Correctness-first: see §2.3. | throughput | 420 |
| 10 | `large-object-pressure` | **LOH and POH behaviour.** LOH is not compacted by default; POH is pinned by construction and therefore collides with #8 and R05. Distinct from #3 because size class, not lifetime, drives placement. | throughput | 600 |

**"Primary" is only which number the matrix headlines.** Every scenario can be driven open-loop, so
**every scenario can produce coordinated-omission-free latency** — `SupportsLatency` is true for all
ten. That matters because the flagship latency scenario needs the ASP.NET Core shared framework and
so cannot reach a bare CoreRun host (§2.4); if `Primary = Latency` were the only source of latency
data, CoreRun would have none at all, which would be useless for the signal §1 established as the
acceptance criterion.

The table above is checked against the catalogue by the gate: scenario ids, primary metric and
timeout must agree between this document and `ScenarioCatalog.cs`, so the two cannot drift.

Each scenario is a class implementing one contract: `Describe()`, `Setup(seed, parameters)`,
`RunOperation()` returning a value folded into a checksum, `Verify()` returning the success marker,
and `Teardown()`. The catalogue in
[`ScenarioCatalog.cs`](harness/src/Lxr.Harness.Core/ScenarioCatalog.cs) carries each scenario's id,
primary metric, required host capabilities, latency support and default timeout, and is one of the
three independent derivations the gate cross-checks (§9).

so no one mistakes it for a measured value. The smoke runs in this document use `hdefault`, the
unpinned heap, because a smoke run's job is to prove the plumbing.

### 2.2 Scenario 8 and the pinning finding it encodes

P0.3 established, at the declared oracle revision `304ce69d`, that LXR **declares pinning
unsupported**: `PinningProcessEdges = UnsupportedProcessEdges` in both work contexts, the
`TPinningClosure` and `PinningRootsTrace` buckets unconditionally `set_enabled(false)`, `is_pinned()`
compiled to constant `false`, and `UnsupportedProcessEdges` panicking in five members. None of it is
`cfg`-gated, so all of it is present in every measured build.

.NET cannot opt out. `GCHandleType.Pinned`, `fixed`, interop and the pinned object heap all produce
immovable objects. Ledger row **R05** carries this with declared oracle `none`, which means this
scenario measures something the reference cannot do at all and is therefore the evidence base for a
port-side design. The scenario drives `fixed` blocks, pinned `GCHandle`s, POH allocation via
`GC.AllocateArray<T>(n, pinned: true)` and overlapped file I/O, with pinning density as an axis.

### 2.3 Scenario 9 asserts semantics, it does not time them

Because the paper generated no evidence in this area, scenario 9 is correctness-first. It asserts
finalizer ordering, weak-reference clearing before and after finalization, dependent-handle liveness,
`ConditionalWeakTable` behaviour, every `GCHandle` type, resurrection, and collectible
`AssemblyLoadContext` unload. **A semantic violation fails the run**; it does not become a slow
number. This is the scenario most likely to catch an LXR port silently changing observable behaviour.

One implementation note worth recording: `DependentHandle` is in `System.Runtime` and was moved out of
the `System.Runtime.CompilerServices` namespace into `System` — it is `System.Runtime.DependentHandle`
on current .NET, not where older samples put it.

### 2.4 The Kestrel decision and its consequence

Scenario 7 uses real Kestrel and ASP.NET, by explicit decision, because a hand-rolled HTTP loop would
not exercise the allocation profile that makes this the flagship.

`Microsoft.AspNetCore.App` is not built by this repository. The consequence is stated plainly rather
than smoothed over:

- The scenario declares `RequiredCapabilities = AspNetCoreSharedFramework`.
- On a host lacking it the run is recorded as `status: "skipped"` with
  `skipReason: "host-lacks-aspnetcore-shared-framework"` — **a declared skip, never a silent
  absence**, the same principle applied to timeouts.
- It lives in a **separate worker executable**, `Lxr.Harness.Worker.AspNet`. The shared
  `Lxr.Harness.Scenarios` assembly must not take an ASP.NET framework reference, or it could not load
  on CoreRun at all. This split is asserted by a unit test so it cannot be undone by accident.
- **It does reach the locally built runtime.** `scripts/compose-testhost-aspnet.ps1` layers the
  installed `Microsoft.AspNetCore.App` shared framework over the built testhost, and the resulting
  runs carry the built `coreclr.dll`'s SHA-256. This resolves what was an open risk: the flagship
  scenario is *not* cut off from the future LXR arm.
- The gate asserts that at least one latency-primary scenario is runnable on **every** host, so no
  host is ever left with zero latency evidence. Every scenario supports open-loop latency
  (`SupportsLatency` is true for all ten), so CoreRun has nine sources of it.

#### How strongly does this actually bind the LXR arm?

The plan for this step said scenario 7 "cannot run on the future LXR arm". That was too strong at the
time it was written — it was a *known-unknown* stated as a negative result, when in fact no candidate
had been tested. The correct statement then was "no path is known to me yet". It is recorded here
because an untested negative that reads like a finding is the failure mode this project keeps
catching, and it is worth catching in one's own writing too.

It is now resolved in the affirmative by composition, above. Two further points bound how much this
ever mattered, and both should be settled before anyone concludes the acceptance signal is at risk:

1. **A standalone GC does not need a rebuilt framework at all.** `System.GC.Name`/`System.GC.Path`
   load a GC library into an otherwise *stock* host — one that already has
   `Microsoft.AspNetCore.App`. To the extent LXR ships as a standalone GC, scenario 7 runs on a
   normal SDK with no composition step. The constraint only binds to the extent LXR **also** needs
   EE/JIT changes, which its field-logging barrier probably does, because CoreCLR's write barriers
   are JIT-emitted rather than GC-side. That dependency is stated here explicitly rather than
   silently assuming the worst case; it is a question for the phase that designs the barrier, not
   an established limitation.
2. **A third, in-repo candidate exists and is untested.**
   [`running-aspnet-benchmarks-with-crossgen2.md:210-226`](../../workflow/testing/coreclr/running-aspnet-benchmarks-with-crossgen2.md)
   documents running ASP.NET benchmarks against locally built CoreCLR bits using **crank**, where
   `--application.options.outputFile` uploads local artifacts to overlay the benchmark app. It is
   the sanctioned in-repo mechanism for this problem. It is not used here: the documented profiles
   (`aspnet-physical-win`, `aspnet-physical-lin`) target the ASP.NET crank benchmark machines rather
   than a developer box, so adopting it is a P0.5-or-later infrastructure decision, not a P0.4 one.
   It is recorded as **untested**, in the same breath as the other two.

## 3. Collector arms, and how the LXR arm gets added

An **arm** is a named, fully specified collector configuration. Three exist as data from day one; the
third has no implementation yet, and that is the point.

| arm | requested | identity confirmed by |
|---|---|---|
| `wks` | `System.GC.Server=false` | `GetConfigurationVariables()["ServerGC"] == false` **and** `GCSettings.IsServerGC == false` |
| `srv` | `System.GC.Server=true`, `System.GC.HeapCount=<n>` | `ServerGC == true`, `HeapCount == n`, `GCDynamicAdaptationMode == 0` |
| `srv-datas` | `System.GC.Server=true`, no heap count | `ServerGC == true`, `GCDynamicAdaptationMode == 1` |
| `lxr` *(future)* | `System.GC.Name=<library>`, `System.GC.Path=<path>` | `GetConfigurationVariables()["GCName"]` equals the requested library |

### 3.1 Adding the LXR arm later — the exact edits

The standalone-GC knobs `GCName` and `GCPath` are declared in `gcconfig.h:142-143` with public names
`System.GC.Name` and `System.GC.Path`, and both are surfaced by `GC.GetConfigurationVariables()`. That
means the harness can **read back the name of the GC that actually loaded**, which is a real
collector-identity signal of the same strength as the `ServerGC` one — not a guess.

Adding the arm requires:

1. One row in [`CollectorArms.cs`](harness/src/Lxr.Harness.Runner/CollectorArms.cs) —
   `CollectorArms.Lxr(libraryName, libraryPath)` already exists and requests the two properties.
2. Its identity assertion, which is the `GCName` readback, already implemented alongside the
   `ServerGC` one.
3. Nothing else. The matrix, interleaving, statistics, conformance and gate are arm-agnostic.

The `corerun` and `testhost` hosts both accept a standalone GC — CoreRun through `-p
System.GC.Name=…`, the dotnet hosts through `configProperties`. **No harness redesign is required**,
which was the explicit requirement of the brief.

### 3.2 Hosts

| host | knob delivery | scenarios |
|---|---|---|
| `sdk` | `<app>.runtimeconfig.json` `configProperties` plus `DOTNET_*` | all ten |
| `testhost` | same, over the locally built runtime under `artifacts/bin/testhost` | all ten, after `compose-testhost-aspnet.ps1` |
| `corerun` | `-p key=value` arguments, `corerun.cpp:726` | nine; `aspnet-request-load` is a declared skip |

Two facts about CoreRun that cost time to establish and are recorded so they need not be rediscovered:

- **CoreRun does not read `runtimeconfig.json` at all.** `corerun.cpp:538-612` builds the property
  list itself. Knob delivery is therefore genuinely different between hosts, which is why it is an
  explicit abstraction in `WorkerLauncher` rather than an accident.
- **CoreRun builds its TPA from exactly two directories**, `core_root` and `CORE_LIBRARIES`
  (`corerun.cpp:132-175`, which iterates `{ core_libraries, core_root }`), and `CORE_LIBRARIES` is a
  single directory rather than a path list. `core_root` defaults to the directory holding
  `corerun.exe`, which has `coreclr.dll` and `System.Private.CoreLib.dll` but **none of the framework
  facades** — so a managed assembly compiled against `System.Runtime` dies with
  `FileNotFoundException: System.Runtime, Version=11.0.0.0` before `Main` is reached. The harness
  supplies the framework as `core_root` via `--clr-path` (`corerun.cpp:711`, `:778`) pointing at the
  built shared-framework directory, whose `coreclr.dll` is byte-identical to the one beside
  `corerun.exe`, and passes the harness output directory through `CORE_LIBRARIES`.

## 4. Measurement methodology

### 4.1 Open-loop, coordinated-omission-free — the core of the design

For a latency measurement at arrival rate *R*:

- The schedule is **precomputed from a seeded RNG before the run starts** —
  `intendedStart[i] = t0 + Σ interarrival`, uniform (`1/R`) or exponential (Poisson) per
  configuration — so it can never be deformed by the system being slow.
- A dispatcher thread walks the schedule. If `intendedStart[i]` is already in the past it dispatches
  **immediately and marks the operation late**. It never skips, never re-times, and never waits for a
  previous operation to finish.
- Operations execute on a bounded worker pool. If the pool saturates, the operation still carries its
  original `intendedStart`, so the queueing shows up in the number instead of vanishing from it.
- Three timestamps are kept per operation: `intendedStart`, `serviceStart`, `end`. **Reported latency
  is `end − intendedStart`.** `serviceStart − intendedStart` is retained separately as `queueDelay`,
  which makes the coordinated-omission component *directly visible* rather than merely absent.
- `backlogMax`, `lateCount` and `achievedRate` are recorded. A run whose achieved rate falls short of
  the requested rate beyond a tolerance is marked `overloaded`, because an overloaded open-loop run
  measures the capacity limit rather than the latency and must not be silently compared.

Timestamps come from `Stopwatch.GetTimestamp()`. Waiting to a deadline uses a coarse sleep followed by
a spin, and the harness calibrates and records the timer's observed resolution at startup rather than
assuming it.

Control 2 (§8) is the proof that this works, and it is the single most valuable control here.

### 4.2 Why not BenchmarkDotNet

1. **BDN is structurally closed-loop.** Its measurement model is "invoke the operation N times,
   divide" — exactly the shape that hides the stalls a GC study exists to find. It cannot express
   §4.1.
2. **The collector-identity requirement fights it.** BDN owns process launching and generates its own
   host configuration. The harness must own the process, its properties, its environment, its dump
   policy and its timeout, and must read the collector back from inside the process under test.
3. **Dependency cost.** A zero-`PackageReference` harness restores and builds offline and — the
   decisive point — runs unchanged on `corerun`, where there is no package resolution at all.

What is given up is BDN's per-iteration overhead calibration and convergence machinery. It is bought
back with fixed-work quanta, many interleaved invocations, and a bootstrap CI on the ratio — and,
critically, **control 7 measures whether that is actually good enough** rather than assuming it.

### 4.3 Invocations, interleaving, statistics

- **Interleaving**: arms alternate across process invocations in a seeded A/B/A order, never
  all-A-then-all-B, so thermal drift and background load hit both arms equally.
- **Warmup and steady state**: a warmup phase is executed and discarded, the boundary is recorded, and
  raw samples retain a phase marker so the choice can be re-analysed later.
- **Statistics**, implemented in `Lxr.Harness.Core` and unit-tested:
  - percentiles by nearest rank from **retained raw samples**, never from pre-summarised data;
  - ratio of arm B to arm A on a declared statistic;
  - **percentile bootstrap CI on the ratio**, resampling *invocations* with replacement (B = 10 000,
    seeded), because latency data is not normal and a t-interval on it is wrong;
  - geometric mean for any cross-scenario roll-up, because P0.2 §7 is a geomean and an arithmetic mean
    would silently disagree with the paper.
- **Raw retention**: every operation's samples go to `runs/<runId>/<cell>/samples.bin.gz` with a
  documented fixed-width record. GZip is in the shared framework, so this costs no dependency. A
  summary cannot be re-analysed; raw can.
- **Environment capture**: CPU model, physical and logical cores, RAM, power plan, virtualization
  flag, and a background-load sample before and after each invocation. A run whose background load
  exceeds a threshold is flagged `noisy` and treated as suspect data rather than as a result.

This host is an **Azure VM** (`Win32_ComputerSystem.Model = Virtual Machine`), Intel Xeon Platinum
8370C, 8 cores / 16 threads, 64 GB, High performance power plan, with roughly 350 background
processes. It is shared and is not a sandbox. That is recorded in every result rather than assumed
away.

### 4.4 Pause data is secondary, and labelled as such

Pause data is collected in-process by an `EventListener` on `Microsoft-Windows-DotNETRuntime`,
deriving stop-the-world durations from `GCSuspendEEBegin`/`GCRestartEEEnd` and per-collection data
from `GCStart`/`GCEnd`, including the **reason**, which is how induced collections are separated. The
fallback, if the listener proves lossy, is differencing `GC.GetTotalPauseDuration()` against
`GC.CollectionCount()`. Which was used is recorded per run.

**Pause figures must not be used as an acceptance threshold** (§1).

### 4.5 Induced collections are counted separately

P0.3's probe 2 resolved the hsqldb p99 anomaly (PLDI 0.34–0.40 ms against HEAD 54–56 ms) as an
*induced-collection policy* difference, not an LXR mechanism question: hsqldb's `MemoryWatcherThread`
calls `System.gc()`, HEAD services it and promotes to a full stop-the-world `Pause::Full`, and the
PLDI oracle cannot service one because the body of `BasePlan::handle_user_collection_request` is
commented out.

A harness that let `GC.Collect()` happen invisibly would reproduce exactly that confound in .NET. So
`GC.Collect()` is banned from every measured region, induced collections are counted separately from
natural ones through the `GCStart` reason field, and the run record carries `inducedCollections`,
which the gate asserts is zero for every scenario that does not declare otherwise.

*(Correction to the brief, recorded here because it matters: this anomaly is **closed**, not open.
P0.3-oracle-probes.md §5 is titled "resolved", §6.2 says "Resolved, not retired", and summary row 5
records "cause identified and proven".)*

## 5. Pinned knobs and how each is verified

Every knob is recorded three ways — `requested`, `observed`, and **`evidence`**, the strength of the
observation. This is the direct answer to *"setting an environment variable is not evidence that the
setting took"*, and it is built to refuse to overclaim.

| level | meaning |
|---|---|
| `runtime-reported` | the runtime states its own effective value |
| `host-reported` | `AppContext.GetData` returns the property the host handed the runtime |
| `behavioural` | a probe whose outcome differs by configuration |
| `requested-only` | **we only know what we asked for**, and the harness says so |

| knob | requested via | observed via | evidence |
|---|---|---|---|
| `System.GC.Server` | host property | `GetConfigurationVariables()["ServerGC"]`, `GCSettings.IsServerGC` | `runtime-reported` |
| `System.GC.HeapCount` | host property | `["HeapCount"]` | `runtime-reported` (init-time; see below) |
| `System.GC.DynamicAdaptationMode` | host property | `["GCDynamicAdaptationMode"]` | `runtime-reported` under `srv`; `requested-only` under `wks` (see below) |
| `System.GC.HeapHardLimit` | host property | `["GCHeapHardLimit"]` | `runtime-reported` |
| `System.GC.Concurrent` | host property | `["ConcurrentGC"]` | `runtime-reported` |
| `System.GC.Name` / `.Path` | host property | `["GCName"]` / `["GCPath"]` | `runtime-reported` |
| `System.Runtime.TieredCompilation` | host property | `AppContext.GetData` | `host-reported` |
| `System.Runtime.TieredCompilation.QuickJit(.ForLoops)` | host property | `AppContext.GetData` | `host-reported` |
| `System.Runtime.TieredPGO` | host property | `AppContext.GetData` | `host-reported` |
| `DOTNET_ReadyToRun` | environment only | — | `requested-only` |

The runner compares observed against requested for every knob and marks the run **`valid: false`,
`invalidReason: "config-pin-not-honoured"`** on any mismatch. Knobs whose evidence is `requested-only`
are listed in the result's `unverifiedKnobs` array. **An honest short list beats a dishonest clean
sheet.**

### 5.1 Four findings that the readback design depends on

**The dictionary key is the C++ identifier.** `gcconfig.cpp:47-68` passes `#name` as `name` and the
public name separately, and `GC.CoreCLR.cs:911-915` drops any config with a null public key. So the
reportable set is exactly the `System.GC.*`-named knobs, keyed as `ServerGC`, `HeapCount`,
`GCDynamicAdaptationMode` and so on — not as `System.GC.Server`. The values reported are the
`s_Updated##name` fields (`gcconfig.cpp:50, 57, 61`), which is what makes them **observed rather than
requested**.

**`HeapCount` is init-time only.** `interface.cpp:431` calls `SetHeapCount(nhp)` and there is no later
call, so under DATAS the reported figure is the *initial* count and goes stale as DATAS varies it. It
is recorded as `initialHeapCount` and never as "the heap count".

**The Workstation DATAS trap.** `DYNAMIC_HEAP_COUNT` is defined only
`#if defined(USE_REGIONS) && defined(MULTIPLE_HEAPS)` (`gcpriv.h:158-162`), and the effective-value
write-back at `interface.cpp:752` sits inside `#ifdef DYNAMIC_HEAP_COUNT`. So under Workstation the
reported `GCDynamicAdaptationMode` is **the raw request, not the effective value** — and it does
report `1` there. The harness must never read `GCDynamicAdaptationMode == 1` as "DATAS active" without
`ServerGC == true`. This was confirmed empirically, not just from source. It is operating rule 15 in
its purest form: a citation is not evidence unless the cited code is compiled in the configuration
under discussion.

**Hex versus decimal, which decides the whole knob-delivery design.** The two channels parse integers
differently: `gcenv.ee.cpp:1338` parses GC integers from the **environment** as **hexadecimal**, while
`utilcode/configuration.cpp:86` parses **host properties** with base 0, i.e. **decimal**. Delivering a
heap count of 16 through `DOTNET_GCHeapCount` would silently request twenty-two heaps. Knobs are
therefore delivered through the runtimeconfig `configProperties` channel, and the environment channel
is used only where a control deliberately wants to override a property — which works because the
environment is consulted first (`gcenv.ee.cpp:1324` before `:1351`). Controls 1 and 3 exploit exactly
this, and control 3's output demonstrates the hex parse at runtime.

### 5.2 Two negative results, recorded rather than buried

**Tiering, PGO and ReadyToRun cannot be confirmed in-process.** The `TieredCompilationSettings` ETW
event (`ClrEtwAll.man:4247`, flags at `:701-706` = `0x1` QuickJit, `0x2` QuickJitForLoops, `0x4`
TieredPGO, `0x8` ReadyToRun) would state the effective values, and `eventtrace.cpp:5495-5525`
populates it from `g_pConfig`. But it is emitted during EE startup under an `IsEnabled()` guard at
`eeconfig.cpp:801-804`, which fires before any managed `EventListener` can exist. Requesting a rundown
would need an out-of-process tracer, which would not run on CoreRun and would be an external
dependency. ReadyToRun is worse still: `eeconfig.cpp:482` reads only `CLRConfig::EXTERNAL_ReadyToRun`,
so there is no `System.Runtime.ReadyToRun` host property at all. These are `host-reported` and
`requested-only` respectively, and are named in `unverifiedKnobs`.

**A behavioural tiering probe was written, tested in both directions, and deleted.** It called a
method 400 times per round over 4 rounds and watched `RuntimeMethodHandle.GetFunctionPointer()` for
the tier-0 to tier-1 transition, intending to upgrade tiering to `behavioural` evidence. Run with
default tiering and again with `DOTNET_TieredCompilation=0`, it returned:

```text
=== DOTNET_TieredCompilation on  ===  observed=  evidence=RequestedOnly
=== DOTNET_TieredCompilation off ===  observed=  evidence=RequestedOnly
```

Identical. 400 × 4 calls is well past the call-counting threshold and the tiered background delay, so
the method certainly was promoted; the probe simply could not see it, because the function pointer is
a **stable precode address that is backpatched underneath** rather than replaced.

A probe that cannot distinguish the two configurations it exists to distinguish is indistinguishable
from no probe, while *reading* as evidence. By the same standard this document applies to controls
(§8), it was removed rather than left in reporting `Inconclusive` forever. The finding is preserved in
the class documentation of
[`TieringProbe.cs`](harness/src/Lxr.Harness.Core/TieringProbe.cs).

### 5.3 Runtime build identity

Every result records `RuntimeInformation.FrameworkDescription`, `Environment.Version`, the
`AssemblyInformationalVersion` of `System.Private.CoreLib`, the path and file version of the loaded
`coreclr.dll`, and its **SHA-256**.

The SHA-256 is not redundant. Locally built runtimes carry **no `+<sha>` suffix** in the CoreLib
informational version, so on exactly the builds this project cares about, the hash is the *only*
working build identity. It is what proves a run used the locally built runtime: the testhost and
corerun smoke runs in §7 carry

```text
coreclrSha256 = 4280a427dbafae427b5e6afaf624461e15edc422c51848836a01af3246a9527a
```

which is the SHA-256 of `artifacts/bin/coreclr/windows.x64.Release/coreclr.dll` from this tree's
`clr+libs -rc Release -lc Release` build.

## 6. Correctness machinery

| requirement | implementation |
|---|---|
| **deterministic success marker** | the worker prints a single line `LXR-HARNESS-COMPLETE <scenario>:<checksum>` folded from every operation's return value. Deterministic scenarios have an expected checksum for the seed; non-deterministic ones assert a non-degenerate value and a minimum operation count. **Exit code 0 is never sufficient.** |
| **timeout** | `Process.WaitForExit(timeout)` then `Kill(entireProcessTree: true)`. Recorded as `status: "timeout"` with the configured limit and captured output — **a failed run, never a missing one.** |
| **crash capture, bounded** | `DOTNET_DbgEnableMiniDump=1`, `DOTNET_DbgMiniDumpType=1` (normal — `clrconfigvalues.h:577`; the runtime **default of 2, withheap**, is what produced the multi-gigabyte files already on this machine), `DOTNET_DbgMiniDumpName` inside the run directory. **Never the shared temp directory.** A `--dump-budget-mb` (default 512) is enforced *before each launch*; over budget means launching with no dump environment and recording `dumpPolicy: "suppressed-budget"`. |
| **collector identity** | §3. Any mismatch means `valid: false`, `invalidReason: "collector-identity-mismatch"`, and the aggregator **refuses to emit a ratio** containing an invalid run. A run whose collector cannot be confirmed is not merely flagged — it cannot contribute. |
| **runtime build identity** | §5.3 |
| **induced collections** | §4.5 |
| **declared skips** | `status: "skipped"` plus `skipReason`. A skip is a declared non-run, so its explanation lives in `skipReason` and the conformance checker does not additionally demand `invalidReason` — which would only invite the uninformative `invalidReason: "skipped"`. Both directions are unit-tested. |

#### What is asserted, and what is only measured

Two conditions decide the verdict, and both are about the **estimator**, not about the machine:

1. **True positive.** A coarse ~16.7% injection must give an interval excluding 1.0 on the low side.
   Observed `0.8122 [0.8023, 0.8220]`. If the estimator could not see an effect this large, it is
   broken — and that conclusion does not depend on how busy the host is.
2. **True negative.** Baseline against an *identical uninjected* baseline must produce an interval
   that **includes** 1.0. Observed `1.0085 [0.9978, 1.0195]`. An interval narrow enough to exclude 1.0
   on the injected arm would do so just as eagerly on no effect at all if it were merely
   over-confident, so without this direction the first condition proves nothing.

Everything about the ~2% fine injection — the ratio, the interval, the ladder — is **measured and
published, never asserted.** That separation is the whole design, and it was forced by evidence.

#### Why the barrier-scale effect is not a pass condition

The first version of this control did assert on the fine effect and on reaching a 1.6% half-width.
Run three times against the same binary on the same host, it reached the target at **n = 8**, at
**n = 15**, and **not at all** — and on the third run the fine effect came out at `0.9906` against a
null replicate of `0.9912`, statistically indistinguishable, so the control reported a failure.

That failure was real, but it was not a failure *of the harness*. Probing the worker directly, three
paired 8 s invocations of exactly this injection returned ratios of **1.0221, 0.9649 and 0.9922** — a
2% signal under a ±3% single-invocation spread, **with the sign flipping.** This is precisely the
paper's 1.6%-inside-±3% problem (P0.2 §7), reproduced on this VM, and it is the finding this control
exists to produce.

Gating the verdict on it made the control's outcome track the machine's background load, which has two
costs. It reports a broken harness when nothing is broken; and — worse — it teaches the next reader
that the way to green is to loosen the threshold or rerun until it passes, which is choosing the
acceptance criterion from the result. **A control that flakes stops meaning anything**, which is the
same failure mode as a control that never fires.

So the assertion moved to a magnitude this host cannot miss, and the barrier-scale question is
answered with a number that is published whether it is welcome or not. On this run the fine effect
*was* resolved (`0.9859 [0.9760, 0.9962]`) and the ladder met 1.6% from n = 3; on the previous run
neither happened. Both are recorded.

#### Why the measured effect need not match the arithmetic

The nominal `1/(N+1)` assumes an injected call costs exactly what a counted one costs — a claim about
this machine's microarchitecture, not about the harness. The coarse arm measures **18.8%** against a
nominal 16.7%, so the injected call is somewhat *more* expensive than a counted one, which is
consistent and unsurprising. The harness's claim is narrower and testable: it resolves an effect of
roughly the injected size, in the right direction, without manufacturing one when none exists.

#### Why a ladder rather than a chosen n

Publishing "n = X reaches 1.6%" after trying values until one did would be choosing the sample size
from the result. The ladder re-runs the estimator over **prefixes of one interleaved sequence** — a
prefix is an earlier contiguous time window, not a cherry-picked subset — and publishes the whole
thing, including the non-monotone stretches that a quieter machine would not show.

**The ladder is not stable between runs, and that is itself the finding.** Across three runs of the
same binary on this host it reached 1.6% at n = 8, at n = 15, and never. **P0.5 must re-run this
control as part of its own setup rather than trusting a resolution measured on a different day**, and
should take the conservative figure it observes rather than the best one.

### The instrumentation defect this control found

The injection originally read `if (options.InjectExtraWorkEveryNth > 0 && counter % N == 0)`. Because
`&&` short-circuits, the **baseline arm never executed the modulo at all**, while the slowed arm paid
a 64-bit `idiv` on every single operation. A nominal 1.96% injection measured **4.6%** — the
instrumentation was being measured rather than the injection.

The fix hoists `long injectStride = N > 0 ? N : long.MaxValue` and compares `counter >= nextInject`,
so **both arms execute an identical instruction stream** and differ only in whether a branch is taken.
The measured effect fell from 4.6% to the 1–2% range the injection actually accounts for — `0.9859`
against a `0.9804` nominal on the run above, though as §"Why the barrier-scale effect is not a pass
condition" records, that figure is not stable run to run and is no longer asserted on.

This is worth recording because it is the general shape of the hazard: *an injected control can
measure its own instrumentation*, and the way to find that is to ask whether both arms execute the
same instructions.

## 9. The verification gate

Two scripts under `harness/scripts/`, following the pattern established by P0.3's `verify-gate.sh`.

**`verify-harness.sh` audits the tree it ships in.** Its root is derived from `${BASH_SOURCE[0]}`, so
it always checks the artifact it is part of; an explicit argument overrides. There is no absolute
machine path anywhere in it. That is the defect that made P0.3's gate silently audit a *different,
mid-edit checkout* — reporting a failure the committed tree did not have, and equally able to report a
pass it had not earned.

**Expected counts are derived, never repeated as literals.** The scenario count is parsed from this
document's §2 matrix table, from `ScenarioCatalog.cs` in source, and from the ids present in the smoke
results — **three independent derivations that must agree**, rather than the number `10` written at
three assertion sites where two could drift from the third unnoticed.

### 9.1 An absent check must not read as a passed check

The gate originally took its results directory as an optional argument and, finding nothing there,
printed `no results to check` and passed. Run the way an auditor naturally would — `git archive` of the
commit into a non-repo, no arguments — it reported `RESULT: PASS (66 checks)`, exit 0. The 21 checks
that had gone missing were the *entire* `results are schema-conformant and carry identity` section,
which is what verifies collector identity. The step's own correctness criterion is *"a run whose
collector cannot be confirmed is invalid"*, so the single most important property this gate asserts
evaporated silently in the mode most likely to be used, and the gate still said PASS.

The asymmetry was visible in the gate's own output. The line-endings section printed *"not a git
checkout (this is expected when auditing a git archive extract)"* — an **explicitly declared** skip.
The results section took a **silent** one. That is exactly the distinction the harness enforces on
scenarios (§7: a declared skip, never a silent absence) and exactly the one §10 asks the canvas to
honour for `null` (an unavailable value must not be charted as a zero). The gate was breaking the rule
the harness exists to enforce.

**The mode is now chosen, never inferred**, and each mode has its own exit code so a caller testing
only for zero cannot be fooled:

| invocation | behaviour | exit |
|---|---|---|
| `--results <dir>` | audits that directory; **fails if it holds no results**, because naming a directory is a claim about it | 0 / 1 |
| *(neither flag, results present in the default location)* | audits them | 0 / 1 |
| `--no-results` | audits the static artifact alone, prints `RESULT: DEGRADED` naming the skipped section and what it leaves unchecked | **3** |
| *(neither flag, and nothing in the default location)* | **refuses** — prints the choice it will not make for you | **2** |

Generalised past the one reported section, because the bug class is not specific to it: every section's
check count is tracked, a section may declare a skip with a reason and a **kind**, and any section that
finishes having run **no checks without declaring one FAILS** as a gate defect. `inherent` skips (the
git index is unreadable in an archive extract — impossible in this mode, not a choice) are declared and
leave the verdict unchanged; `elected` skips (`--no-results`) are declared and downgrade it to DEGRADED.
Both are printed and both are counted; neither can be mistaken for a section that ran.

**`verify-harness-control.sh` is the gate of the gate**, in five steps:

- **A**: run the committed gate against a clean `git archive HEAD` extract, outside any worktree —
  expect pass.
- **B**: copy that extract, perturb **one** thing in the copy, run the same gate on the copy — **expect
  fail**. This is the whole point. Steps A and C alone would pass equally happily if the gate were
  reading the wrong tree.
- **C**: re-run on the untouched original — expect pass.
- **D**: the three results modes against an extract with no results — bare invocation must exit 2 and
  must **not** print `PASS`, `--no-results` must exit 3 and print `DEGRADED`, `--results` on an empty
  directory must exit 2. A mode that has not been shown to refuse is indistinguishable from one that
  cannot, which is §8's rule applied to the gate rather than to the harness.
- **E**: strip a section of its only check and require the gate to fail with *"ran no checks and did
  not declare a skip"* rather than quietly shrinking its total.

Both are run from **extracted committed content**, never from the working tree, and §12 records the
exact invocations and the `git ls-files --eol` output. An `i/lf` script checked out `w/crlf` cannot be
executed by bash at all, so a pass obtained from a converted copy would attest to the copy rather than
to the artifact.

## 10. Proposed benchmark-result schema extension

The harness emits `schemaVersion: 2`. The canvas extension currently reads `schemaVersion: 1`.

This proposal is **reconciled against the v1 artifact**, which the coordinating session supplied verbatim
from `.github/extensions/lxr-gc-roadmap/benchmark-results/README.md` after this document first went out.
The earlier draft was built from a prose description of v1 because the canvas extension is not committed
on `main` and is not present in this worktree, so it could not be read. Reading it changed the design in
two ways that a prose summary had hidden, both recorded below — which is the reason the rule is to read
the artifact rather than a description of it. The first of those two entries then broke that same rule in
its own text, and is corrected in place below rather than quietly rewritten.

**Structure (unchanged from v1, and this matters).** The canvas loads every `*.json` in its directory,
merges each file's `checkpoints` array and orders the result by date:

```json
{ "schemaVersion": 2, "checkpoints": [ { "id": …, "date": …, "stepId": …, "notes": …, "results": [ … ] } ] }
```

The emitter originally wrote its rows at the **top level**, with no `checkpoints` wrapper. This document
first claimed such a file "contributes nothing to the board — the quietest possible failure." **That claim
was false, and it was made about code this session could not read** — the canvas is not committed on
`main` and was absent from this worktree, as the paragraph above says two paragraphs before asserting how
that code behaves. The coordinating session settled it by writing the exact file and reading it back
through the running canvas: `store.mjs` merged it through a `document.checkpoints ?? [document]` fallback,
so the flattened record **loaded and charted.**

The correction matters in the direction that makes it worse, not milder. "Silently dropped" is the *safer*
of the two behaviours; the truth is that an unvalidated record was plotted as though it were a real
measurement. The argument given for the fix — that the failure was quiet — was therefore backwards, and
the fix never needed a behavioural claim in the first place: the wrapper is the documented shape, which is
sufficient on its own. The wrapper is asserted by `ResultConformance` and by a both-directions unit test
that also rejects the flattened shape.

That unit test passed while the claim was false, and this is the transferable part: **a test of this
harness's emitter can only ever confirm this harness's emitter.** It says nothing about how a consumer
outside the repository treats the bytes, so it could not have caught the error and did not. Verifying that
required rendering the file in the real consumer, which is what found it — and what also found a genuine
defect in the canvas that neither side was looking for, where a file with a mistyped key produced a
checkpoint with no `date` and took the entire board down through the sort comparator rather than merely
losing its own row.

**Null means unavailable, and zero does not.** v1's README says to use `null` for unavailable metrics.
The harness previously coerced missing pause and committed-memory data to `0` via `?? 0`. For
`low-allocation-compute` — a scenario designed to collect almost nothing — that published
`pauseAverageMs: 0, pauseP99Ms: 0, committedMb: 0`, which reads as a collector with perfect zero pauses
rather than one that was never observed to pause. `GCMemoryInfo` describes the last completed
collection, so every field of it is zero until one happens; `GCMemoryInfo.Index > 0` is the documented
signal and is what the worker now gates on. Verified on a real run: `low-allocation-compute` (gen0=0)
emits `null` for all three pause fields and for `committedMb`, while `allocation-churn` (gen0=449) emits
`2.581598`, `6.5006` and `28.644531`.

The gap v2 closes: v1 is pause-centric and has **no field for application-observed latency percentiles**,
which §1 establishes is the *acceptance* signal, with pauses being characterization. As written, the
harness could not publish the number that decides whether the port succeeds.

v2 is additive; all nine v1 result fields and all four v1 checkpoint fields are retained with their
meanings unchanged, so an unmodified v1 reader still parses a v2 file.

| new field | why |
|---|---|
| `latencyP50Ms`, `latencyP99Ms`, `latencyP999Ms`, `latencyP9999Ms`, `latencyMaxMs` | **the gap.** Table 5's supported G1-relative target is a **99.99%** latency ratio, so p99.99 is not optional |
| `latencyMethod` | `"open-loop-intended-start"`, so a closed-loop number can never be mistaken for a CO-free one. **Records lacking it must be treated as not CO-free** |
| `arrivalRatePerSecond`, `achievedRatePerSecond`, `overloaded` | an open-loop latency number is meaningless without the offered load, and an overloaded run measures capacity rather than latency |
| `heapFactor`, `heapLimitMb` | the paper's results **invert** with heap generosity; a throughput number without its heap factor is unusable |
| `requestedConfig`, `observedConfig`, `configEvidence`, `unverifiedKnobs` | observed versus requested, with honesty about evidence strength (§5) |
| `collectorConfirmed`, `valid`, `invalidReason` | *"a run whose collector cannot be confirmed is invalid"* must be representable, or the board will chart invalid runs |
| `status`, `skipReason` | `ok` / `failed` / `timeout` / `crashed` / `skipped`; a skip must be **declared**, not absent |
| `runtimeBuildId`, `runtimeDescription`, `coreclrSha256` | ties a number to a commit (§5.3) |
| `ratioStatistic`, `ratioVsBaseline`, `ratioCiLow`, `ratioCiHigh`, `ciMethod` | ratios with CIs; `ciMethod` records the bootstrap parameters |
| `invocations`, `seed`, `warmupSeconds`, `steadyStateSeconds` | reproducibility |
| `rawSamplesPath` | raw retention — a summary cannot be re-analysed |
| `inducedCollections` | §4.5, made checkable |
| `machine` block | cpu, physical/logical cores, ramGb, powerPlan, virtualized, backgroundLoadPercent, `noisy` |

Two behavioural requests alongside the fields:

1. Make `schemaVersion` **required**, so a v1 reader cannot silently mis-read a v2 record.
2. Have the canvas **exclude `valid: false` and `status != "ok"` records from charts while still
   listing them**, so failures are visible rather than invisible.
3. Treat a **null metric as absent, not as zero**, wherever the canvas charts or aggregates. This is
   already v1's stated rule, but with v1 emitters coercing to `0` it may never have been exercised;
   a chart that averages a null as zero would reintroduce the exact fabrication described above.

Two environment facts that cost real time and are recorded so they need not be rediscovered:

- **The runtime build needs a short path.** `build.cmd clr+libs -rc Release -lc Release` failed with
  `fatal error C1083` from MAX_PATH, because this worktree lives under a long
  `.copilot/repos/copilot-worktrees/...` path. Resolved by `subst L: <worktree>` and building from
  `L:\`, after which it completed in 19:48. `subst` persists for the logon session.
- **PowerShell has no heredoc**, `$?` is a `[bool]` so `echo exit=$?` prints `True` rather than an exit
  code (`$LASTEXITCODE` is the right one), and `Out-String` fabricates CRLF so it must never be used
