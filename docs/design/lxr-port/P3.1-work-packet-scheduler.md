# P3.1 - Work packets and strictly ordered buckets

P3.1 implements the collector-internal scheduler substrate for later LXR phases. It provides
reference-bearing work packets, persistent workers, local queues, work stealing, exact ownership,
and a stop-the-world bucket chain that cannot advance until all earlier work has drained. It does
not implement an LXR collector, RC metadata updates, object scanning, SATB, sweeping, evacuation,
pause selection, or EE suspension.

## Paper requirements

The paper is Zhao, Blackburn, and McKinley, *Low-Latency, High-Throughput Garbage Collection
(Extended Version)*, arXiv:2210.17175, 1 Nov 2022.

- Section 3.2.1, PDF pp.5-6 requires every RC epoch to apply all increments before decrements.
- Section 3.5, PDF p.9 states that increment/decrement work is parallel and uses work stealing for
  load balancing.
- Figure 2 and Sections 3.2.1-3.3.1, PDF pp.6-7 separate brief parallel STW increment/young work
  from concurrent lazy decrements and mature sweeping.

## Stage contract

`P3.1/mechanism-spec.json` is the structured authority. The exact active order is:

```text
Unconstrained
Concurrent
ConcurrentResumable
FinishConcurrentWork
Initial
Prepare
Closure
Release
STWRCDecsAndSweep
Final
```

Every ordinal and the name-table cardinality has a compile-time assertion. `FinishConcurrentWork`
is the first STW synchronization bucket. `Initial` is the first RC work bucket and is aliased as
`LxrRCProcessIncs`, matching `304ce69d:src/scheduler/work_bucket.rs:469`.
`STWRCDecsAndSweep` is aliased as `LxrRCProcessDecs`; `Final` is the end marker, not an RC work
bucket. Actual RC packet behavior is deferred.

## Packets and ownership

A packet has an immutable ID, stage, reference range, callback, and cycle generation. Its atomic
lifecycle is caller-owned, queued, executing, completed. Submission transfers execution ownership
to the scheduler; one worker wins the queued-to-executing transition; completion returns the packet
to its pool. A completed packet may be explicitly recycled only after its execution has accounted
for its bucket.

Payload entries are `uintptr_t`, independent of P2.1's selectable 2/4/8-bit RC width. The default
LXR RC packet has 1024 references, from `304ce69d:src/args.rs:88-100`; the supported policy is
256/512/1024/2048. The separate generic edge recommendation is 4096 at
`304ce69d:src/scheduler/mod.rs:3-9`. Queueing moves packet pointers, never the payload.

## Workers, stealing, and drain

Workers persist for the scheduler lifetime. Each has a bounded 16-packet local deque, matching
`304ce69d:src/scheduler/worker.rs:174-210`; buckets own global injector queues. Workers prefer local
work, refill from the eligible global bucket, then steal oldest eligible work round-robin from
another worker.

The scheduler serializes admission and stage changes. Outstanding work is counted before
publication and decremented after callback completion. A STW stage completes only when its global
queue, every local queue, outstanding count, and executing count are empty. The next stage opens
once, in ordinal order. Submissions to completed or stale-generation stages fail explicitly.

`Concurrent` and `ConcurrentResumable` expose explicit enable/resume operations, but P3.1 does not
choose pause policy. `BeginStwCycle` requires concurrent execution to be quiescent; P3.2 owns the EE
suspend/resume coordinator.

## Integration boundary

Product sources are compiled only with
`CLR_CMAKE_ENABLE_LXR_WORK_PACKET_SCHEDULER_TEST=1`. The option defaults off. The opt-in build
exports only `GC_LxrWorkPacketSchedulerTest_Run` for linked and standalone validation. No
`IGCHeap`, `IGCToCLR`, JIT-EE, public managed API, configuration knob, or versioned contract changes.
Normal Workstation/Server builds contain no P3.1 source object, call, branch, or export.

## Validation

The direct Windows and Linux validators cover stage names and ordinals, packetization boundaries,
closed-stage queueing, ordered opening, blocked predecessor work, exactly-once execution, packet
ownership, local caching, spills, and stealing. The linked/standalone smoke runs Workstation and
Server modes.

The archive gate runs the verifier from committed clean archive content and demonstrates negative
controls for stage order/rename, premature opening, executing-work drain accounting, lost and
duplicate packets, stealing, duplicate ownership, increment/decrement placement, source identity,
evidence cardinality, and benchmark A/A/injected-cost sensitivity.

## Benchmark boundary

The existing `multi-thread-throughput` scenario has an opt-in native bridge. Its direct and
scheduled policies call the same payload consumer through the same managed/native transition.
Workers are persistent; packets and 1024-reference payloads are preallocated. The fixed matrix uses
1/2/4/8/16 workers and direct, scheduled, null, sixty-four-extra-pass injected, and same-code replicate
policies.

The A/A control is paired inside one native replicate operation: the same packet is scheduled twice,
A/B label order alternates by sequence, and native nanoseconds are accumulated per label. The
`[0.90, 1.10]` bound applies to that in-process ratio, not to two process-level throughput means.

This is scheduler-substrate evidence. No complete LXR collector exists, so these measurements are
not LXR-versus-Workstation/Server throughput or application-latency results.

## Candidate validation and measurement

The pre-freeze candidate source passes 637/637 direct checks on both Windows x64 and Linux x64.
Linked and standalone smoke passes in Workstation and Server modes on both platforms, eight rows in
total. Windows x64 Debug and Linux x64 Debug product builds pass with the test option enabled.
Default-off Windows x64 builds contain no scheduler export. A Linux combined-feature build exposes
the P3.1, P2.2 Immix, write-barrier, and allocation-notification hooks together.

The x86 and ARM64 product translation units compile with the target MSVC toolchains. The attempted
full x86 Release build reaches and compiles all three P3.1 product objects, then fails in the
pre-existing x64-host cross-component debug build because the Windows SDK `_CONTEXT` selected for
that component has no x86 `Eax`/`Ecx`/`Eip` members. ARM64 execution hardware is unavailable.

The first full benchmark attempt is retained as failed sensitivity evidence. With only eight extra
payload passes, the injected arm did not clear its predeclared 1.25x bound at 8 and 16 workers, and
sequential A/A placement drifted outside `[0.90, 1.10]`. The final fixed policy uses 64 extra passes
and adjacent alternating A/A order. It is a superseding policy, not a rewritten result.

The first immutable-source run at `face23b1b401534469cb1d899ad49a5de93f1aa1` then retained a
second negative result: all functional rows passed, but three launches left the one-worker A/A
ratio at 1.136. A six-launch process-level attempt still measured 1.124. The bound remains
`[0.90, 1.10]`; final A/A evidence uses the paired in-process control described above and returns to
the original three-launch policy. Both failed process-level matrices remain part of final raw
evidence.

The next immutable source `e9f47205d37` exposed a validation scheduling race rather than a scheduler
failure: 636/637 checks passed, but worker 0 sometimes drained its local cache before a thief ran.
The scheduler's original counter recorded only local-deque theft and missed non-owner execution from
the global injector. The superseding packet records its preferred worker, and any execution by a
different worker counts as a steal. The failed immutable attempt is retained.

The first raw-only child reached the clean-archive verifier, then its stage-order perturbation failed
to apply because Windows `tar` materialized the LF-indexed C++ blob as CRLF. The superseding gate
detects and preserves each extracted file's newline style when applying a perturbation; it does not
convert a copy and mistake that copy for the shipped artifact.

The next raw-only child reached verifier controls and exposed perturbation state leakage: the
source-identity case inherited the previous stage-rename mutation. The final gate restores every
mutable source/evidence path from the untouched clean archive before injecting one fault, so each
negative result is attributable to exactly that fault.

The isolated gate then showed that bypassing only the predecessor-drain predicate was insufficient:
the independent all-workers-parked condition still prevented premature opening. The final negative
controls deliberately disable both independent protections, while the production scheduler retains
both.

The drain-accounting control initially raced because the main validator thread released its blocking
packet before the other workers necessarily re-parked. The final test waits for those park events,
then asserts that the executing `Initial` packet remains outstanding and `Prepare` remains closed.

The first fully passing 15-scenario gate printed PASS but inherited the last expected negative
validator's process exit code. The final gate explicitly exits zero after all scenario results and
cleanup have been written.

After steal accounting expanded to include non-owner global-injector execution, disabling only
local-deque theft no longer removed steal evidence. The final stealing control disables the
preferred-worker mismatch accounting itself and requires the validator's non-owner-steal assertion
to fail.

The clean baseline initially fails with 16 NU1903/NU1904 warnings-as-errors for the pinned
`Microsoft.DiaSymReader.Native` and `Microsoft.Native.Quic.MsQuic.Schannel` packages. That exact
failure is preserved. The authorized baseline rerun uses direct `eng/build.ps1` with only
`NU1903;NU1904` demoted; later build logs continue to print those audit warnings. No dependency is
changed and no other warning is demoted.

## P3.2 and later

P3.2 owns pause taxonomy, triggering, EE suspension/resumption, and concurrent interruption policy.
Later RC/SATB phases own actual increment/decrement work, recursive decrements, side metadata,
sweeping, tracing, object scanning, forwarding, and evacuation.
