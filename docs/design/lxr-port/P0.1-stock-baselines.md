# P0.1 follow-up — stock JVM baselines for the LXR reference run

This follow-up adds G1, Parallel GC, Serial GC, and ZGC runs to the original
P0.1 HEAD-LXR DaCapo 2006 characterization. It uses the same retained HEAD
OpenJDK image, DaCapo jar, `Bench` wrapper, `Hiccup` stall meter, benchmarks,
fixed heaps, iteration count, and invocation count. It does **not** build or run
the .NET port.

## 1. Scope and the comparison limit

The original HEAD-LXR measurements were collected on 7 August 2026. The stock
collector measurements were collected on 7 October 2026. They use the same
machine and retained JDK binary, but the two arms were not randomized,
interleaved, or run under a quiesced host.

Consequently:

- the tables are a same-machine, same-JDK, same-harness comparison anchor;
- absolute per-workload differences are characterization, not a causal
  collector-performance claim;
- the geometric means in §4.3 are descriptive only;
- three invocations yield ranges, not confidence intervals;
- the 1 ms Hiccup meter observes all mutator scheduling stalls, not only GC;
- the stock collector run has no separate A/A arm or injected-cost control.

This is deliberately weaker than the later .NET benchmark gates. It answers
the presentation question “what did the original LXR reference look like next
to ordinary JVM collectors on this machine?” It does not reproduce the paper’s
quiesced methodology.

## 6. Reading the result

The measured shape is favorable to HEAD LXR on this host, particularly at
500 MB. At 2000 MB, antlr is slower under LXR than G1/Parallel/Serial, luindex
is approximately tied with Serial/ZGC, and hsqldb is slower than ZGC.

The pause table is not a simple “LXR wins” table:

- LXR has low p99 on six workloads and visible mid-tails on lusearch/xalan.
- ZGC generally has the tightest extreme tails in this JDK build.
- LXR’s luindex p99.9 is near 1 ms but its maximum is 233–315 ms.
- Parallel and Serial show very large isolated maxima on several workloads.
- the Hiccup meter includes OS/VM scheduling, so maxima are characterization.

### 6.1 `hsqldb` is an induced-GC policy test

DaCapo 2006 hsqldb calls `System.gc()` five times per iteration. P0.3 proved
that HEAD LXR turns all 25 calls into full stop-the-world collections, while
the PLDI handler is inert. Stock collectors also have collector-specific
explicit-GC policies. Therefore the hsqldb row is not a clean steady-state LXR
latency comparison.

The earlier controlled HEAD-LXR run with `-XX:+DisableExplicitGC` removed all
25 collections/stalls and reduced wall time by about 39%; see
`P0.3-oracle-probes.md` §5. It was not repeated here because this follow-up
preserves the exact original P0.1 workload configuration.
