# P1.6 — Negotiated GC-reserved object-header bits

P1.6 adds a generic startup contract for a collector that needs a small atomic state in every
object header. It establishes reservation, transition, and preservation correctness only. It does
not copy objects or install a forwarding pointer.

The implementation was developed from `kkokosa/runtime:lxr` commit
`02fbc68684994a6071c07ce00bacac95d693b13e`, which contains P1.1–P1.5 and GC interface 5.14.

## 1. Oracle

The declared S01 oracle is the binding-pinned HEAD pair:

- OpenJDK binding `0682434ae725787e38defbc17bd66dc918e4bdb7`;
- `mmtk-core` `304ce69d43aae87de501111fceb8cbd33173a03a`;
- `MMTK_PLAN=LXR`.

The binding pins that core at `0682434:mmtk/Cargo.toml:42-50`, imports the LXR plan at
`0682434:mmtk/src/lib.rs:13`, and verifies selection by downcasting at
`0682434:mmtk/src/lib.rs:225-255`. Core reachability is
`304ce69d:src/lib.rs:68-70` → `src/util/mod.rs:58-60` →
`src/util/object_forwarding.rs`.

`304ce69d:src/util/object_forwarding.rs:8-19,23-40,52-75,78-100,119-183` defines the state:

| state | encoding |
| --- | ---: |
| clear / not triggered | `0b00` |
| invalid | `0b01` |
| transition / being forwarded | `0b10` |
| published / forwarded | `0b11` |

Claim is a `00 → 10` compare-exchange. Claim and publication use sequentially consistent
operations; waiters load while the state is `10`. The forwarding pointer is a separate mechanism
and is not part of P1.6.

The PLDI pair (`abbdd1d` + `df8d30a3`, `GC_FEATURES=lxr,immix`) has the same state protocol at
`df8d30a3:src/util/object_forwarding.rs:12-23,27-75,79-183`. HEAD is selected because the parity
ledger declares it for S01 and its `u8` API and runnable LXR configuration are the portable basis.
PLDI's lack of `src/plan/lxr` is not a missing mechanism; LXR is an Immix feature configuration
there.

## 2. CoreCLR header ledger

Every CoreCLR object has a 32-bit `m_SyncBlockValue` immediately before its MethodTable pointer.
On 64-bit targets another 32-bit word precedes it to make the header pointer-sized.

### Synchronization word

| bits | mask | owner |
| --- | --- | --- |
| 31 | `0x80000000` | defined as unused; no operational consumer at the P1.6 base |
| 30 | `0x40000000` | finalizer-run state |
| 29 | `0x20000000` | GC reserve/pinning state, including persistent FOH use |
| 28 | `0x10000000` | header spin lock |
| 27 | `0x08000000` | thin-lock versus hash/index discriminator |
| 26 | `0x04000000` | hash versus sync-block-index discriminator |
| 0–25 | `0x03ffffff` | 26-bit hash or 26-bit sync-block index |
| 0–15 in thin-lock mode | `0x0000ffff` | thread ID |
| 16–21 in thin-lock mode | `0x003f0000` | recursion |
| 22–25 in thin-lock mode | — | free only in this conditional encoding |

Only bit 31 is unconditionally unused. A two-bit reservation in this word would either halve the
sync-block-index range and reduce hash entropy or reduce thin-lock capacity. P1.6 rejects both.

### Separate 64-bit state word

The existing 64-bit padding word is:

- born zero with the rest of `ObjHeader`;
- at object offset `-8`;
- naturally 32-bit aligned;
- copied with the full header by compacting GC;
- excluded from pinned-plug gap/relocation snapshots by `plug_skew`;
- not read by retail runtime code;
- checked only by the old debug `m_alignpad == 0` assertion.

P1.6 renames it to `m_GCReservedBits`, removes the obsolete zero-only assertion, and assigns bits
0–1 to the negotiated state. Bits 2–31 remain zero and unassigned. `m_SyncBlockValue` remains the
last field at object offset `-4`; all lock, hash, finalizer, pinning, and diagnostic masks retain
their exact values and capacities.

There is no padding word on x86 or other 32-bit targets. An enabled request is rejected before
managed execution rather than approximated with synchronization-word bits.

## 3. Interface 5.15

The GC interface remains major 5 and advances from minor 14 to 15. The EE interface remains major
4. P1.2–P1.5 constants, structures, and vtable slots retain their exact layout.

P1.6 appends zero-based `IGCHeap` slot 91:

```cpp
virtual ObjectHeaderBitsParameters* GetObjectHeaderBitsParameters()
{
    static ObjectHeaderBitsParameters parameters = {};
    return &parameters;
}
```

The all-zero descriptor is disabled. The default method preserves source compatibility, while the
exact-major/minor loader gate prevents a 5.15 runtime from calling slot 91 on a 5.14 binary.

The fixed-width 80-byte descriptor carries:

- `NotProcessed → Accepted/Unsupported` status;
- disabled/enabled request;
- descriptor version and size;
- requested bit and valid-state counts;
- requested protocol and required atomic operations;
- required memory ordering;
- runtime-selected object-relative offset, word size, mask, and shift;
- granted protocol and operations;
- granted memory ordering;
- clear, invalid, transition, and published encodings.

A valid enabled request asks for two bits, three valid states, the generic `ClaimAndPublish`
protocol, atomic load, compare-exchange, store, and wait, and sequentially consistent ordering. On
64-bit CoreCLR and NativeAOT the runtime returns offset `-8`, 4-byte word size, mask `0x3`, shift 0,
states `00/01/10/11`, and a sequentially consistent ordering grant.

Malformed input or nonzero output fields return `E_INVALIDARG`; a null descriptor or invalid initial
status returns `E_FAIL`; a well-formed unsupported request, including 32-bit, returns `E_NOTIMPL`.
All fail before heap publication and managed `Main`.

Configuration runs after `GC_Initialize` and before `g_pGCHeap` publication in:

- CoreCLR default and standalone loading through `FinalizeLoad`;
- NativeAOT default loading;
- NativeAOT standalone `clrgc` loading.

`IGCHeap::Initialize` independently rejects an enabled descriptor that was not accepted.

## 4. Atomic API and ownership

CoreCLR, the shared GC object adapter, and NativeAOT each expose the same four masked operations
over the separate word:

- sequentially consistent interlocked load;
- masked compare-exchange;
- masked store implemented as a CAS loop;
- GC-side wait with scheduler yield.

Every update preserves all bits outside the runtime-selected mask. Allocation owns zeroing, the
runtime owns placement, and the collector owns only the granted mask after successful negotiation.

Within an active epoch the state is one-way:

```text
clear (00) --claim--> transition (10) --publish--> published (11)
                         |
                         +--pre-publication failure--> clear (00)
```

Reset from published to clear requires a quiescent boundary with no stale observers. This excludes
ABA within an active epoch. A single CAS wins the claim. The winner never waits for a losing worker
and must publish or roll back. Loads, claim, and publication use established interlocked primitives
with sequentially consistent ordering, matching the declared oracle. Publication follows
payload/metadata writes; a waiter that observes published sees those writes.

Runtime lock/hash/sync-block operations never inspect this word, including while it is `10`.
Consequently a GC transition cannot create a monitor/hash dependency or be mistaken for a thread
ID, recursion level, hash, or sync-block index.

## 5. Runtime interactions

- **Allocation:** ordinary, LOH, POH, and FOH objects begin clear. P1.4's callback contract is
  unchanged.
- **Cloning:** `MemberwiseClone` allocates a fresh clear header and copies only object data; source
  state is preserved and clone state is clear.
- **Locks and hashes:** thin-lock acquisition/recursion/contention/inflation and first/cached hash
  touch only `m_SyncBlockValue`.
- **Sync blocks:** allocation, lock/hash transfer, wait/pulse, scavenging, and index reuse are
  disjoint.
- **Finalization:** `BIT_SBLK_FINALIZER_RUN` remains in the synchronization word.
- **Pinning:** `BIT_SBLK_GC_RESERVE` remains in the synchronization word.
- **Relocation:** compacting copies from `dest - plug_skew`, preserving the full header.
  `plug::skew` separates the header from gap/relocation bookkeeping, so pre/post-plug snapshots end
  where the header begins and never overwrite or restore the state word.
- **Free/reuse:** allocation clearing removes stale state. Bounded churn marks a dying object
  published, observes exact address reuse on both LOH and POH free-list allocation, and requires the
  replacement object's state to be clear. The same bounded SOH arm is retained as coverage but does
  not require address reuse on every run.
- **DAC/cDAC:** `ObjHeader` size and `SyncBlockValue` offset do not change. The collector-private
  state is intentionally not interpreted by existing diagnostic contracts.
- **Mono:** no change; Mono uses a different object/monitor representation.

## 7. Performance boundary

Default and negotiated-clear lock/hash code has no state-word access or branch. Managed thin-lock
source changes only in comments. Release evidence compares the preserved 5.14 testhost with the
final 5.15 testhost for:

- uncontended and recursive locks;
- contended locks;
- first and cached hash;
- lock→hash and hash→lock inflation.

The paper's 1.6% field-barrier geomean is not a P1.6 target. It is from the 1 November 2022 extended
version, arXiv:2210.17175, Figure 3/Table 7, against no-barrier Immix on OpenJDK. P1.6 requires
byte-identical hot paths and no reproducible lock/hash regression.

The same-binary registered-off versus negotiated-clear rerun reports:

| operation | clear/off ratio |
| --- | ---: |
| uncontended lock | 1.002 |
| recursive lock | 1.006 |
| contended lock | 0.999 |
| first hash | 1.002 |
| cached hash | 0.995 |
| lock then hash | 0.992 |
| hash then lock | 1.006 |

With the negotiated word explicitly held in each valid raw state, the same runtime reports:

| operation | transition/clear | published/clear |
| --- | ---: | ---: |
| uncontended lock | 0.992 | 0.996 |
| cached hash | 1.045 | 0.987 |

The explicit SeqCst helper characterization, including the native test-hook call boundary, is
20.6–26.8 ns for one masked load and 55.0–58.2 ns for a two-CAS state round trip across the three
valid states. These are collector-operation costs, not lock/hash hot-path costs.

The base/default paired run reports exact parity for uncontended and contended locks and first hash.
Recursive lock and cached hash differ by 2.5% and 2.2% in one run, while allocation-plus-inflation
arms swing in opposite directions by roughly 8–10%; the reverse-order run therefore characterizes
those arms as host noise rather than a directional effect.

The stronger code evidence is exact: normalized Release instruction streams and instruction counts
match for `Object::GetHashCodeEx`, `ObjHeader::GetSyncBlock`, and
`ObjHeader::GetSyncBlockIndex`. The default `coreclr.dll` grows by 1,024 bytes for cold interface and
configuration code; object and synchronization structure sizes do not change.

## 8. P1.6 boundary

This step closes storage negotiation and transition correctness. It does not choose forwarding
pointer placement, copy an object, redirect a reference, or activate a copying collector. Those
remain P6 work.
