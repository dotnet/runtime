# P1.1 — GC-requested write-barrier shape

**Status:** implemented and validated. **Redesign base:** `f3f02c558d3bd8af73d034f03c2d097c900a5de7`.

This step replaces the earlier versioned capability exchange with one generic request on the
existing GC-to-EE write-barrier initialization path:

```text
IGCToCLR::StompWriteBarrier(WriteBarrierParameters*)
```

The collector requests exactly one write-barrier shape. The built-in collector requests the
zero-valued `CardTable` default and retains its existing specialized helper contract. The first
non-default shape, `SideMetadataFieldLog`, describes generic barrier mechanics without naming a
collector. Production P1.1 rejects that shape before successful GC initialization because its
metadata fast path belongs to P1.2. An opt-in Windows AMD64 validation build accepts it solely to
execute and measure the ordinary-platform-ABI slow-call strategy.

There is no parallel `IGCHeap` query, bounded record, record version, selector, caller/callee
version negotiation, or loader-published capability state.

## Shape request

`WriteBarrierParameters` keeps every existing field and offset through
`region_use_bitwise_write_barrier`, then appends:

- `WriteBarrierShape`
  - `CardTable = 0`
  - `SideMetadataFieldLog = 1`
- `WriteBarrierRequestStatus`
  - `NotProcessed = 0`
  - `Accepted = 1`
  - `Unsupported = 2`
- `WriteBarrierSideMetadataParameters`, meaningful only for the side-metadata shape:
  - a biased metadata base;
  - a slow callback;
  - the base-2 destination granularity shift;
  - whether a clear or set bit requires slow work.

For destination address `D`, the metadata byte and bit are:

```text
byte = metadata_base + (D >> (granularity_shift + 3))
bit  = (D >> granularity_shift) & 7
```

The runtime rejects `granularity_shift >= pointer_bits - 3`, preventing overflow in the first
shift. The callback runs before the field is overwritten and receives the destination, old
reference, and new reference. It must not collect, block, switch GC mode, or throw across the
boundary.

The tail applies only to `WriteBarrierOp::Initialize`. Resizes and ephemeral/write-watch stomps
retain their existing meanings.

## Layout and interface compatibility

The GC interface remains major 5, minor 9. The EE interface remains major 4 because no virtual
slot is added or reordered. `GC_WRITE_BARRIER_SHAPE_INTERFACE_MINOR_VERSION` marks the minor
version at which the additive parameter tail exists.

`write_barrier_shape` is explicitly pointer-aligned. This prevents the new tail from occupying
the trailing padding of the frozen 5.8 structure:

| layout | x64 | x86 |
|---|---:|---:|
| complete 5.8 prefix | 80 bytes | 44 bytes |
| shape offset | 80 | 44 |
| status offset | 84 | 48 |
| side-metadata offset | 88 | 52 |
| side-metadata size | 24 bytes | 12 bytes |
| complete 5.9 structure | 112 bytes | 64 bytes |

All five in-tree constructions use aggregate zero initialization. An unchanged collector source
rebuilt with the 5.9 header therefore requests `CardTable` with `NotProcessed` without source
changes.

For a standalone collector, the runtime checks the version returned by `GC_VersionInfo` before
touching the tail:

- a major below 5 is rejected;
- major 5, minor 8 or lower uses only the frozen prefix;
- major 5, minor 9 or higher exposes the tail;
- a major above 5 remains loadable under the existing forward-compatibility protocol but does not
  expose the 5.9 tail.

The real-loader compatibility matrix is:

| collector/runtime pairing | behavior |
|---|---|
| unchanged 5.8 source rebuilt with the 5.9 header, new runtime | Zero initialization requests cards; the runtime acknowledges and starts. |
| 5.8 binary, new runtime | The version gate uses only the 5.8 prefix. A guard-page test proves no tail byte is read or written. |
| 5.9 card binary, 5.8 runtime | The old runtime ignores the tail. `CardTable + NotProcessed` means historical card behavior and succeeds. |
| 5.9 side binary, 5.8 runtime | Status remains `NotProcessed`; the collector returns `E_NOTIMPL` instead of silently using cards. |
| 5.9 side binary, production 5.9 runtime | The runtime writes `Unsupported`; the collector returns `E_NOTIMPL`. |
| major below 5 | The standalone loader returns `E_FAIL` before `GC_Initialize`. |
| major above 5 | The loader preserves the existing forward-compatible behavior and calls `GC_Initialize`; the 5.9 tail remains hidden. |
| linked CoreCLR or NativeAOT | The complete layout is known at build time; the same shape/status rules apply. |

`legacy-5.8-guard-page.patch` applies to `d272dabb7b4`. It moves the genuine 5.8 prefix-sized
parameter block to the end of a readable page and makes the following page inaccessible. Both
Workstation and Server startup pass on the redesigned runtime.

## Processing and initialization failure

The initial request follows one acknowledgment protocol:

1. The collector sets one shape and resets status to `NotProcessed`.
2. The EE establishes that the tail exists before reading it.
3. The EE validates support and all shape-specific parameters before changing card-table,
   heap-bound, write-watch, region, helper-address, or codegen-mode globals.
4. A supported shape becomes `Accepted`.
5. An unsupported shape or malformed shape-specific parameter becomes `Unsupported`.
6. The collector accepts `NotProcessed` only for `CardTable`, preserving old-runtime behavior.

The collector maps `Unsupported` and non-default `NotProcessed` to `E_NOTIMPL`; an unknown
acknowledgment maps to `E_FAIL`. `stomp_write_barrier_initialize` returns that exact result through
`gc_heap::init_gc_heap`, `make_gc_heap`, and `GCHeap::Init`. Unrelated heap-construction failures
retain their existing out-of-memory mapping.

Collectors older than 5.9 have no acknowledgment tail. If their implicit CardTable request
conflicts with an already-observed or finalized compiler barrier convention, the EE terminates
initialization with a specific fatal diagnostic rather than returning without initializing the
barrier globals. Initialization-only global invariants are asserted before every shape-rejection
path.

Rejection occurs before `create_gc_thread()` and before successful runtime/application startup.
CoreCLR assigns an internal `g_pGCHeap` during loader setup before `IGCHeap::Initialize`, so the
guarantee is deliberately not “no internal pointer was assigned.” The guarantee is that the heap
never becomes usable by managed application code and runtime startup fails deterministically.
No second public selection state exists.

CoreCLR and NativeAOT both acknowledge `CardTable`, reject non-default production requests before
barrier-global mutation, and propagate initialization failure. NativeAOT's bootstrap surface maps
the internal rejection to process exit `-1`; its paired card-table executable reaches managed
`Main` and returns `100`.

## Calling-convention strategy

### Why the specialized contract cannot call C++

Current JIT write barriers are not normal `GT_CALL` nodes. Lowering fixes their input registers,
LSRA uses a write-barrier-specific kill set, codegen synthesizes the helper call, and the emitter
separately invalidates GC-tracked registers. AMD64's specialized helpers preserve almost all
SIMD/opmask state and more integer state than the platform ABI. Retargeting such a call site
directly to C++ would let live values remain in ABI-volatile registers and silently corrupt them.

The implementation uses two immutable compiler-visible contracts instead of an XSAVE/FXSAVE
transition stub:

- **Specialized** — the existing card-table helper convention and exact existing code.
- **Standard** — the normal platform ABI, permitting an ordinary C/C++ callback.

The selected mode is finalized once during the initial stomp. If a JIT compilation asks for flags
before finalization, it records that Specialized was observed; a later Standard selection fails
closed. A later attempt to change either finalized mode also fails.

`CORJIT_FLAG_USE_STANDARD_WRITE_BARRIER_ABI` carries Standard to every runtime JIT compilation.
The JIT/EE GUID changed with the contract, and SuperPMI records and displays the flag.
While the validation helper targets are being installed, Standard remains in an internal
initializing state. A concurrent JIT flag query waits until target installation is complete, so it
cannot compile for one convention and bind a helper using the other.

### Windows AMD64 implementation

AMD64 write-barrier inputs already occupy platform argument registers: `RCX/RDX` on Windows and
`RDI/RSI` on System V. In Standard mode the JIT:

- uses full dynamic `RBM_CALLEE_TRASH`, including ABI-volatile integer, SIMD, mask, and available
  APX registers;
- uses full dynamic `RBM_INT_CALLEE_TRASH` for GC-reference invalidation;
- reserves the Windows 32-byte outgoing shadow space;
- calls `BuildKills`, not just a raw kill-position builder, so LSRA preserves the volatile upper
  halves of partially callee-saved vectors.

The helper IDs remain `CORINFO_HELP_ASSIGN_REF` and `CORINFO_HELP_CHECKED_ASSIGN_REF`. Their fixed
targets are selected once during startup; generated stores contain no shape test or family branch.
The validation helper calls the collector's ordinary-ABI C++ callback and then performs the real
stock card write barrier. `CORINFO_HELP_ASSIGN_BYREF` deliberately retains the Specialized contract
and does not invoke the P1.1 callback.

The destructive callback chooses its implementation once during GC startup using CPUID/XGETBV.
On the executed AVX-512 host it destroys:

- `RAX`, `RCX`, `RDX`, and `R8`–`R11`;
- `XMM/YMM/ZMM0`–`5`;
- volatile upper state through `vzeroupper`;
- `ZMM16`–`31`;
- `K1`–`K7`.

The JIT must preserve every value that remains live across the managed store. A captured negative
control that bypassed LSRA's partial-vector save handling failed with
`Vector256 state was corrupted across a write barrier`; the corrected `BuildKills` implementation
passes.

### Precompiled code

ReadyToRun call sites already contain the Specialized kill/reporting contract. Standard selection
therefore requires `DOTNET_ReadyToRun=0` from process start and is rejected when ReadyToRun is
enabled. No loaded image is reinterpreted or invalidated.

NativeAOT call sites are compiled with a fixed barrier contract. P1.1 keeps the image contract
Specialized and rejects runtime-selected non-default shapes. Future NativeAOT activation requires
a build-time convention choice and an image/runtime expected-shape check.

The destructive callback detects OS-enabled APX and uses REX2 instructions to clobber
`R16`–`R31`; the dynamic JIT kill/reporting masks include those registers. The executed host has
no APX support, so that callback arm and managed preservation remain source-audited rather than
executed.

The relevant region/Satori-era changes (`063f7b761dc`, `e2ad5fcc170`, `3aa00d745525`, and
`db876108487`) establish immutable startup helper selection and keep extra mechanics in patched
assembly. No Satori-named C/C++ barrier-call precedent exists in the inspected history. Standard
ABI is the additional contract needed for a generic C/C++ slow path.

## Executable validation

`run-barrier-shape-validation.ps1` compiles and executes the x64/x86 layout/default checks, audits
all in-tree constructions, verifies obsolete negotiation symbols are absent, and builds a
older- and newer-major standalone GC probes.

`run-barrier-shape-integration.ps1` passes 31/31 scenarios:

- production built-in and standalone cards, Workstation and Server;
- built-in and standalone Standard destructive callbacks, Workstation and Server;
- standalone Standard counting callbacks;
- Workstation/Server `DOTNET_JitStressRegs=8`;
- `DOTNET_GCStress=0xC`;
- old binary/new runtime and new binary/old runtime;
- deterministic fatal rejection of a conflicting legacy codegen reservation;
- unchanged old source/current header;
- guard-page old binary;
- production side rejection, older-major rejection, newer-major loading, and ReadyToRun rejection;
- unknown shape and null/overflow/invalid side parameters;
- non-default new GC on an old runtime.

Every final destructive run, including built-in Workstation and Server, executes a callback delta
of 169,993 and preserves integer, object, `Vector128`, `Vector256`, and `Vector512` state on this
host. The count is execution evidence rather than a stable contract. The AVX-512 callback
additionally destroys `K1`–`K7`, and the JIT kill set includes the allocatable opmask registers.
There is no separately observable managed mask value in this test, so opmask liveness across the
store is not claimed as an executed assertion.

`run-nativeaot-barrier-shape-validation.ps1` passes 2/2 paired executables and restores the
production NativeAOT runtime artifacts before exiting.

Generated-code evidence for the vector liveness methods is:

| method | Specialized | Standard | Standard behavior |
|---|---:|---:|---|
| `StoreVector128` | 108 bytes | 155 bytes | ABI-volatile values are not kept across the call. |
| `StoreVector256` | 111 bytes | 236 bytes | Upper halves are extracted before and reinserted after the call. |
| `StoreVector512` | 129 bytes | 260 bytes | Full live vectors are spilled and restored. |

## Slow-call measurement

`write-barrier-benchmark` performs 16 unrolled managed reference stores per invocation and reports
per-store cost through BenchmarkDotNet. The three jobs used the same Windows AMD64 machine,
Workstation GC, ReadyToRun off, tiering off, 3 launches, 8 warmups, and 20 measured iterations.
The host was a Hyper-V VM with an Intel Xeon Platinum 8370C; results should not be compared across
machines.

| managed store | stock Specialized | Standard + empty C++ callback | Standard + counting C++ callback |
|---|---:|---:|---:|
| field | 3.008 ± 0.005 ns | 5.090 ± 0.007 ns | 8.498 ± 0.010 ns |
| array | 4.252 ± 0.013 ns | 6.724 ± 0.015 ns | 9.361 ± 0.012 ns |

Errors are BenchmarkDotNet 99.9% confidence-interval half-widths. An initially bimodal counting-array
run was discarded; the stable isolated rerun is reported above. The empty callback adds 2.082 ns for
field stores and 2.472 ns for array stores over stock. The observable counting callback adds 5.490 ns
and 5.109 ns over stock, respectively. These stable deltas measure the P1.1 convention and callout
strategy, not the not-yet-implemented P1.2 metadata fast path.

The Standard field benchmark adds only the required 40-byte Windows call frame
(`sub/add rsp, 40`) and grows from 225 to 233 bytes. The stock and Standard array methods are both
322 bytes because that path already has normal helper-call outgoing space. Empty and counting
callbacks use the same managed codegen.

## Zero-cost default

Release builds of the inherited prototype and this redesign used the same toolchain and
configuration.

- The 1,300-byte CoreCLR `JitHelpers_FastWriteBarriers.asm.obj` code section is byte-for-byte
  identical; raw SHA-256 is
  `B654EC9EF5B41DD6506D5E73C0C5AF6F7FD4B0926123A752BD03868A3AE87C94`.
- The 486-byte NativeAOT `WriteBarriers.asm.obj` code section is byte-for-byte identical; raw
  SHA-256 is
  `8C7959B2CBCFA89321C2F6C78D33608D66E20571DCF289C053B371D447527DEE`.
- Specialized managed vector-store disassembly is byte-for-byte identical between the inherited
  and redesigned runtimes.
- Validation wrapper/callback code is compiled only under
  `CLR_CMAKE_ENABLE_WRITE_BARRIER_STANDARD_ABI_TEST`; that option defines both built-in GC object
  libraries and exports the callback counters from the validation `coreclr`.

The built-in barrier therefore pays no added managed-reference-write instruction, load, branch,
spill, call, or native barrier byte when the non-default shape is unused.

## Phase boundary and limitations

- **P1.1:** generic startup request/acknowledgment, exact failure, immutable compiler-visible
  calling convention, and validation-only AMD64 C++ callout proof for scalar field and array stores
  through `CORINFO_HELP_ASSIGN_REF` and `CORINFO_HELP_CHECKED_ASSIGN_REF`.
- **P1.2:** side-metadata fast-path instructions, slow-path condition, production activation on x64,
  and the complete reference-store/runtime-helper surface required for sound activation. The current
  tree has no `CORINFO_HELP_ASSIGN_BYREF`; unknown byref stores use `CHECKED_ASSIGN_REF`.
- **P1.3:** interface 5.12 adds bounded native-word metadata scanning, layout-aware JIT bulk
  copy/clear helpers, and a repeated fill operation. NativeAOT remains fail-closed until its image
  contract can select the convention at build time.

Production P1.1 intentionally does not implement a side-metadata barrier on any architecture.
Only Windows AMD64 executed the Standard contract. Windows x86 and ARM64 were cross-built but not
executed; the remaining targets were source-audited only. APX high registers were not available on
the executed host. Opmask destruction was executed, but preservation of a live managed mask value
was source/codegen-audited rather than independently observed.
