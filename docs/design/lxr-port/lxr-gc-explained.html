“LXR” can mean a paper design, a particular MMTk implementation revision, or the in-progress CoreCLR port. They overlap, but they are not identical.

Paper means measured design

The primary paper source is Zhao, Blackburn, and McKinley, Low-Latency, High-Throughput Garbage Collection (Extended Version), arXiv:2210.17175v1. Page numbers here are PDF pages, not proceedings pages.

Reference means an exact build pair

The paper-era oracle is MMTk core df8d30a3, pinned by binding abbdd1d. The newer validation oracle is core 304ce69d, pinned by binding 0682434. Citations use git show revision:path, never the checked-out tree.

.NET implemented means code that exists

The port has generic runtime substrate (P1.1–P1.6), fixed-address side metadata (P2.1), Immix block/line state (P2.2), and a default-off sticky RC/straddle substrate (P2.3).

.NET planned means not present yet

There is no selectable LXR collector yet. Allocation, hole finding, barrier packet processing, lazy decrement cascades, sweeping, SATB, young copying, mature evacuation, and end-to-end policy remain future work.

Most important status boundary: P2.3 proves substrate semantics. Its benchmark is synthetic. It is not a benchmark of a functioning LXR collector, and it is not a Workstation/Server GC comparison.

LXR in one picture

LXR uses fast reference-count epochs for most garbage, a concurrent SATB trace for cycles and saturated counts, and an Immix heap for bump allocation, hole reuse, and occasional stop-the-world copying.

Paper The design is not “pause-free.” It deliberately uses regular parallel stop-the-world RC epochs, runs most decrements and SATB work concurrently, and performs all copying during pauses. [P §§1, 3; PDF pp.2, 5–9]

1. GC basics: the graph, the roots, and the mutator

Start with a directed graph. Objects are nodes; object fields are edges; stacks, registers, statics, and VM-owned handles are roots. The application threads are “mutators” because they continuously mutate this graph.

Background

Reachable

An object is live if at least one path from a root reaches it.

Background

Unreachable

No root path reaches it. Its memory may be reclaimed safely.

Background

Collector invariant

Never reclaim something a correct mutator can still reach.

Tracing

Start at roots and walk outward. Anything visited is live; everything else is dead. Tracing naturally finds disconnected cycles, but a whole graph traversal can be expensive.

Reference counting

Maintain incoming-edge counts incrementally. A count that becomes zero proves death immediately, but positive count does not prove reachability. Cycles are the counterexample.

2. Reference counting: cheap proof of death, expensive updates

Conceptually, every object stores the number of references pointing to it. Creating an edge increments the target; deleting an edge decrements the old target.

RC(object) = number of incoming references currently represented by the counting scheme
  1. Store a new reference. Increment the new target.
  2. Overwrite the old reference. Decrement the old target.
  3. Observe 1 → 0. The target is dead. Scan its outgoing fields and recursively decrement their targets.

What RC is good at

  • Death can be identified without scanning the whole heap.
  • Most garbage can be reclaimed close to when it becomes unreachable.
  • Work is naturally incremental and can target changed objects.

What naïve RC gets wrong

  • Every pointer store can require atomic metadata work.
  • Recursive decrement chains can be arbitrarily long.
  • Disconnected cycles retain positive internal counts forever.
Key logic: RC == 0 is sufficient evidence of death. RC > 0 is not sufficient evidence of life. LXR is built around this asymmetry.

3. Deferred and coalescing RC: pay for the boundary, not every mutation

LXR does not update counts synchronously after every assignment. It divides time into mutator epochs separated by short RC pauses and retains just enough information to compute each field’s net change.

Root deferral

Roots change too frequently to barrier every register and stack slot. At an RC pause, LXR scans roots, increments their targets, and remembers those targets so matching decrements can be applied at the next epoch. [P §2.1, PDF p.3; Deutsch–Bobrow 1976]

Heap-field coalescing

Paper On the first write to a field in an epoch, LXR logs the old referent and the field address. At the next RC pause it reads the final referent from that address. Intermediate values cancel. [P §2.1; §3.4, Fig.3; PDF pp.3, 8–9]

What coalescing requires

At every reference-store path

  • A per-field “unlogged this epoch” state.
  • A cheap fast-path test.
  • Atomic first-writer arbitration.
  • The old referent and the exact field address.
  • Thread-local buffers with flush/teardown rules.

At each RC pause

  • Stop mutators long enough to get a stable boundary.
  • Scan roots and modified slot addresses.
  • Apply all increments before decrements.
  • Reset logging state for the next epoch.
  • Hand old referents to lazy decrement/SATB work.
Why increments first? Suppose a reference moved from one slot to another. Decrementing the old slot first could transiently drive the object to zero and reclaim it before the new slot’s increment arrives. Increment-first ordering turns a move into a temporary over-count, which is safe.

4. Sticky counts: make tiny counters safe

The evaluated paper design uses two bits per allocation quantum. The value 3 means “three or more,” not exactly three. Once reached, it never moves again.

Paper design
  • Two bits per 16-byte minimum object quantum.
  • Values 0, 1, 2, and sticky 3+.
  • Sticky counts are recovered only by backup tracing.
  • 0–1% stuck objects in 16/17 benchmarks; Batik 6.6%.

[P §3.2.1, Table 7; PDF pp.6, 13]

Reference + .NET
  • Reference code parameterizes 2/4/8 active bits.
  • .NET implements all three widths; default remains 2 bits.
  • .NET granularity is 8 bytes; minimum object is 24 bytes.
  • Masked native-word CAS preserves neighboring packed counters.

[df8d30a3:src/util/rc.rs:30–43,72–100; 304ce69d:src/util/rc.rs:13–26,90–123; a9817282:reference_count.cpp:243–323]

Why saturation is safer than wraparound

Two bits cannot represent an arbitrary number of incoming references. A normal modulo counter would be catastrophically unsafe: the fourth increment could wrap 3 → 0, making a heavily referenced live object look dead. Saturation deliberately loses precision in the safe direction. The collector remembers “at least three” forever and asks tracing—not arithmetic—to decide whether the object later dies.

Exact region: 0, 1, 2

Increment and decrement preserve exact incoming-edge information. A 1 → 0 transition may start a recursive death cascade.

Conservative region: maximum

The maximum value means “this object had at least this many references.” Refusing decrements may retain garbage, but cannot reclaim live data.

Precision recovery: SATB

A later root-based trace ignores the imprecise arithmetic: marked means reachable; unmarked means dead even if the stored count is sticky.

Packed counters and the neighboring-count problem

Side metadata packs several small counters into one native word. Updating one object therefore performs a masked compare-and-swap over a word that also contains other objects’ counters. A correct retry loop must re-read the whole word after a failed CAS, replace only its own bit field, and preserve every neighbor exactly.

5. The implicit nursery: “young” means allocated since the last epoch

LXR does not require a permanently reserved semispace nursery. Time defines the nursery: objects allocated since the previous RC epoch start with count zero.

Paper Mutations inside newly allocated zeroed objects need not be logged. At the next RC epoch, only young objects receiving an external increment seed survive; the collector follows their outgoing edges to establish counts. A disconnected young cycle receives no seed and dies without cycle tracing. [P §2.1; PDF p.3]

“Promotion” here is temporal. It means a new object survived its first RC epoch and joined the mature counted graph. It need not cross a fixed address-space boundary, and copying may stop if reserve space runs out.

Why internal young-object writes need no old-image log

A newly allocated object did not exist at the previous epoch boundary. Therefore no reference from its fields can belong to the old graph whose decrements must be preserved. While the object is being initialized, replacing null or another new value inside it does not remove an edge that was counted at the last boundary. Suppressing those logs is the implicitly dead young-object optimization.

Old or root → young

This is a boundary edge. The final root/field scan contributes a seed increment. Without at least one such seed, the young subgraph remains dead.

Young → young / mature

When the first seed reaches a young object, promotion scans its outgoing fields. Young targets join the promotion traversal; mature targets receive ordinary increments.

Young copying is an optimization, not the liveness rule

Liveness is established by the seed-and-promotion traversal. Copying is possible because that traversal already enumerates incoming references to first-surviving young objects. LXR normally targets blocks containing only current-epoch allocations, packs the few survivors into partially free blocks, and releases the source block wholesale. If copy reserve is exhausted, it stops moving and establishes counts in place; correctness does not depend on successful copying. [P §§2.1, 3.3.2; PDF pp.3, 7–8]

CoreCLR P1.4 and P1.5 provide those generic capabilities; P2.3 does not yet connect them to an allocator or promotion packet.

6. SATB: recover cycles and saturated counts without stopping RC

Periodic mature-only tracing answers the question RC cannot: “is this positive count backed by a path from roots, or only by a cycle?”

Snapshot-at-the-beginning in plain language

A concurrent tracer sees a graph while the application changes it. SATB models the graph as it existed at trace start. If a field’s old value is overwritten while tracing, a pre-write/deletion barrier gives that old referent to the tracer. LXR reuses the same old referent already captured for RC. [Yuasa 1990; P §§2.2–2.3, 3.4; PDF pp.4, 8–9]

What triggers a backup trace?

  • Too few clean blocks remain after RC.
  • Predicted mature wastage (dead objects + fragmentation) crosses a threshold.
  • The evaluated mature-wastage threshold was 5%.

What the trace recovers

  • Disconnected mature cycles.
  • Dead objects whose count stuck at maximum.
  • Any mature garbage still carrying a nonzero count.

One SATB trace may span several RC epochs

  1. Begin at a normal RC pause. Snapshot roots and start concurrent mature tracing.
  2. Keep running normal RC epochs. Young and ordinary zero-count reclamation do not wait for tracing to finish.
  3. Before RC deletes an unmarked, unscanned mature object, mark and scan it. Its outgoing snapshot edges become visible before its storage is reused.
  4. Finish the trace. At the next RC pause, unmarked mature objects are trace-dead; clear their counts and reclaim them.
This is not local trial deletion. LXR does not discover cycles by speculatively subtracting internal edges. It uses a periodic global mature-only SATB backup trace.

Why the deletion barrier is necessary

A concurrent marker may have discovered object A but not yet scanned A’s field pointing to B. If the mutator clears that field first, a naïve marker can miss B even though B belonged to the graph at snapshot time. SATB solves this by preserving the deleted edge’s old target. In LXR, that old target is already the before-image needed for deferred RC, so one logged value serves both algorithms.

Deletion versus insertion: SATB needs the old value because it preserves the beginning-of-trace graph. A new edge inserted after the snapshot need not become part of that snapshot. RC still needs the slot’s final value as the after-image, so the same field log serves both different semantics.

Why LXR traces mature objects only

New objects start at RC zero and are handled by the implicit nursery. Tracing zero-count young objects would conservatively retain objects that did not exist at snapshot start—the classic SATB floating-garbage effect. LXR instead ignores zero-count objects in the backup trace and uses the RC promotion rules for young liveness. This both reduces work and keeps young reclamation precise. [P §3.2.2; PDF p.7]

How a trace safely crosses RC pauses

The safety invariant, stated precisely

While SATB is active, RC must not reclaim an unmarked and unscanned mature object whose outgoing edges may still be required by the initial snapshot. LXR does not need to retain the object itself until trace completion; it needs to publish its outgoing snapshot edges first. Mark-then-scan-before-reclaim satisfies that requirement and lets normal RC reclamation continue.

Trace trigger, priority, and completion details
  • The trace starts when clean blocks are scarce or predicted mature wastage crosses the configured threshold.
  • The paper’s evaluated mature-wastage threshold was 5%.
  • Lazy decrements run at higher priority than SATB work because they expose immediately reusable garbage.
  • At final mark, remaining unmarked mature objects are dead even when their RC is positive or sticky.
  • Counts for trace-dead objects are cleared before their lines are returned.

[P §3.2.2; PDF p.7; 304ce69d:src/plan/lxr/barrier.rs:136–175; 304ce69d:src/plan/lxr/global.rs:870–946]

7. Immix: fast bump allocation without giving up hole reuse

Immix divides memory into blocks and lines. Allocation is usually a fast bump through a contiguous run; collection can reuse free line runs inside partially occupied blocks; selective evacuation repairs fragmentation.

Allocation

Thread-local bump pointer, partially free blocks first, clean overflow blocks when a run is too small.

Large objects

Objects larger than half a block (16 KiB) use a separate large-object allocator.

Fragmentation

Reuse holes cheaply; occasionally evacuate low-occupancy blocks to recover whole blocks.

Paper parameter LXR uses 32 KiB blocks and 256-byte lines. The original 2008 Immix paper used 128-byte lines; do not transfer that value into LXR. [P §§2.6, 3.1; PDF p.5]

The allocation hierarchy

“Immix allocation” is not one free list. A thread normally owns a local cursor inside a line run. When that run cannot satisfy a request, it asks successively broader sources for space. The order is chosen to consume holes first and preserve clean contiguous blocks for objects or copying that genuinely need them.

Three different kinds of metadata are easy to confuse

An RC of zero does not by itself make a byte range allocatable. The death transition, outgoing-edge processing, straddle cleanup, line-availability update, and block ownership rules must agree before reuse.

Fragmentation: what Immix fixes and what it cannot hide

Reusable internal holes

If dead objects leave sufficiently large line runs, bump allocation can consume those runs directly. This recovers space without moving live neighbors.

Stranded small holes

Live objects may split a block into runs too small for incoming requests. Total free bytes can be high while useful contiguous capacity is low. Selective evacuation converts these fragments into whole free blocks.

Zeroing and reuse

Reused regions are zeroed before the mutator receives them. Whole free blocks can be zeroed in bulk, which is cheaper than interleaving small clears with every allocation. Zeroed memory also supports the young-object optimization: untouched reference fields are null, and initialization cannot expose a previous tenant’s pointers. [P §3.1; PDF p.5]

What P2.2 implements versus what P2.4 still owes

P2.2 implements checked block/line arithmetic, state bytes, owners, locks, and odd/even phase epochs. It can say whether a transition is valid. It does not yet maintain an allocation cursor, discover holes, skip unsafe partial tails, map object requests to free runs, zero returned memory, or publish a shipping block pool. Those are allocator semantics, not merely more state bits.

8. Straddle lines: keep a multi-line object from looking like a hole

An object can start in one line and continue through later lines. Those line starts are not object starts, but the allocator/sweeper still needs to know that their bytes belong to the earlier object.

continuation range = [align_down(S, 256) + 256, align_down(S + N, 256))

For object start S and size N, the .NET P2.3 substrate marks only full continuation lines. It excludes the first line and a partial final line. An object of 257 bytes starting exactly at a line boundary therefore has no full continuation line.

Reference

Paired sentinel

At each full continuation line start, the reference sets a straddle marker and an RC sentinel of 1. PLDI and HEAD use the same interval and order.

  • ReferenceCountStraddle(line) = 1

Write order matters. Marking stores straddle first, then RC. Clearing stores RC first, then straddle. A concurrent observation can therefore fail closed as inconsistent; it cannot silently reinterpret a stale RC=1 as a real object start. The accepted source is a9817282:src/coreclr/gc/reference_count.cpp:602–678.

Still needed in .NET The allocator-side “skip the first dead line” rule that makes partial-tail omission safe belongs to P2.4. P2.3 intentionally proves metadata semantics, not reclamation.

Read the half-open interval literally

align_down(S, 256) + 256 is the first line boundary strictly after the object’s start line. align_down(S + N, 256) is the boundary at or before the object end. Because the end is exclusive, only line starts whose entire line lies inside the object are emitted.

Why a continuation line is not an object start

The RC table is addressable on an 8-byte lattice, so a count stored at a line boundary could otherwise look like a real object’s count. P2.3 uses a three-part interpretation:

Mark and clear ordering as observable states

Mark: straddle → RC

  1. Store straddle = 1.
  2. Store RC = 1 at line start.

A reader between stores sees straddle=1/RC=0 and reports inconsistency. It never mistakes the half-written sentinel for a real object.

Clear: RC → straddle

  1. Store RC = 0.
  2. Store straddle = 0.

A reader between stores again sees an explicit inconsistency, not an apparently valid standalone RC=1 object.

Lifecycle and reuse

Returning or reassigning P2.2 block ownership does not prove that old objects died; therefore ownership handoff alone does not clear RC/straddle metadata or license overlap. Reclamation must first revoke the old object’s registration, clear its own count, and dismantle its derived continuation sentinels. P2.3 models that operation with ResetObjectQuiescent; the future allocator/sweeper will own when production code invokes the equivalent lifecycle.

Worked mid-line example

Let S = lineBase + 64 and N = 512. The object ends at lineBase + 576. 

first = align_down(S, 256) + 256 = lineBase + 256
end   = align_down(S + N, 256)   = lineBase + 512
range = [lineBase + 256, lineBase + 512)

Exactly one line start is marked: lineBase + 256. The bytes from 512 through 575 occupy a partial tail and receive no sentinel.

9. One LXR epoch, step by step

The algorithm is easiest to understand as three overlapping time domains: mutator logging, a short RC pause, then concurrent cleanup.

A. While mutators run

  1. Allocate zero-count young objects into Immix space. New-object initialization suppresses needless logging of internal writes.
  2. On the first write to an old field, log old referent + slot address. Later writes to that slot in the same epoch do not add more RC boundary work.
  3. If SATB is active, the same old referent preserves the initial snapshot. One barrier payload serves RC, SATB, and later evacuation remembered sets.

B. During the parallel stop-the-world RC pause

  1. Scan roots and increment current root targets. Save matching root decrements for the next epoch.
  2. Read every logged slot address and increment its final referent. This computes each modified field’s after-image.
  3. Finish all increments before any decrements. Avoid temporary zero when a reference merely moved.
  4. Trace first increments into young objects. Establish the reachable young subgraph’s counts and reclaim zero-count young garbage.
  5. Optionally copy young survivors or evacuate selected mature blocks. All movement is stop-the-world and bounded by known incoming slots.

C. After mutators resume

  1. Process old referents and previous root targets as lazy decrements. A 1 → 0 transition enqueues the dead object.
  2. Scan dead objects and cascade decrements through outgoing references. This recursive graph work can be long, so it runs concurrently.
  3. Sweep affected mature blocks and return reusable lines/blocks. If lazy work has not finished by the next pause, that pause completes it first.

Paper evidence Only avrora, lusearch, and xalan reported lazy decrement spillover into the next pause; xalan was the substantial outlier. [P §3.2.1, Table 7; PDF pp.6, 13]

What must be stop-the-world, and what may be concurrent?

Stop-the-world boundary work

  • Obtain a stable root set.
  • Freeze the current modified-slot boundary.
  • Apply final-slot and root increments before decrements.
  • Classify/promote current young objects.
  • Rewrite pointers while copying.
  • Finish previous lazy decrements if they spilled into this pause.

Concurrent after-boundary work

  • Process old-reference decrements and death cascades.
  • Sweep mature blocks affected by those cascades.
  • Advance mature-only SATB marking.
  • Build/maintain evacuation remembered information.

When does an RC pause start?

The design can trigger on heap fullness, accumulated increment work, or predicted young survival/work. The evaluated configuration used a 128 MiB survival threshold and no increment threshold. The survival predictor reacts faster when survival exceeds its prediction (¾ latest + ¼ old) than when it falls below (¼ latest + ¾ old), biasing toward avoiding unexpectedly large pauses. [P §§3.2.1, 4; PDF pp.6, 9]

Pause-overrun rule

The collector must never let unresolved decrements from epoch N coexist ambiguously with a new boundary that assumes epoch N is complete. If concurrent lazy work reaches pause N+1 unfinished, mutators are already stopped, so the pause drains the remaining work before establishing the next boundary. This makes the cost visible as a longer pause rather than weakening count correctness.

How the HEAD scheduler realizes this shape

304ce69d:src/plan/lxr/barrier.rs:136–175 flushes increment packets separately from decrement/SATB packets and routes lazy decrements to deferred concurrent work. global.rs:870–946 enables and disables scheduler buckets according to pause type, schedules RC, initial and final mark, emergency full-heap work, and previous-root decrements. The concrete scheduler is more complex than the conceptual three-phase diagram, but it preserves the same ordering edges.

Current .NET boundary: P1 provides barrier/store/allocation/ enumeration contracts and P2 provides metadata/state. No CoreCLR code yet creates these increment, decrement, zero-count, SATB, or sweep packets. This complete schedule is roadmap work, not a hidden mode behind P2.3.

10. Copying and evacuation: movement is selective, never concurrent

Young copying

On first survival, every incoming edge to a young object is already being enumerated. LXR can copy the survivor, pack it into partially free space, rewrite those edges, and free an all-young source block. If reserve space runs out, it establishes counts in place instead.

Mature evacuation

Before SATB, estimate occupancy from RC metadata, sort blocks under 50% occupancy, and choose a bounded evacuation set. SATB bootstraps incoming slot locations; the write barrier keeps the remembered set current.

Why remembered sets contain slots, not only source objects

Moving an object requires rewriting the exact memory locations that point to it. The remembered set therefore stores incoming reference locations. A line-reuse counter rejects stale entries whose source line died and was reused before evacuation.

Mature evacuation, from selection to release

  1. Estimate per-block occupancy from RC metadata. Consider blocks below 50% occupancy and sort the sparsest first.
  2. Choose a bounded evacuation set. Candidates come from a contiguous region (4 MiB or whole heap); the evaluated configuration used one set, limiting pause scope.
  3. Bootstrap incoming locations during SATB. When tracing sees a reference into a selected block, record the address of the slot containing that reference.
  4. Keep the remembered set current. Field logging observes later writes. Final slot values into the set become new incoming locations.
  5. Stop mutators and trace only into the set. Roots and remembered slots define the incoming frontier; unrelated heap objects do not need a full evacuation trace.
  6. Copy, forward, and rewrite. Allocate destination objects, publish old→new forwarding information, and rewrite every incoming slot.
  7. Release the emptied source blocks. The useful result is not just packed objects—it is whole blocks returned to the clean pool.

Why stale remembered-set entries are dangerous

A remembered entry is an address in the heap. If its source line dies and is reused, that same numeric address may now contain unrelated data. Treating it as a reference slot could corrupt a new object. LXR tags remembered entries with a line-reuse counter; a mismatch proves that the recorded slot belongs to an older incarnation of the line and must be discarded.

Remember source object only?

Insufficient. After moving the target, the collector would still need to rediscover which field or array element inside that source object to edit.

Remember exact slot address?

Directly rewritable, but only while the source line incarnation is still valid. The reuse counter supplies that temporal validity check.

Pinning changes the proof, not only the implementation

The reference implementation’s measured configuration treats is_pinned() as false and disables pinning work buckets. Its proof that every selected live object moves—and therefore every source block empties—depends on that premise.

CoreCLR cannot adopt the premise: fixed statements, interop, and runtime services can create heap-resident pinned objects. A correct port must either exclude pinned blocks from candidate sets, split sets around immovable objects, or retain partially evacuated sources with adjusted metadata. The choice affects candidate selection, forwarding, line availability, pause budgeting, and the condition for releasing a block. It is a first-class design obligation, not an edge-case branch.

11. What is needed to port coalescing LXR correctly?

The algorithm depends on runtime surfaces far outside a collector source file. Missing one store path or one lifecycle transition is a correctness bug, not a small performance loss.

Important reference-code correctness caveat

The PLDI oracle fails under sustained load in its normal barrier path: assert!(old.is_null() || rc::count(old) != 0) at df8d30a3:src/plan/barriers.rs:312–320. The condition spans lines 315–316.

A clean default run of HEAD does not prove that invariant there. HEAD removed the barrier-side check; its only equivalent assertion is 304ce69d:src/util/sanity/sanity_checker.rs:311–316, condition line 312, behind the non-default sanity feature.

Therefore the port uses “specify from PLDI, validate against HEAD after reinstating the invariant,” rather than treating either default binary as a complete executable specification.

Code-level barrier and scheduler flow at HEAD
  • flush_incs() packages increments into RC work.
  • flush_decs_and_satb() packages old referents for decrements and, when active, SATB.
  • Lazy decrements route to the concurrent work bucket; otherwise they enter stop-the-world decrement/sweep work.
  • global.rs enables/disables work buckets per pause type, schedules RC, initial/final mark, emergency full-heap work, zeroing, and defrag selection.

13. What exists in the CoreCLR port today

The port is deliberately building generic runtime capabilities first. LXR is the first consumer, not the definition of those contracts.

P2.1: fixed-address side metadata

Implemented P2.1 reserves metadata outside objects, commits pages only for represented data ranges, and supplies atomic bit/byte/word and masked packed-field operations. Concrete surfaces are side_metadata.h:37–53,90–147 and side_metadata.cpp:101–220.

P2.2: block state and phase epochs

Geometry

  • 32 KiB block (BlockLogBytes = 15)
  • 256-byte line (LineLogBytes = 8)
  • 128 lines per block
  • Objects may straddle lines, not blocks

State byte

  • 0: unallocated
  • 1..253: reusable with encoded unavailable lines
  • 254: marked
  • 255: unmarked

A global phase epoch starts at 1. Odd means normal execution; even means GC work. Each block also records an epoch. State + global epoch + block epoch derive nursery/reusing/GC-reusing predicates without embedding all modes in one state byte. This follows the HEAD mechanism rather than combining it with PLDI’s incompatible six-state representation.

P2.3: sticky RC facade and object lifecycle

Accepted start

8-byte aligned, owned, registered in ValidObject, at least 24 bytes, single block.

Rejected input

Interior/byref, misaligned, unregistered, cross-block, or a start inside a marked continuation line.

Lifecycle

Quiescent initialize, copy, object reset, range reset; copy re-derives destination sentinels.

  • Class unloading, compressed pointers, and weak references were disabled in every collector.

The accepted substrate benchmark has 57 rows: width operations for 2/4/8-bit configurations and contention controls at 1/4/16 workers. Its A/A control, extra-CAS slowdown, and injected-delay slowdown prove the harness responds to noise and known perturbations. It measures native RC/straddle operations and synthetic increment-heavy churn—not an allocator and not full LXR.

15. Common misconceptions

“LXR is pause-free or purely concurrent.”

False. Frequent parallel stop-the-world RC epochs are central. Lazy decrements and SATB are mostly concurrent; all copying is stop-the-world.

“Reference counting collects cycles.”

Zero counts cannot discover a closed cycle. LXR’s mature-only SATB backup trace finds cycles and saturated-count garbage.

“A sticky count eventually decrements again.”

No. Once maximum is reached, increments and decrements stop. Tracing decides whether the object remains reachable.

“LXR never moves objects.”

Incomplete. Most reclamation is non-moving, but young survivors and selected mature evacuation sets may be copied during pauses.

“LXR has a conventional copying nursery.”

Misleading. Young means allocated since the previous RC epoch. Copying all-young blocks is opportunistic and may fall back to promotion in place.

“The paper’s 1.6% barrier overhead is versus G1.”

False. The baseline is no-barrier full-heap Immix. The value is a geometric mean from this experiment and sits near a roughly ±3% noise scale.

“The current CoreCLR branch contains a working LXR collector.”

False. It contains enabling runtime contracts and P2.1–P2.3 metadata/state substrate. The allocator, work packets, sweep, SATB, evacuation, and collector integration are not implemented yet.

16. Glossary

After-image

The final value of a modified field at the RC epoch boundary.

Before-image

The old referent captured on the field’s first write in an epoch.

Coalescing

Replacing many intermediate field updates with one boundary decrement and one boundary increment.

Lazy decrement

A deferred decrement processed concurrently after the pause, including recursive death cascades.

Line

A 256-byte LXR Immix allocation/reuse unit inside a 32 KiB block.

RC epoch

The interval between two stop-the-world reference-count boundary operations.

SATB

Snapshot-at-the-beginning concurrent tracing, preserving referents that existed at trace start.

Sticky count

A saturated counter that refuses future increments and decrements until tracing reclaims the object.

Straddle line

A full line occupied by an object that began in an earlier line.

Temporal nursery

The set of objects allocated since the previous RC epoch, rather than a fixed nursery address range.
