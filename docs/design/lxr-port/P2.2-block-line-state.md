# P2.2 - Immix block and line geometry and phase state

P2.2 adds the collector-internal geometry and lifecycle substrate for Immix
blocks. It does not add a collector, allocator, sweep, or public/runtime
contract.

## Paper context

The local paper is Zhao, Blackburn, and McKinley,
*Low-Latency, High-Throughput Garbage Collection (Extended Version)*,
arXiv:2210.17175, 1 Nov 2022.

- Section 2.6, PDF p.5 defines the Immix hierarchy used here: 32 KiB blocks
  composed of 256-byte lines. Objects may span lines but not blocks.
- Section 3.1, PDF p.5 describes bump allocation into free and partially-free
  blocks and skipping unavailable lines. Allocation itself is not P2.2.
- Section 3.3.1, PDF p.7 describes returning empty blocks and partially-free
  blocks to separate global lists. P2.2 supplies the state needed by that
  later sweep.
- Section 3.5, PDF p.9 motivates low-contention issue of clean and recycled
  blocks at high allocation rates. P2.2 benchmarks this native substrate; it
  does not compare .NET timing directly with Java/MMTk.
- Section 5.4, PDF p.14 reports only 0.6% average improvement from halving the
  paper's 32 KiB block. That is sensitivity context, not a reason to alter the
  geometry.

Table 1 (PDF p.2) shows longer LXR pauses than G1 but better application query
latency. Table 5 (PDF p.11) shows heap-sensitive LXR/G1 throughput ratios of
0.97, 0.96, and 1.01. Table 7 (PDF p.13) is LXR-only for pause percentiles.
None of those values is a P2.2 microbenchmark threshold.

## Oracle decision

P0.3 row A05 declares the paper-era PLDI state machine, while D02 declares
HEAD's block allocation. The two representations are not composable:

- PLDI `df8d30a3:src/policy/immix/block.rs:12-80` puts
  `Nursery` and `Reusing` directly in a six-state byte.
- HEAD `304ce69d:src/policy/immix/block.rs:17-70` removes those two tags.
- HEAD derives nursery and reuse from a global and per-block phase epoch at
  `304ce69d:src/policy/immix/block.rs:311-374`.
- HEAD couples that epoch with block lock/owner and availability decisions at
  `304ce69d:src/policy/immix/block.rs:220-306` and
  `304ce69d:src/util/heap/blockpageresource_nosweep.rs:153-284`.
- The live LXR coordinator bumps the epoch at pause start and release at
  `304ce69d:src/plan/lxr/global.rs:297,327`.

Keeping PLDI `Nursery`/`Reusing` tags while adding HEAD's epoch would create
two sources of truth for the same lifecycle property. P2.2 therefore records
an explicit A05 exception: PLDI remains the geometry/terminology source and
comparison point, while HEAD is the single mechanics oracle for the coupled
four-state, epoch, lock, and owner unit. No hybrid or third oracle is used.

## Geometry

`ImmixBlockGeometry` fixes and statically checks:

| property | value |
|---|---:|
| block log bytes | 15 |
| block bytes | 32,768 |
| line log bytes | 8 |
| line bytes | 256 |
| lines per block | 128 |
| represented address limit | `2^47` |

The default values are present at both oracles:
`df8d30a3:src/policy/immix/block.rs:89-117`,
`df8d30a3:src/policy/immix/line.rs:20-29`,
`304ce69d:src/policy/immix/block.rs:78-133`, and
`304ce69d:src/policy/immix/line.rs:20-27`.

Conversions use half-open ranges. A zero-size range is empty. An exact
boundary end does not include the next line or block. `2^47` is accepted only
as an exclusive end. Addition and alignment are checked before mutation.
Object-range conversion rejects a range that crosses a block but permits
line straddling.

P2.2 maps no heap pages and allocates no objects.

## P2.1 metadata use

| plane | width | coverage | use |
|---|---:|---:|---|
| `BlockMark` | 8 bits | block | state byte |
| `BlockLog` | 1 bit | block | one-winner log claim |
| `BlockDefrag` | 8 bits | block | lifecycle clear; hole count deferred |
| `NurseryPromotion` | 8 bits | block | one-winner in-place promotion |
| `PhaseEpoch` | 8 bits | block | last acquisition/promotion phase |
| `BlockOwner` | 64 bits | block | opaque owner identity |
| `BlockInUse` | 8 bits | block | one-winner lifecycle lock |
| `LineReuse` | 8 bits | line | declared by P2.1; deferred to later remset work |

Initialization requires every plane P2.2 consumes before any represented data
range is committed. Missing/disabled metadata fails explicitly. Manager-wide
epoch reset walks P2.1's existing merged data ranges and rounds each outward
to the selected plane's granularity, so an unrelated non-block-aligned P2.1
range cannot make wrap fail.

The fixed layout remains 64-bit-only and bounded to 47 data-address bits.
Windows x86 fails closed. WebAssembly cannot provide the fixed reservation.

## Block state

The HEAD byte representation in `BlockMark` is:

| raw | state |
|---:|---|
| 0 | `Unallocated` |
| 1-253 | `Reusable` with raw unavailable-line count |
| 254 | `Marked` |
| 255 | `Unmarked` |

The decoder remains total like the oracle. P2.2 can create only reusable
counts 1 through 128.

There is no arbitrary public state store. Operations use the following
transition relation:

| from / to | `Unallocated` | `Unmarked` | `Marked` | `Reusable(n)` |
|---|---|---|---|---|
| `Unallocated` | fresh mutator initialization or release | fresh GC copy or in-place promotion | forbidden | forbidden |
| `Unmarked` | release | idempotent prepare/copy | trace mark | reusable result |
| `Marked` | release | trace prepare/copy | idempotent mark | reusable result |
| `Reusable` | release | trace prepare/copy | trace mark | updated reusable result |

Mutator acquisition requires an odd global epoch. GC-copy, trace, promotion,
and reusable-result operations require an even epoch. Invalid-phase and
invalid-state requests do not modify metadata.

Post-lock availability follows
`304ce69d:src/util/heap/blockpageresource_nosweep.rs:153-182`.
A reusable mutator block must not already be reusing in the current mutator
phase. A reusable copy block must be neither mutator-reusing from the prior
phase nor GC-reusing in the current phase. Normal clean-copy acquisition
rejects a prior nursery; the explicit `GcMatureEvacuationFresh` kind is the
oracle's `mature_evac` exception and accepts that clean block. P2.2 does not
implement owner stealing or pool selection.

## Ownership and synchronization

P2.1's sequentially-consistent masked operations update state, lock, owner,
log, promotion, and per-block epoch. This is stronger ordering than some
HEAD relaxed operations but preserves its state and predicate results.

Lifecycle mutation follows:

1. enter the block-operation/phase-transition gate;
2. claim `BlockInUse` from 0 to 1;
3. re-read state, epoch, and owner after the claim;
4. publish owner and lifecycle metadata;
5. clear the lock after publication.

The global gate prevents a phase bump from interleaving with an in-flight
phase-sensitive block operation. The per-block post-lock recheck prevents a
contender from applying an expected state after another owner completed a
state cycle. There is no cross-plane atomic instruction; the gate and lock
are the synchronization boundary.

Outcomes distinguish update, idempotence, lock contention, stale eligibility,
and invalid transition. P2.1 reservation/commit/address errors are propagated
separately.

## Phase epoch

One collector-scoped atomic byte starts at `1`. Each represented block has a
P2.1 `PhaseEpoch` byte initially zero.

The predicates match
`304ce69d:src/policy/immix/block.rs:333-359`:

```text
nursery_or_reusing =
    global odd  ? block_epoch == global
                : block_epoch == global - 1

nursery    = state == Unallocated && nursery_or_reusing
reusing    = state != Unallocated && nursery_or_reusing
gc_reusing =
    state != Unallocated && global even && block_epoch == global
```

`gc_reusing` follows the oracle's state-first order: an unallocated block
returns false even outside the GC phase, while an allocated block queried in
an odd phase is rejected.

Pause start changes odd to even. Release changes even to odd. At even epoch
254, release follows the reference order at
`304ce69d:src/policy/immix/block.rs:366-374`: publish global epoch 1, then
zero every represented block epoch. The block-operation gate makes that
store/reset pair unobservable and keeps mutators stopped until reset
completes. A reset failure restores the global epoch to 254 before releasing
the gate; the reset path prevalidates all ranges before changing any block
epoch.

Zero cannot equal post-wrap global epoch 1. Consequently, an untouched block
from an earlier cycle cannot alias a newly stamped block after wrap.

## Lifecycle boundary

P2.2 implements:

- represented-range registration;
- fresh/reusable mutator acquisition;
- fresh/reusable GC-copy acquisition;
- the mature-evacuation clean-copy exception;
- owner return and block deinitialization;
- trace preparation, block mark state, and reusable result state;
- log claim/reset and in-place nursery promotion;
- phase changes and predicates;
- quiescent reset and shutdown.

P2.2 does not implement:

- an allocation cursor, object allocation, or a shipping block pool;
- line marking, hole counting, or sweeping;
- heap-page mapping/release;
- RC, SATB, evacuation, copying, or forwarding.

P2.3 may consume the checked line ranges and reusable-state operation but must
not add a second hole/state plane. P2.4 may supply mapped blocks and register
their ranges but must not replace P2.1 address translation.

## Default runtime path

Product and smoke sources are compiled only when
`CLR_CMAKE_ENABLE_IMMIX_BLOCK_STATE_TEST=1`. The AMD64-only option defaults
off and fails configuration explicitly on another target architecture. The
test-enabled linked CoreCLR and standalone GC export only
`GC_ImmixBlockStateTest_Run`; no normal Workstation/Server allocation or
collection path calls it.

On Unix the P2.2 export is appended to the export set selected by the other
validation features. A combined-feature build verifies that the P2.2,
write-barrier, and allocation-notification exports coexist.

Default builds contain no `immix_block` or smoke-test source object, branch,
call, or export. The P2.1 manager's generic reset-all helper is compiled as
part of `side_metadata.cpp` but has no default-path caller. This compile-time
and call-site absence is the normal-GC non-interference evidence; P1.7 is not
used to make a broader regression claim.

## Validation and performance evidence

`P2.2/immix-block-validation.cpp` compiles the product sources directly
against the P2.1 OS shim. It enumerates geometry boundaries, all 256 raw state
bytes, legal/illegal transitions, metadata failures, one-winner operations,
concurrent acquisition and phase contenders, both epoch bumps, and the
254-to-1 wrap.

`P2.2/run-immix-block-runtime-smoke.ps1` executes the exported smoke in linked
and standalone Workstation/Server modes. Linux product-path runs are
distinguished from the OS-shim validator.

The native/BenchmarkDotNet harness characterizes:

- geometry, metadata mapping, state CAS, and pool-only lower bounds;
- fresh acquire/release, reusable acquire/return, and GC-copy acquire/return;
- 1, 4, and 16 persistent workers;
- same-block contention and epoch changes;
- duplicate A/A, sixteen extra block-log claim/reset pairs, and an injected
  delay while a block remains owned.

The declared evidence run is three launches, eight warmups, and twenty
measured iterations. A/A must remain within `[0.90, 1.10]`; extra CAS must be
at least 1.5x; injected owner delay must be at least 1.25x. Absolute rates are
characterization, not acceptance thresholds. `EpochChanges` uses the single
phase coordinator; its three `WorkerCount` rows intentionally repeat the
same coordinator operation and are not independent scaling evidence.

Raw evidence, exact source/runtime/machine identities, archive-gate results,
and limitations are recorded under `P2.2/raw/` only after the immutable source
commit is created. The standalone verifier checks every source hash against
that committed archive. Git ancestry and the requirement that source and
evidence be distinct commits are enforced by the archive gate, because an
extracted archive intentionally contains no `.git` directory.
