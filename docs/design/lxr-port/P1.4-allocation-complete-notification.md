# P1.4 — Exact generic allocation-complete notification

**Status:** implemented; validation and performance evidence are under
`P1.4/raw/`.

## 1. Scope and base

P1.4 adds an opt-in, collector-neutral callback for successful managed heap
births. It reports the object, its exact aligned object extent, stable runtime
allocation facts, and an opaque collector context after the runtime object
shape is valid and before managed/profiler publication.

The implementation base is the `lxr` integration tip
`8b4f037f82a92395f304b716c8a630aba2ec20d3`.

| dependency | commit |
|---|---|
| final P1.1 barrier-shape contract | `f4971fe7d2bc4dafb8b1280445e7bdc5f0bb6568` |
| P1.2 x64 slot-log family | `a75c0bb0afd932cca7c38da8f3dabc8afa06d415` |
| P1.3 complete store/bulk coverage | `94ff421641854c5491359e141c70e6b6122bbe11` |

The complete P1.1-P1.3 `WriteBarrierParameters` layout remains unchanged:
152 bytes on x64, 84 bytes on x86, with the 5.12 bulk tail at offsets 136 and
76. P1.4 does not add a write-barrier field, shape, helper, flag, or status.

This is runtime enablement only. It does not initialize RC metadata, select an
RC width, implement LXR policy, or expose a managed API.

## 2. Oracle

The allocation/lifecycle oracle is the executable HEAD shipped pair:

- `mmtk-openjdk` binding `0682434`;
- `mmtk-core` `304ce69d`.

HEAD is selected because it has runtime `PlanSelector::LXR`, the cleaner
LXR/Immix split, and the runnable lifecycle selected for the coupled block
allocation mechanism:

- `304ce69d:src/plan/global.rs:39-70,73-110`;
- `304ce69d:src/plan/lxr/global.rs:96-105`.

Both pinned cores expose generic `post_alloc`:

- PLDI `df8d30a3:src/memory_manager.rs:166-182`;
- HEAD `304ce69d:src/memory_manager.rs:303-319`.

Both delegate to the selected space's metadata initialization:

- `df8d30a3:src/plan/mutator_context.rs:92-100`;
- `304ce69d:src/plan/mutator_context.rs:256-264`.

The shipped configurations matter:

- PLDI builds with `GC_FEATURES=lxr,immix`; LXR is compile-time and
  `global_alloc_bit` is not enabled.
- HEAD builds the runtime-selectable plans and runs with `MMTK_PLAN=LXR`;
  `LXR_CONSTRAINTS.rc_enabled` is true.

Neither oracle provides the contract implemented here:

- PLDI explicitly calls `post_alloc` only from its slow binding allocator and
  records the fast-path omission:
  `abbdd1d:openjdk/mmtkMutator.cpp:16-29`.
- Its heap-level call is commented:
  `abbdd1d:openjdk/mmtkHeap.cpp:476-481`.
- HEAD's default fast allocation returns raw memory directly and calls the
  generic hook only for non-default allocation semantics:
  `0682434:openjdk/mmtkHeap.cpp:587-613` and
  `0682434:openjdk/mmtkMutator.cpp:25-51`.
- LOS performs real birth work in both:
  `df8d30a3:src/policy/largeobjectspace.rs:72-100` and
  `304ce69d:src/policy/largeobjectspace.rs:100-121`.

P1.4 therefore supplies the missing CoreCLR capability required to establish
exact birth metadata. RC width remains collector-owned and tunable; no width
is encoded in the callback.

## 3. Interface 5.13

The GC interface remains major 5 and advances from minor 12 to 13. The EE
interface remains major 4.

P1.4 appends one final `IGCHeap` slot with a source-compatible disabled
implementation:

```cpp
virtual AllocationNotificationParameters*
    GetAllocationNotificationParameters()
{
    static AllocationNotificationParameters parameters = {};
    return &parameters;
}
```

The fixed 5.13 descriptor is:

```cpp
struct AllocationNotificationParameters
{
    AllocationNotificationRequestStatus request_status;
    alignas(void*) AllocationCompleteCallback callback;
    void* context;
};
```

Layouts:

| field | x64 | x86 |
|---|---:|---:|
| status | 0 | 0 |
| callback | 8 | 4 |
| context | 16 | 8 |
| structure size | 24 | 12 |

Zero initialization means disabled: null callback/context and `NotProcessed`.
An unchanged 5.12 collector source rebuilt with the 5.13 header inherits this
process-lifetime static descriptor, remains concrete, and requires no source
edit. The runtime writes `Accepted` or `Unsupported`. A collector override must
return non-null process-lifetime storage; null is malformed and fails before
`IGCHeap::Initialize`. After acceptance the runtime's copied callback/context
is authoritative and descriptor mutation has no effect.

The callback is:

```cpp
void callback(
    Object* object,
    size_t aligned_object_size,
    AllocationCompleteFlags flags,
    void* context);
```

`aligned_object_size` includes runtime header, payload, and trailing object
alignment. It excludes any preceding alignment filler/free object.

Flags:

| flag | meaning |
|---|---|
| `ContainsReferences` | the MethodTable contains GC references |
| `Finalizable` | finalization was registered during allocation |
| `LargeObjectHeap` | LOH placement |
| `PinnedObjectHeap` | POH placement |
| `Array` | managed array, including MD arrays |
| `String` | managed string |
| `BoxedValueType` | heap object is a boxed value type |
| `Collectible` | MethodTable belongs to a collectible loader allocator |
| `PayloadMayBeUninitialized` | zeroing was optional and the payload may contain stale bytes |
| `FrozenObjectHeap` | runtime FOH birth |

The opaque context avoids forcing a collector-global singleton and costs one
fourth x64 argument register.

## 4. Negotiation and immutability

`GC_Initialize` first returns the configured `IGCHeap`. Before `FinalizeLoad`
publishes it and before allocation helper binding, CoreCLR:

1. calls the final slot only for exactly major 5, minor 13 or later;
2. requires initial `NotProcessed`;
3. validates callback/context, x64 support, ReadyToRun state, and allocation
   context mode;
4. copies callback/context and writes `Accepted`, or writes `Unsupported` and
   fails initialization;
5. forces TLS allocation contexts in accepted mode, so the locked Windows
   `_UP` helpers cannot bypass ordering;
6. binds the notifying helper family once, before any JIT compilation.

An enabled 5.13 collector checks for `Accepted` in its later
`IGCHeap::Initialize`. On an older runtime the slot is never called, status
remains `NotProcessed`, and initialization fails with `E_NOTIMPL`.

| pairing | result |
|---|---|
| unchanged 5.12 source, rebuilt with 5.13 header/runtime | inherited zero descriptor accepted; Workstation and Server start |
| existing 5.12 binary, 5.13 runtime | old vtable prefix; notification disabled |
| 5.13 disabled collector, 5.13 runtime | accepted; default helpers |
| enabled 5.13 collector, supported CoreCLR AMD64 | accepted before managed execution |
| enabled 5.13 collector, 5.12 runtime | `NotProcessed`; collector fails closed |
| enabled collector with ReadyToRun | `Unsupported`, `E_NOTIMPL` |
| enabled collector on non-AMD64 | `Unsupported`, `E_NOTIMPL` |
| enabled NativeAOT image | `Unsupported`, exit before managed `Main` |
| major above 5 | 5.13 slot hidden; enabled request fails on `NotProcessed` |
| override returning null | malformed; `E_FAIL` before `IGCHeap::Initialize` |

No JIT-EE API, helper ID, JIT/EE GUID, ThunkGenerator entry, CorInfoImpl method,
or SuperPMI packet is added. Existing helper IDs and startup binding are
sufficient.

## 5. Allocation-complete boundary

The callback marks runtime birth, not constructor or semantic payload
completion.

At entry:

- sync-block state is empty;
- MethodTable is installed;
- SZ array/string length is installed;
- MD array component count, bounds, and lower bounds are installed;
- finalizer registration has completed;
- reference storage is GC-safe;
- aligned size and placement/type facts are available.

Not promised:

- instance constructor completion;
- boxed value copy;
- MemberwiseClone payload copy;
- jagged-array child allocation;
- COM backing-object completion;
- application field initialization beyond allocation defaults.

Normal GC-heap callbacks run cooperative and cannot move the object. FOH is
the sole mode exception: after MT/length initialization, the callback runs
preemptive while the FOH allocation lock serializes births and before the
segment is registered with the GC.

Every callback is no-throw, no-GC, non-blocking, allocation-free, and
non-reentrant. It cannot switch GC mode, enter managed code, take a
GC-dependent lock, or retain the unrooted raw pointer for later dereference.

## 6. Path ledger

| allocation path | realization |
|---|---|
| x64 object fast helper | separate `RhpNewFast_Notify`; MT/frontier publication, then no-GC callback before return |
| x64 ref/value array fast helpers | separate notifying helpers; MT/length precede callback |
| x64 string fast helper | separate notifying ECall target |
| helper rare path | tail-jumps unchanged slow helper without pre-notifying |
| runtime/slow object, SZ/MD array, string | one `PublishObjectAndNotify` funnel with exact aligned size |
| boxing / nullable boxing | `InternalAllocNoChecks_FastPath`; nullable null emits zero |
| runtime async continuation | same internal fast allocator before continuation linking |
| Activator/reflection/GetUninitializedObject | cached selected helper; callback before constructor/return |
| MemberwiseClone | birth callback before payload copy; optional-zero flag for uninitialized array payload |
| finalizable | slow path after registration |
| LOH/POH | placement flags; one callback before return |
| runtime FOH | serialized pre-registration callback; later profiler publication suppresses a second callback |
| explicit preinitialized frozen segment | rejected while enabled |
| collectible | ordinary helper plus `Collectible` fact |
| COM wrapper | managed wrapper birth only; cached RCW reuse emits zero |
| interpreter | regular helpers plus the separately audited `InternalAllocNoChecks_FastPath` |
| allocation sampling | registered mode defers event until after callback/MT |
| profiler/heap ETW | generic callback precedes profiler and heap-allocation event |
| GC stress/refill/retry | only final successful formatted object reaches callback |
| OOM/overflow/fault | zero callbacks |
| stack allocation / dead allocation | no managed heap birth, zero callbacks |
| alignment filler/free object | GC bookkeeping, zero callbacks |
| survivor copy/relocation | existing object identity, zero callbacks |

The exhaustive allocation-context write audit found only the shared
architecture fast helpers, portable/non-x64 helpers rejected by negotiation,
the Windows `_UP` helpers made unreachable by TLS selection, and
`RuntimeTypeHandle::InternalAllocNoChecks_FastPath`.

## 7. x64 ABI

Default `AllocFast.asm` and `AllocFast.S` are untouched. New CoreCLR-only
MASM/GAS objects define notifying variants.

Each variant keeps its allocation test and slow tail-jump in a leaf entry.
Fast success jumps to a separate unwindable epilogue that:

1. reserves Windows shadow space or records System V CFI;
2. publishes the pending TLS frontier and saves the object result;
3. invokes the ordinary-ABI no-GC trampoline;
4. restores the object in `RAX` and returns.

Allocation helpers are already ordinary JIT calls, so existing ABI-volatile
GPR/SIMD/opmask kills remain correct. No specialized JIT kill set changes.

## 8. Ordering

- Fast TLS: MT/length stores → allocation-frontier store → no-GC callback →
  return. The cooperative thread cannot reach a safepoint, so GC cannot observe
  the object before callback completion; publishing first also makes a
  contract-violating nested allocation non-aliasing.
- Runtime internal fast allocation uses the same MT → frontier → callback →
  return order.
- Slow SOH: GC allocation succeeds → shape initialization → callback, with no
  intervening GC trigger.
- UOH: shape initialization → callback → explicit GC publication.
- FOH: shape initialization → callback under serialization → segment
  registration → profiler/event publication → managed root/return.
- Profiler callbacks remain under `GCPROTECT` and may move the object only
  after generic notification.
- Failed allocation never reaches publication.

The callback call itself is a compiler barrier. Concurrent metadata consumers
must use the collector's appropriate atomic ordering.

## 9. Validation

The managed matrix covers ordinary/ref-containing objects, arrays of refs and
values, MD arrays with lower bounds, strings, boxes and nullable boxes,
Activator, `GetUninitializedObject`, MemberwiseClone, finalizable and
collectible types, LOH, POH, FOH, optional-zeroing arrays, fast/forced-slow
helpers, refill, multi-thread uniqueness, interpreter, tiering/OSR, and
Release stack-allocation exclusion.

The native validator asserts 5.13 enum/layout values on x64 and x86 and freezes
the unchanged 5.12 write-barrier structure.

Executed configurations and exact evidence paths are in
`P1.4/raw/validation-summary.csv` and `platform-summary.csv`. Important
controls include:

- `run-allocation-source-compatibility.ps1` rebuilds the exact P1.3/5.12 GC
  binary and runs it on the current runtime, rejects the current enabled binary
  on the 5.12 runtime, then rebuilds the old source with only the current header
  overlaid and starts Workstation and Server. It proves a one-site
  `PURE_VIRTUAL` perturbation fails with `C2259`, restores the header, rebuilds,
  and repeats both startups. Null overrides fail closed on both current and 5.12
  runtimes (14/14 controls);
- the 5.12-runtime legs replace `coreclr.dll` and `corerun.exe` in the complete
  current `Core_Root`; P1.4 changes no managed runtime assembly, so this isolates
  the native loader/vtable gate without claiming an unrelated old library build;
- the existing GC allocation profiler verifies that its `ObjectAllocated`
  object is the callback's matching preallocated native record and that the
  record carries the expected LOH/POH placement bit; explicit dropped-bit and
  swapped-bit perturbations both make the profiler test fail;
- the registered-counting benchmark resolves the count-only counter from the
  executing runtime, resets it, forces 4,096 escaping object births in every
  benchmark process, and requires a scaled callback delta; selecting the empty
  callback under the same expectation is an executable negative control;
- validation consumer fails against the old capability;
- a null descriptor fails before managed execution and before the built-in
  `GCHeap::Initialize` dereference;
- malformed context/callback returns `E_INVALIDARG`;
- ReadyToRun returns `E_NOTIMPL`;
- NativeAOT exits `-1` before `Main`;
- removing either architecture callback call, the runtime-internal fast hook,
  the ReadyToRun gate, the inherited default, the counting increment/cardinality
  check, or the profiler placement comparison makes the committed verifier
  fail.

## 10. Performance and identity

Measurements use the same no-PGO Release runtime, ReadyToRun and tiering off,
and record Workstation/Server separately.

Three callback arms are measured:

- unregistered;
- registered empty callback;
- registered atomic-count callback.

BenchmarkDotNet covers ordinary objects, boxes, finalizable objects, byte/ref
arrays, and strings from empty/minimum sizes through 8 KiB and the LOH
boundary. The harness `allocation-churn` scenario supplies paired AB/BA
end-to-end invocations.

The short local run used one launch, one warmup, and three measured
iterations. It is sufficient to characterize the cost shape, but not to claim
precision for noisy large-object rows:

| GC | operation | unregistered | empty callback | counting callback |
|---|---|---:|---:|---:|
| Workstation | small object | 4.55 ns | 8.31 ns (1.83x) | 12.46 ns (2.74x) |
| Server | small object | 5.33 ns | 8.98 ns (1.68x) | 13.37 ns (2.51x) |
| Workstation | 16-byte array | 5.43 ns | 9.93 ns (1.83x) | 13.29 ns (2.45x) |
| Server | 16-byte array | 7.03 ns | 10.65 ns (1.52x) | 21.50 ns (3.06x) |
| Workstation | 1 KiB array | 57.36 ns | 54.26 ns (0.95x) | 61.36 ns (1.07x) |
| Server | 1 KiB array | 95.88 ns | 113.19 ns (1.18x) | 130.59 ns (1.36x) |

The representative small-allocation signal is roughly 3.6–4.5 ns for the
empty callback and 7.9–14.5 ns for the atomic-count callback in this short run.
All 48 registered-counting benchmark processes observed exactly 4,097
callbacks for the 4,096-object probe plus its root array. Larger-object and LOH
ratios cross 1.0 and are reported as noisy rather than as speedups or
regressions.

Five paired allocation-churn ratios per GC are much more consequential:

| GC | registered-empty / unregistered throughput | range |
|---|---:|---:|
| Workstation | 0.8580 mean (0.8578 geomean) | 0.8413–0.8872 |
| Server | 0.7557 mean/geomean | 0.7485–0.7620 |

The registered path therefore has material residual cost: about 14% in this
Workstation churn scenario and 24% in Server. P1.4 does not hide or defer this
result; it is the evidence P1.7 must use when choosing later optimizations.
The compatibility follow-up reruns every microbenchmark arm because the
counting evidence changed. It retains the paired churn data because neither
the registered-empty callback nor any allocation helper changed, and rebuilt
Debug/Release helper `.text` still matches the disabled baseline exactly.

not a contract for this service.

## 11. Limitations

- P1.4 executes the registered fast path on AMD64 only.
- ReadyToRun and NativeAOT remain fail-closed until their image contracts can
  prove all preinitialized births.
- Other targets are cross-built or source-audited and are not described as
  executed.
- The callback cannot perform arbitrary collector work; it must reduce birth
  handling to bounded no-GC metadata/TLS operations.
- The full Checked runner was executed after a successful complete test build
  and a separate successful Priority 1 build. It returned exit 0 after 23,881
  tests (23,707 passed, 166 skipped, 29 covered by active issues), but still
  reported eight missing native/generated test-asset failures: six COM client
  executables, `RunBasicTestWithMcj.cmd`, and `PlatformNativeR2R`. Those are
  reported as infrastructure limitations, not as passing tests. All focused
  P1.4 matrices and the allocation profiler test pass.
