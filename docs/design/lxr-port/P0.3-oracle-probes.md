An oracle is defined by the brief as *the pair the binding actually builds with no override*. That
makes the `mmtk-core` half of each oracle a **cargo git checkout**, not a working tree. Every
`mmtk-core` working tree on this machine is at a *named* revision that is not an oracle:

### 1.1 The preferred citation basis: `git show <rev>:<path>` against the read-only reference

A cargo checkout is a machine-local cache that cargo may prune, so it is a poor thing for a design
record to depend on. The read-only reference clone is better, and it turns out to be sufficient:
**all four revisions exist as objects in `C:\github\lxr-reference`**, even though neither working
tree is checked out at an oracle. So every citation resolves without touching the checkout:

```text
git -C C:\github\lxr-reference\mmtk-core    show df8d30a3:src/plan/barriers.rs
git -C C:\github\lxr-reference\mmtk-core    show 304ce69d:src/plan/lxr/barrier.rs
git -C C:\github\lxr-reference\mmtk-openjdk show 0682434:openjdk/barriers/mmtkFieldBarrier.cpp
```

`show`, `ls-tree` and `cat-file` are read-only; nothing is checked out, fetched or written. This
also confirms the revision topology directly from the object store:

| revision | `src/plan/lxr/` contents |
|---|---|
| `df8d30a3` (PLDI oracle) | *does not exist* |
| `4d4e516c` (PLDI named) | *does not exist* |
| `304ce69d` (**HEAD oracle**) | 9 flat files: `barrier.rs`, `cm.rs`, `gc_work.rs`, `global.rs`, `mature_evac.rs`, `mod.rs`, `mutator.rs`, `rc.rs`, `remset.rs` |
| `9625c174` (HEAD named) | `barrier.rs`, `block_allocation.rs`, **`gc_work/`** (a directory), `global.rs`, `mature_evac.rs`, `mod.rs`, `mutator.rs` |

The difference is one of **shape, not just count**: `9625c174` moved GC work into a `gc_work/`
subdirectory and added `block_allocation.rs`, while `cm.rs` and `remset.rs` exist **only** at the
oracle. Any citation of the form `src/plan/lxr/gc_work/<file>.rs` therefore names a path that does
not exist at the declared oracle.

`scripts/verify-ledger.sh` resolves every citation this way and additionally proves the two bases
agree: for all **50** distinct files cited by this step, the cargo checkout is byte-identical to the
reference clone's blob at the pinned revision (`identical: 50  differing: 0  absent locally: 0`).
Citations derived from the cargo checkouts therefore transfer unchanged.

> **Convention for the design record.** A citation of the form `src/... : line` is meaningless
> unless the revision is named. Every citation in the ledger is written
> `<oracle> <short-hash> <path>:<line>` and resolves with `git show <rev>:<path>` against
> `C:\github\lxr-reference`.

## 3. P0.1 §16 open items resolved by reading the oracles

### 3.1 `CM_LARGE_ARRAY_OPTIMIZATION` true → false is a vestigial flag, not a behavioural flip

- PLDI `args.rs:9` `= true`, consumed at `src/util/cm.rs:116–126`: object arrays longer than 1024
  are split with `data.chunks(...)` into separate work packets.
- HEAD `args.rs:87` `= false`, and the **only** other occurrence in the tree is the `dump_feature!`
  at `args.rs:173`. The flag has no consumer.
- The optimization did not disappear — it became **unconditional**, reimplemented at
  `src/plan/lxr/cm.rs:258–266` and `:666–674` as `ObjectKind::ObjArray(len) if len >= 1024`. Same
  threshold.

**Closes P0.1 §16 item 4**, and eliminates it as a candidate cause for §5.

### 3.2 `RC_LOCK_BITS`: the removal is real, and it is not a weakening — it inverts P0.1's guess

| | PLDI `df8d30a` | HEAD `304ce69` |
|---|---|---|
| function | `plan/barriers.rs:290–298` `log_edge_and_get_old_target` | `plan/lxr/barrier.rs:86–96` `log_slot_and_get_old_target` |
| protocol | lock via a **separate** `RC_LOCK_BIT_SPEC` (`:231` `attempt_to_lock_edge_bailout_if_logged`, `:257` `unlock_edge`, `:268` `log_and_unlock_edge`) → load `old` **inside** the critical section → log + unlock | bail if already logged → load `old` **before** any CAS → CAS the unlog bit (`attempt_to_log_field`, `:60`) |
| memory ordering | `Ordering::Relaxed` throughout | `Ordering::SeqCst` |
| constant | `LOG_BYTES_PER_RC_LOCK_BIT` `args.rs:57` | survives at `args.rs:117`, dumped at `:171`, **no consumer** — vestigial, same pattern as §3.1 |

**Assessment — flagged as reasoning, not observation.** The dedicated lock bit was removed, but the
log-bit CAS itself linearizes which thread gets to record `old`, and the ordering was *strengthened*
from `Relaxed` to `SeqCst`. Under P0.1 §15's own rule the removal is therefore **not semantic in the
sense that matters**, so coupled sets A and B stay separate rather than collapsing into one.

**Inference, not observation:** PLDI's blanket `Relaxed` ordering across the slot-logging protocol is
a plausible root cause of PLDI's own `zero rc count` violation — there is no happens-before edge
between logging a slot and the RC operations that later consume it. This is not tested here and is
recorded as a candidate only. See §6.1 for why it does not need to be tested for the port to proceed.

**Closes P0.1 §16 item 3**, in the opposite direction to the one P0.1 guessed.

### 3.3 `plan/concurrent/` exists at the HEAD oracle — but LXR does not use it

P0.1 §18.2/§18.3 recorded `plan/concurrent/` as post-oracle and downgraded HEAD's concurrent marking
to `[obs-override]` on that basis. Both halves need correcting:

- It **exists at the HEAD oracle**: `plan/concurrent/{barrier.rs 163, concurrent_marking_work.rs 309,
  global.rs 10, mod.rs 29}` plus `plan/concurrent/immix/{gc_work.rs 25, global.rs 452, mod.rs 7,
  mutator.rs 130}`.
- But `src/plan/lxr/` contains **no** `use crate::plan::concurrent` — it is a *sibling* plan, a
  generic concurrent-marking substrate that LXR does not consume. LXR's concurrent marking lives in
  `plan/lxr/cm.rs`.

**Therefore HEAD's LXR concurrent marking is `[obs-oracle]`, not `[obs-override]`** — it was in the
shipped build and executed. The §18.3 downgrade was based on a file that is present, and on a
dependency that does not exist. Both the premise and the conclusion were wrong.

## 4. Probe 1 — does the HEAD oracle uphold PLDI's zero-RC invariant?

### 4.1 Why the probe was necessary: the existing claim was vacuous

P0.1 records "HEAD never trips the `zero rc count` assertion, in any configuration". Reading both
oracles shows that claim could not have been tested:

- PLDI `df8d30a3` `src/plan/barriers.rs:313–319`, inside `FieldLoggingBarrier::slow`. The span is
  worth stating precisely because it is easy to cite the wrong line: `:313` is the `fn slow`
  signature, `:314` the `cfg` gate, `:315` the `assert!(` token, **`:316` the condition**, `:317` the
  format string, `:318` its argument `old`, and `:319` the closing `);`. The assertion *statement* is
  therefore `:315–319`; the coordinator's brief cited `:317`, which is the line a `grep` for the
  literal `zero rc count` returns, and an intermediate revision of this document cited `:315–317`,
  which stops one argument short. Written out below with the source's own line breaks removed.

  ```rust
  #[cfg(any(feature = "sanity", debug_assertions))]
  assert!(old.is_null() || rc::count(old) != 0, "zero rc count {:?}", old);
  ```

- HEAD `304ce69d` `src/plan/lxr/barrier.rs::slow()` (line 98) contains **no RC-count assertion**. The
  only assertion in that entire 246-line file is `debug_assert!(self.should_create_satb_packets())` at
  `:179`. The equivalent invariant survives only at `src/util/sanity/sanity_checker.rs:311–316`, on
  the **sanity-GC** path, which is a different code path gated on a feature neither shipped build
  enabled (`scripts/build-shipped.sh`: PLDI `GC_FEATURES=lxr,immix`, HEAD none). At `304ce69d`
  `Cargo.toml` declares `sanity = []` with `# default = ["sanity"]` commented out, so nothing turns
  it on implicitly.

Verified at the binary level rather than by reading alone:

```text
strings <lib> | grep -c 'zero rc count'
  pldi-fastdebug-shipped.so   2      <- the assertion is compiled in
  head-fastdebug-shipped.so   0      <- it is not present at all
  probe1 instrumented .so      1      <- re-instated by this probe
```

The 0 is independently meaningful: the sanity-path message at `sanity_checker.rs:313` reads
`"{:?} -> {:?} has zero rc count"`, which **would** have matched this grep had it been compiled in.
Its absence therefore confirms the sanity feature was compiled out of the shipped HEAD build, rather
than merely confirming that the barrier-side assertion is gone.

So HEAD's fastdebug runs could not have tripped a check that is not in the binary. The claim was
**unfalsified, not verified** — and the brief's binding "specify-from-PLDI, validate-against-HEAD"
rule rested on it.

### 4.2 Method

`scripts/probe1-build.sh`, `scripts/probe1-run.sh`; the positive control of §4.4 uses
`scripts/probe1-control-build.sh` and `scripts/probe1-control-run.sh`.

1. Fresh root `/root/lxr/probe1/`; `mmtk-core` cloned at `304ce69d` and selected through the
   binding's own documented `path` override. `/root/lxr/{pldi,head}` and `so-backup` untouched.
2. **One** edit: PLDI's invariant re-expressed in HEAD's API inside `LXRFieldBarrierSemantics::slow()`
   — HEAD's `Option<ObjectReference>` old-target form and the `self.lxr.rc.count(o)` accessor.
   No other source change.
3. Built fastdebug (`MAKE_EXIT=0`); presence of the assertion string confirmed in the built `.so`
   before running anything.
4. DaCapo 2006, the same 8 benchmarks as P0.1, `-n 5`, 3 invocations, at **2000 MB and 500 MB** —
   P0.1's method, so the numbers are comparable, and 500 MB because P0.1 established the PLDI failure
   is load-dependent.
5. **Every** log scanned, not one directory — P0.1 §7.3 records that scanning one of seven produced a
   wrong conclusion once already.
6. Shipped `.so` restored on exit via `trap restore EXIT`; restoration verified by `cmp`.

**This is a third configuration, not "HEAD".** It is the HEAD oracle source plus one added assertion,
built by cargo's `dev` profile (`Finished \`dev\` profile [unoptimized + debuginfo]`, so
`debug_assertions` is on) inside the fastdebug JDK. The `sanity` feature was **not** enabled — the
`cfg` gate is satisfied by `debug_assertions` alone. Nothing here is a parity baseline.

| | runs | PASSED | logs containing `zero rc count` | panics / SIGSEGV |
|---|---|---|---|---|
| HEAD oracle + PLDI's invariant, 2000 MB | 24 | 24 | **0** | 0 |
| HEAD oracle + PLDI's invariant, 500 MB | 24 | 24 | **0** | 0 |
| **total** | **48** | **48** | **0** | **0** |

### 4.4 Positive control — was the assertion site actually reached?

A null result is only evidence if the code under test executes. §4.2 step 3 proves the assertion was
**compiled in**; it does not prove it **ran**. Without this control, "48/48 clean" would be the same
*shape* of claim as P0.1's vacuous "HEAD never trips it" — a silence that could mean either "the
invariant held" or "nothing evaluated it".

`scripts/probe1-control-build.sh`, `scripts/probe1-control-run.sh`. Same oracle copy, same `cfg`
gate, same build recipe; the invariant is replaced by a reach counter that logs at every power of
two. A logging counter is preferable to one that aborts: it yields a magnitude rather than a bit, and
the run completes normally.

| benchmark | heap | PASSED | slow-path reaches with a non-null old target |
|---|---|---|---|
| lusearch | 2000 MB | yes | **≥ 4 096** |
| hsqldb | 2000 MB | yes | **≥ 65 536** |
| xalan | 2000 MB | yes | **≥ 8 192** |

Counts are power-of-two lower bounds, one process each, `-n 5`. The plan was confirmed to be LXR from
the runtime banner rather than assumed — `MMTK_VERBOSE=3` prints `barrier: "FieldBarrier"` and the
`lxr_no_nursery_evac` / `lxr_no_lazy` / `lxr_no_cm` argument block.

These counts are smaller than a naive "one per reference write" estimate, and the reason is
structural rather than suspicious: `slow()` is reached only via `enqueue_node`
(`src/plan/lxr/barrier.rs:126–131`) when `log_slot_and_get_old_target` **wins** the log-bit CAS, so it
fires once per *slot* rather than once per write, and the counter only counts the non-null-`old` case
that the invariant constrains.

**So probe 1's null result is a real negative.** The invariant was evaluated tens of thousands of
times per process, across 48 processes, and was never violated.

**The HEAD oracle upholds PLDI's invariant under exactly the load that trips PLDI**, at both heap
sizes, including the 500 MB configuration where PLDI fails hardest. Provenance `[obs-override]`: an
instrumented build that never shipped, so it is evidence about the invariant and not a parity
baseline.

This is the first *evidence* — as opposed to an untested premise — that the specify-from-PLDI,
validate-against-HEAD rule has a valid validation oracle.

## 5. Probe 2 — the hsqldb p99 anomaly: **resolved**

P0.1 §6.2 recorded, like-for-like at `-n 5` @2000 MB: PLDI p99 **0.34–0.40 ms**, HEAD p99
**54–56 ms**. The brief requires this be resolved or retired, not carried.

**It is resolved.** The cause is not an LXR mechanism difference at all. Five stages; the first four
eliminated seven candidate causes, and the fifth found the cause and proved it.

### 5.1 Stage 1 — timeline (`scripts/mk-harness-timeline.sh`, `scripts/probe2-timeline.sh`)

The P0.1 meter reported percentiles only. It was extended to emit every sample with a timestamp, then
recompiled with each oracle's own release JDK. No MMTk rebuild.

| | stalls > 5 ms | total stall | p99 | max | wall |
|---|---|---|---|---|---|
| HEAD ×3 | **25, 25, 25** | 1893–1914 ms | 59.3–63.0 ms | 137–174 ms | 4391–4505 ms |
| PLDI ×3 | **0, 0, 0** | 0 ms | 0.35–0.42 ms | 1.3–4.5 ms | 3370–4312 ms |

P0.1 reproduced exactly. Two structural facts fell straight out and turned out to be the whole
answer:

- **Exactly 5 stalls per DaCapo iteration, in all 5 iterations, in all 3 invocations.** Perfectly
  deterministic — not a heap-pressure or scheduling phenomenon.
- The first stall of each iteration is the largest (107–145 ms), then four of ~56–88 ms.

### 5.2 Stage 2 — ablation of `LAZY_MU_REUSE_BLOCK_SWEEPING` (`scripts/probe2-ablation.sh`)

The planning-stage hypothesis. Present and effectively `true` at PLDI (`args.rs:10`, consumed at
`policy/immix/immixspace.rs:460` and `policy/immix/block_allocation.rs:299`), entirely absent at HEAD.
Set to `false` at PLDI, rebuilt release, re-measured.

Choosing a source ablation over toggling the `lxr_lazy` *feature* was correct, and is now
evidence-backed rather than assumed — PLDI `Cargo.toml:110` reads
`lxr_lazy = ["lxr_basic", "lxr_lazy_decrements"]`, so the feature toggle would have moved two
variables.

**Hypothesis falsified:** p99 0.35–0.48 ms, 0–1 stalls, max 2.6–8.0 ms. Marginal tail growth, two
orders of magnitude short of 54 ms. Binding and `.so` restored.

### 5.3 Stage 3 — runtime knob sweep (`scripts/probe2-knobs.sh`)

HEAD reads a large set of runtime knobs at `args.rs:44–70` that PLDI exposes only as
`Lazy<Option<…>>` statics defaulting to `None` (`args.rs:86–183`). One is a genuine default
inversion: `MAX_SURVIVAL_MB` is `None` at PLDI and **128** at HEAD, and hsqldb's live set is ~117 MB
— close enough to the threshold to be suspicious. `MAX_SURVIVAL_MB`, `RC_STOP_PERCENT`,
`TRACE_THRESHOLD` and `MAX_YOUNG_EVAC_SIZE` were swept on the shipped HEAD build, no rebuild.

**All four completely inert:** 25 stalls, ~1.94 s total, p99 ~60 ms in every configuration.

### 5.4 Stage 4 — eager decrements at HEAD (`scripts/probe2-nolazy.sh`)

`LAZY_DECREMENTS` is `cfg!(feature = "lxr_lazy_decrements")` at PLDI (`args.rs:49`) and

**All 25 pauses are `Pause::Full`, every one labelled `cause=UserTriggered`.** Not one `RefCount`

The chain, read at both oracles:

1. `dacapo/hsqldb/PseudoJDBCBench$MemoryWatcherThread.reset()` calls **`System.gc()`** and then

2. **The `handle_user_collection_request` overrides that print `"The request is ignored."` are not

   HEAD `:376`). That feature appears in neither oracle's `default` list (HEAD: `dep:sysinfo`,

   as a dependency of no other feature in either `Cargo.toml`. Under `GC_FEATURES=lxr,immix` neither
   line exists in the binary. *An earlier revision of this document cited these two lines as the
   oracles' behaviour. That was wrong, and it is the failure mode of §7's second habit: the code is
   right there, it reads correctly, and it does nothing.*
3. **The live chains differ in kind, not in degree — HEAD services the request and PLDI cannot.**

   | | what actually happens on `System.gc()` |
   |---|---|
   | **HEAD** `304ce69d` | **services it.** `src/memory_manager.rs:686` → `src/mmtk.rs:436` → `src/util/heap/gc_trigger.rs:143`; at `:149` `if force \|\| !*self.options.ignore_system_gc && VM::VMCollection::is_collection_enabled()`, then `:158–160` stores `user_triggered_collection` and `:161` requests the collection. `src/plan/lxr/global.rs:614` reads the flag and `:643` promotes: `if emergency \|\| user_triggered \|\| hint_emergency_gc { … Pause::Full }`. **A first-class promoter to a full-heap STW collection.** |

   - **PLDI's `ignore_system_g_c` option (`src/util/options.rs:179`, default `false`) is inert.** Its

### 5.6 Proof

If the diagnosis is right, suppressing explicit GC at HEAD must remove the pauses entirely.
`-XX:+DisableExplicitGC`, HEAD, hsqldb @2000 MB, `-n 5`, two invocations each:

| HEAD configuration | pause census | stalls > 5 ms | total stall | wall |
|---|---|---|---|---|
| default | 25 Full, 25 Full | 25, 25 | 2056 ms, 2016 ms | 4692 ms, 4492 ms |
| `-XX:+DisableExplicitGC` | *(empty — no GC at all)* | **0, 0** | **0 ms** | **2856 ms, 2895 ms** |

Zero collections, zero stalls, and wall time falls by ~39 %. The anomaly is fully accounted for.

### 5.7 What this means — including a correction to my own earlier reading

- **The hsqldb p99 gap is a difference in induced-collection policy, not in any LXR mechanism.** No
  ledger row moves from HEAD to PLDI as a result. The stage-2 hypothesis that sweeping and block
  allocation would have to move is dead.
- **P0.1 §6.2 was measuring `System.gc()` handling, not LXR steady-state latency.** At 2000 MB with
  explicit GC suppressed, HEAD performs *no collections at all* across the whole run — so that
  configuration carries no information about LXR's own pause behaviour on hsqldb either way. Any
  future latency comparison on hsqldb must either suppress explicit GC or treat induced full GCs as
  the thing being measured, and say which.
- **Correction to an intermediate conclusion of my own.** After stage 1 I recorded that "HEAD's
  mutator is ~1.7× faster and pays for it in STW pauses — a throughput/latency redistribution rather
  than a regression". That was wrong, and stage 5.6 disproves it: with induced GCs removed HEAD is
  faster in wall time than PLDI (2.86–2.90 s versus PLDI's 3.37–4.31 s) **and** has zero stalls. The
  ~1.9 s was not work moved out of the mutator, it was additional work the other oracle never did.
  Recorded here because it was very nearly written into the ledger.
- **It is directly portability-relevant, and gets its own ledger row (C05).** .NET's `GC.Collect()`
  is a documented public API with defined semantics, so the port must choose deliberately among
  **three** design points — not the two an earlier revision of this document offered:

  | | behaviour | precedent at the oracles |
  |---|---|---|
  | **(a)** | ignore the request | HEAD ships it as the **runtime** option `ignore_system_gc` (`304ce69d` `src/util/options.rs:869`, default `false`), tested at `src/util/heap/gc_trigger.rs:149`. PLDI reaches the same behaviour by having no live handler at all. |
  | **(b)** | service it as an ordinary collection, **without** promoting to full-heap | no oracle exhibits this at runtime; it is the shape of PLDI's own code were its body uncommented (§5.5 corollary 2) — recorded as inference, not observation. |
  | **(c)** | service it **and** promote to full-heap STW | HEAD's default (`304ce69d` `src/plan/lxr/global.rs:643`) — costs the ~60 ms per call this probe measured on a ~117 MB live set. |

  `GC.Collect()` being public API with documented semantics rules out **(a)** as a *silent default*;
  it does not rule it out as a *configurable mode*, and HEAD's `ignore_system_gc` is the precedent
  that it belongs in the options surface rather than in the plan. **(b)** is the point .NET most
  plausibly wants — it honours the API contract that a collection occurs without inheriting the
  full-heap pause — and it is the one the earlier two-point framing omitted entirely. The choice is a
  decision the port must make and measure, not inherit.

## 6. The two questions the step must close

### 6.1 Q1 — is root-causing the PLDI `zero rc count` violation on the critical path?

**No.** Recorded with its reason and, unlike the prior record, with evidence behind it.

The honest sequencing matters. On the evidence available at the start of this step the answer had to
be *yes* — not because PLDI's defect mattered in itself, but because the premise that made it
skippable ("HEAD holds the invariant") had never been tested and, per §4.1, **could not** have been:
the check is absent from HEAD's source and from HEAD's shipped binary. Recording "not on the critical
path" then would have been recording an absent check as a passing one.

Probe 1 supplied the missing test. **48/48 runs pass with PLDI's invariant re-instated at the HEAD
oracle, at 2000 MB and 500 MB, with zero occurrences of the assertion** — and §4.4's positive control
establishes that this silence is a real negative rather than a second vacuous one: the assertion site
executes **≥ 65 536 times per process** on hsqldb, ≥ 8 192 on xalan, ≥ 4 096 on lusearch. That
settles which world we are in: PLDI's violation is an implementation defect of a 2022 research
snapshot that the codebase subsequently fixed, not a property of the algorithm.

Consequences for the ledger:

- The brief's **specify-from-PLDI, validate-against-HEAD** rule for coupled sets A and B is
  **vindicated with evidence**, and rows A01–A05 and B01–B05 carry a real validation oracle.
- Root-causing PLDI is **downgraded to a recorded curiosity**, not a gate. §3.2 names a candidate
  (PLDI's blanket `Relaxed` ordering in the slot-logging protocol, strengthened to `SeqCst` at HEAD)
  and flags it as an untested inference.
- **The residual obligation is transferred to the port, not dropped.** The invariant is cheap and it
  is the one that PLDI actually violated, so ledger rows A04 and B02 require the .NET realization to
  carry it as a debug assertion from the first commit. That is what makes not root-causing PLDI safe:
  the port checks the invariant itself rather than trusting that it holds.

### 6.2 Q2 — the hsqldb p99 anomaly: resolve or retire

**Resolved**, not retired. Cause: hsqldb's `MemoryWatcherThread` calls `System.gc()`; HEAD promotes
any user-triggered collection to `Pause::Full` while PLDI excludes user-triggered from its pause
selection. Proven by suppressing explicit GC at HEAD, which removes all 25 pauses and all stalls.
Full derivation in §5; consequences in §5.7; the port-side obligation is ledger row **C05**.

Seven candidate causes were eliminated with evidence along the way and are recorded so they are not

Neither would have been caught by running it once and reading the exit code.

Two further changes came out of the same report:

- **The expected row count was a literal `26` in three places.** It is now derived from the index
  table, and §4's self-reported "Rows total" is checked against it — so the document's own stated
  total is now an audited claim rather than prose, and adding or retiring a row cannot leave the gate
  passing while under-checking.
- **Eleven scripts were CRLF in the Windows worktree** (`i/lf w/crlf`). Committed content was always
  LF and `.gitattributes:24` already says `*.sh text eol=lf`, so a fresh clone was never affected —
  but the worktree copies failed `bash` with `$'\r': command not found`, which is why every run in
  this step went through `tr -d '\r'` into a converted copy. **The passing results before this commit
  therefore attest to converted copies, not to the files as committed** — true of the content, which
  is identical, but not a claim the runs themselves could make. Normalized in place; the other ten
  produced a zero-byte content diff, confirming only the worktree encoding differed. The gate now
  runs directly from the worktree and from a clean extract.

## 9. What was not verified

- **PLDI's own `zero rc count` root cause.** Not investigated; §3.2 names an untested candidate.
  Deliberate, per §6.1.
- **PLDI's pause census.** Stage 5 ran the census on HEAD only. PLDI's equivalent needs a rebuild
  with the `log_gc` feature; `scripts/probe2-gclog.sh pldi` implements it but was not run, because
  §5.6 already proved the diagnosis from the HEAD side and PLDI's source shows directly that a
  user-triggered collection can never even be requested there — `plan/global.rs:590–598` is an empty
  handler, so `user_triggered_collection` is never set.
- **Whether other DaCapo benchmarks are affected.** They cannot be: §5.5 established that
  `PseudoJDBCBench$MemoryWatcherThread` is the only `System.gc()` call site in the suite. Not
  separately measured.
- **Probe 1 at heap sizes other than 2000 MB and 500 MB**, and beyond `-n 5`. The invariant could
  still be violated at HEAD under some load not tried. 48 clean runs is evidence, not proof.
- **The positive control's exact reach count.** §4.4 reports power-of-two lower bounds, and it was
  run on 3 of the 8 benchmarks at one heap size, not on all 48 probe-1 configurations. It establishes
  that the site is exercised heavily; it does not quantify each run.
- **The `-XX:+DisableExplicitGC` configuration was not run on PLDI** — PLDI already has zero stalls,
  so there is nothing for it to show.
- Every ledger row's .NET realization is a **design statement, not a measurement**. Nothing in this
  step builds or runs CoreCLR.
- **§1c's gate analysis is a heuristic, not a compiler.** It counts braces on source text with string
  and comment literals stripped, so it can be fooled by unusual formatting, and it cannot see a
  `#[cfg]` applied at a module declaration in another file unless that gate is listed in the script's
  `MODULE_GATES` table (one entry today, for `src/util/sanity/`). It is designed to over-report and
  force acknowledgement, not to decide. **No attempt was made to enumerate every `#[cfg]` in either
  oracle** — only the gates covering this document's own 122 citations.
- **Whether the reference's `object_pinning` code even compiles** in a full LXR configuration. Row
  R05's `cfg`-gated citations are never built by either oracle's recipe, so nothing here — and
  nothing in P0.1 — demonstrates that they type-check alongside LXR. Not tested; building it would be
  a fourth configuration and is out of this step's scope. Note that it would still not produce a
  parity oracle: LXR's `PinningProcessEdges = UnsupportedProcessEdges` and its disabled pinning
  buckets are *not* gated on `object_pinning`, so enabling that feature would not switch LXR onto a
  working pinning path.
